Regular V2 API — 編輯定期購方案 實作規劃

對應 EPIC：定期購支援贈品_202607。

本文件為 nine1.regularpurchase.v2 下游 API 的實作規劃文件，聚焦後端內部設計決策與異動範圍。不涵蓋 OSM 前端實際呼叫的 Api/RegularProduct/Edit 對外規格（SMS ApiResultEntity 包裝、前端錯誤文案對照等），該部分待後續另行整理為獨立的前端對接 Spec 文件。

1. 背景與目標

現況 EditProductAsync（PUT /api/regular/products/{productNo}）僅能修改配送設定，且以 productNo 定位「單一啟用中商品」。但同一商品頁可能對應多筆方案（不同生效期間），需求要求：

  • 以 planId（rpd_pk）精準定位單一方案
  • 依方案狀態（尚未生效／生效中／已結束）限制可修改欄位範圍
  • 開放方案名稱、生效結束時間、贈品缺貨處理等既有 Edit 不支援的欄位
決策：新增一支獨立的 API，不修改/共用舊有 PUT /{productNo} 相關程式（DTO／Validator／Service 方法／Controller Action 皆獨立）。舊路由暫不處理，維持現況。

3.1 商品頁序號（RpdPageId / SalepageId）可編輯性與換頁風險處理 ✅ 已定案（依需求原文修正）

修正說明：原規劃「任何狀態皆不可異動（含尚未生效）」為風險評估建議，並非需求規定。核對 EPIC 需求原文後，需求明確要求「尚未生效」狀態應開放所有欄位編輯（含商品頁序號）；僅「生效中」「已結束」鎖定商品頁序號。本節修正為依需求原文的最終結論，並補上對應的換頁防呆設計。
結論：「尚未生效」狀態開放修改商品頁序號（換頁）；「生效中」「已結束」鎖定，與 DB 現值不同即整筆驗證失敗。

為何「尚未生效」開放換頁的風險相對可控

「尚未生效」方案尚未實際出貨，沒有任何訂單快照依賴目前的商品頁綁定關係，換頁不會造成歷史訂單資料不一致；相對「生效中」方案已有訂單依此設定持續出貨，換頁會直接影響進行中的訂單，風險不對等，故僅在「尚未生效」開放。

風險來源（換頁時仍需處理）

修改商品頁序號等同「換綁商品頁」，需要處理：① 新商品頁：驗證交期為定期購、非點數商品、未結束銷售，成功後開啟該商品頁定期購標記；② 舊商品頁：判斷是否還有其他方案在使用，若無則關閉其定期購標記（SalePage_IsClosed = true），若有則維持開啟 —— 這是風險核心，需新增防呆檢查。

SalePage_IsClosed 是商品頁的全站共用欄位，並非定期購專屬，會被以下多處共用/引用：

  • GetStatusValidList（一般購買資格判斷，SCMAPIV2／SalePageService.cs line ~1766：AND SalePage_IsClosed = 0）
  • 贈品商品頁邏輯（SaleProductGiftService）
  • 促銷引擎排名（PromotionEngineService）
  • 變更時會觸發全站事件 SalePageClosed / SalePageOpened（FireEvents，SalePageService.cs line ~2101-2105）

且同一商品頁可能有多筆非重疊的定期購方案（例如方案 A 換到別的商品頁後，舊商品頁可能仍被方案 B 使用中），若換頁時貿然關閉舊商品頁，會誤傷其他仍在使用的方案，因此必須新增防呆檢查。

既有行為佐證（「開」是既有、已驗證過的路徑）

SMS 前端（C:\91APP\NineYi.Sms\WebSite\WebSite\TypeScripts\Modules\SalePage\edit.controller.ts line 3129-3135）：商品頁建立/複製時，若交期選擇「定期購」且供應商為支援的第三方 Provider，前端會主動強制關閉商品頁：

// 定期購，provider 為支援的第三方廠商，預先關閉商品頁 if ( this.Model.ApplyType === this.ApplyTypeValue.RegularOrder.Name && this.IsSupportedRegularOrderProvider(this.RegularOrderProvider) ) { this.Model.IsClosed = true; }

（對照組：一般商品/複製商品頁預設 IsClosed: false 開啟，見同檔 line 2963 註解「複製商品頁，預設開啟」）

V2 AddProductAsync（RegularProductService.cs line ~409, 711）：新增定期購方案成功後，主動呼叫 UpdateSalePageIsClosedOfRegularOrderAsync(apiProfile, request.ProductNo, isClosed: false)，把商品頁打開，代表「方案設定完成，可以正式對外開放購買」。此呼叫失敗僅 LogWarning，不影響主流程（try/catch 吞例外，與 V1 行為一致）。

完整迴圈：SMS 建立商品頁時強制關閉 → 品牌方設定定期購方案（AddProductAsync）→ V2 主動打開商品頁。這個「關 → 開」的迴圈設計良好且已在正式環境運行、驗證過，換頁時的「開新頁／關舊頁」比照此既有慣例延伸設計。

換頁防呆設計 ✅ 已定案

新增 Repository 方法判斷舊商品頁是否還有其他方案在使用：

/// <summary>判斷指定商品頁除了 excludePlanPk 外，是否還有其他「尚未生效」或「已生效」方案在使用</summary> Task<bool> ExistsOtherActivePlansByPageIdAsync(long shopId, long pageId, long excludePlanPk);
  • 換頁成功寫入（UpdateAsync）後：先對新商品頁呼叫 UpdateSalePageIsClosedOfRegularOrderAsync(newPageId, isClosed: false) 開啟
  • 再呼叫 ExistsOtherActivePlansByPageIdAsync(oldPageId, excludePlanPk: planId)：
    • 若無其他方案使用舊商品頁 → 呼叫 UpdateSalePageIsClosedOfRegularOrderAsync(oldPageId, isClosed: true) 安全關閉
    • 若有其他方案使用中 → 維持開啟，不做任何動作
  • 開關頁呼叫皆比照既有 AddProductAsync 慣例：失敗僅 LogWarning，不影響主流程、不回滾方案本身異動

決策

  • 「尚未生效」開放修改 RpdPageId（換頁），並執行上述換頁防呆設計；「生效中」「已結束」鎖定，與 DB 現值不同即整筆驗證失敗
  • 換頁時新商品頁需通過完整 SCM 驗證（交期定期購、非點數商品、未結束銷售），並檢查與其他方案是否重疊（見第 7 節）

4. DTO 設計決策：獨立新增 ProductEditPlanRequest

4.1 決策理由

  • Repo 既有先例：ProductAddRequest 與 ProductEditRequest 雖欄位高度重疊，但並未共用，各自獨立且有獨立 Validator
  • 新舊兩支 API 的定位鍵（ProductNo vs PlanId）、欄位範圍、驗證規則差異過大，共用會讓 Validator 條件式越疊越複雜
  • 舊路由已決定「暫不處理」，共用 DTO 等於間接牽動舊路由行為，違反此決定

4.2 欄位規劃 ✅ 已定案

5. Validator 設計：ProductEditPlanRequestValidator

驗證類型放置層理由
純欄位格式驗證Validator不需外部 I/O，比照 ProductAddRequestValidator 慣例
狀態鎖定比對（需查 DB 取得現值）✅ Service需查詢 Repository，屬有 I/O 的驗證，比照 ValidateSalePageDataForAddAsync 先例放 Service 層
SCM 商品頁驗證Service 層需呼叫 SCM API
已確認：狀態鎖定比對放在 Service 層，新增 private method（例如 ValidateFieldLockByPlanStatusAsync），Validator 僅負責純格式驗證，不查 DB。此設計與 EditProductByPlanAsync 流程草案（第 6.1 節第 4 步）一致。

5.2 Validator 涵蓋規則（純格式，無 I/O）

  • PlanId／ShopId／ProductNo > 0
  • PlanTitle 字數上限（全半形混合 20 字／純半形 40 字，沿用 ProductAddRequestValidator 邏輯）
  • PlanDateEnd 須晚於 PlanDateBegin
  • ProductShippingPeriod 不可為空
  • ProductShippingSet 值域 1/2/3；ProductShippingMax/ProductShippingFixed 條件必填與範圍（2~99）
  • ProductPurchaseOption 值域 1/2
  • RegularProductPromotionRules 至多 1 筆；陣列內 Interval 範圍、GiftItemList 數量/加總上限（複用 RegularProductPromotionRuleValidator）

6. Service 設計：EditProductByPlanAsync

6.1 流程草案

1. 呼叫 Validator（純格式驗證）→ 失敗直接回傳 Failure 2. LoadByPlanAsync(shopId, planId) → 查無 → Failure「查無此定期購方案」 3. 依 DB 現值計算 PlanStatus（沿用 GetPlanStatus） 4. 依狀態鎖定矩陣，比對 Request 傳入值 vs DB 現值： - 有差異的鎖定欄位 → 立即 Failure，不繼續往下執行（all-or-nothing） 5. 呼叫 SCM 取得 salePageData，驗證： - 商品交期為定期購、非點數商品（複用 ValidateSalePageData） - 商品尚未結束銷售 - 生效結束時間不得晚於商品銷售結束時間（複用/抽出 Add 共用邏輯） - 若 ProductNo（RpdPageId）與 DB 現值不同（換頁，僅「尚未生效」允許）：對新商品頁執行同樣的 SCM 驗證 6. ExistsOverlappingPlanAsync(shopId, pageId, planDateBegin, planDateEnd, excludePlanPk: planId) → 重疊 → Failure「此商品序號於指定生效期間已存在重疊方案」 7. 組裝更新後的 entity（僅更新狀態允許的欄位，其餘沿用 DB 原值做雙重保險） 8. UpdateAsync(entity) 9. 若換頁：呼叫 UpdateSalePageIsClosedOfRegularOrderAsync(newPageId, isClosed:false) 打開新商品頁； 再呼叫 ExistsOtherActivePlansByPageIdAsync(oldPageId, excludePlanPk:planId)，若無其他方案使用舊商品頁， 呼叫 UpdateSalePageIsClosedOfRegularOrderAsync(oldPageId, isClosed:true) 關閉舊商品頁（皆比照 Add 慣例，失敗僅 LogWarning，不影響主流程） 10. 清除 GetRegularSettingAsync 快取（換頁時新舊 PageId 快取皆需清除，見 11.3 節） 11. 回傳 Success「成功儲存定期購方案」

7. Repository 設計決策：ExistsOverlappingPlanAsync 加 Optional 參數

已確認採用方案：加 Optional 參數，不使用 Overload 或 Request 物件包裝。
Task<bool> ExistsOverlappingPlanAsync( long shopId, long pageId, DateTime? planDateBegin, DateTime? planDateEnd, long? excludePlanPk = null);

7.2 決策理由

方案評估
Optional 參數（採用）與既有 repo 慣例一致（LoadByProductAsync/LoadByPlanAsync 已用 status = 1 模式）；Add 呼叫端零異動；SQL 僅一份

11.1 🔴 UpdateAsync SQL 目前缺少本次所需欄位 ✅ 已定案

好消息：RegularProductEntity（BE 層）早已具備這幾個欄位（RpdPlanTitle／RpdPlanDateBegin／RpdPlanDateEnd／RpdPromotionJson，分別於工作項目 #647549／#651076 新增），只是 UpdateAsync 的 SQL SET 子句忘了加上去，不需異動 Entity，僅需擴充 SQL。

  • 兩個 Service 方法各自組好完整的 entity（沿用 DB 舊值 + 套用新值）後呼叫同一支 UpdateAsync，行為清楚、易懂

11.2 贈品規則 Id 保留邏輯 ✅ 已定案

現況 EnsurePromotionRuleIds（RegularProductService.cs line ~600）僅在 rule.Id 為空時補 Guid。Edit 情境下既有規則的 Id 必須保留原值，因為訂單快照（歷史訂單回溯）依賴此 Id 對應到當初下單時的贈品規則。

核心原則：Id 對 Id 更新——同一筆規則的生命週期應延續同一個 Id，不應該無故產生新 Id。

設計依據第 3 節欄位可編輯矩陣自然推導：

欄位尚未生效生效中已結束
贈送條件 Interval、贈品內容 GiftItemList✅❌❌
贈品缺貨處理 OutOfStockAction✅✅❌
贈品開關（有無這筆規則）✅❌❌

由此可知：「生效中」狀態下，規則本身是否存在、Interval、GiftItemList 都被鎖死必須與 DB 現值相同，唯一可能被改動的只有 OutOfStockAction——本質上是同一筆規則的欄位微調，不存在「換一筆規則」的可能性；「尚未生效」狀態下規則可整筆新增/移除/改動核心內容，此時方案尚未生效、不可能有訂單快照到這筆規則，即使產生新 Id 也沒有回溯風險。

最終處理邏輯：

方案狀態Id 處理方式
生效中Service 組裝最終 entity 時，規則 Id 一律強制沿用 DB 現值，完全不採信前端傳入的 Id（因規則內容已被鎖定為與 DB 相同，等同同一物件）
尚未生效寬鬆處理：前端有傳 Id 就沿用（Id 對 Id），沒傳或傳空則視為新規則，呼叫既有 EnsurePromotionRuleIds 產生新 Id
已結束不適用，任何贈品欄位異動皆整筆驗證失敗，不會走到組裝階段

此設計不需要額外設計「內容比對救援」邏輯（例如比對 Type/Interval/GiftItemList 是否相同來猜測是否為同一筆規則）——「生效中」狀態下由狀態鎖定機制保證內容必然相同，因此直接以 DB 現值的 Id 覆寫即可，無需比對，是最簡單且可靠的做法。

11.3 快取清除範圍 ✅ 已定案（換頁需雙 Key 清除）

修正說明：原規劃假設 RpdPageId 恆鎖定、快取 Key 不會變，因此只需複製 EditProductAsync 的單一清除邏輯。現依需求原文，「尚未生效」狀態允許換頁，快取 Key（由 ShopId + PageId 組成）會改變，需同時清除新、舊兩個 PageId 對應的快取 Key，否則舊 Key 的快取會殘留過期資料（TTL 24h 內讀到舊的 RegularSettingData）。
