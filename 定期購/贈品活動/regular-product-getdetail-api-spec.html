定期購方案 查詢明細 API Spec

GET/Api/RegularProduct/GetDetail?planId={planId}　對應下游 GET /api/regular/products/plan/{planId}?shopId={shopId}

1. API 基本資訊

用途依「定期購方案序號」查詢單筆定期購方案明細（含基本設定與贈品活動設定），供編輯畫面回填使用
HTTP MethodGET
OSM 前端路徑/Api/RegularProduct/GetDetail?planId={planId}
對應下游GET /api/regular/products/plan/{planId}?shopId={shopId}（nine1.regularpurchase.v2）
Content-Type無 Request Body
呼叫時機使用者進入「定期購方案編輯」畫面時，依網址列或列表帶入的方案序號查詢明細以回填表單

2. Request

2.1 Query String 參數

欄位型別必填說明
planIdlong是定期購方案序號（對應下游 rpd_pk）；需為大於 0 的正整數
ShopId 不需前端傳入：由 OSM 後端從登入 Session 取得，比照既有 Api/RegularProduct/* 系列 API 的慣例。

2.2 Request Sample

GET /Api/RegularProduct/GetDetail?planId=12345

（無 Request Body）

3. Response Body

重要：本節已依 NineYi.Sms 既有 API 包裝機制修正。 所有 /Api/* 端點的 HTTP Response 都會被 UnifiedResultHandler（WebSite/WebSite/Extensions/DelegatingHandlers/UnifiedResultHandler.cs）統一包裝成 ApiResultEntity 外層結構，Controller Action 本身回傳的內容只會被放進 Data 欄位；不會有 IsSuccess／ErrorCode 這種自訂欄位直接出現在頂層。

3.0 SMS 統一外層包裝結構 ApiResultEntity

欄位型別說明
Statusstring"Success"／"Failure"，由 UnifiedResultHandler 依 HTTP 狀態碼自動判斷（IsSuccessStatusCode 為 true 則 Success）
Dataobject成功時為 Controller Action 實際回傳的物件（見 3.1 節）；失敗時通常為 null
ErrorMessagestring失敗時的錯誤訊息文案；成功時為 null
TimeStampdatetime伺服器回應時間，由 UnifiedResultHandler 自動填入

此結構為 SMS 全站共用（NineYi.Sms.BL.BE.Apis.ApiResultEntity），GetDetail API 本身不需要、也不應該自訂 IsSuccess／ErrorCode 欄位，前端應統一以外層 Status／ErrorMessage 判斷成功或失敗；業務邏輯失敗案例改以 HTTP 4xx（ApplicationException）搭配 ErrorMessage 文案表達，見 4 節錯誤案例。

3.1 成功

Controller Action 實際回傳、會被放進外層 Data 欄位的內容：

命名說明：本節欄位命名與型別刻意比照 Api/RegularProduct/Create 的 Request 欄位（OSM 端慣用詞彙），不會直接透傳下游 v2 API 的原始欄位名稱／型別（例如下游 Title 其實是「商品標題」，與 OSM 慣用的 Title=「方案名稱」語意相反，故本 API 另外拆出 salePage_Title 欄位承接，避免前端誤用）。
欄位型別說明
SalepageIdlong商品頁序號；語意對應 Create Request 的 SalepageId
Titlestring方案名稱，可能為 null；語意對應 Create Request 的 Title
salePage_Titlestring商品標題（即該商品頁本身的標題，非方案名稱）
Pricestring商品售價（含幣值符號的格式化字串，如 $1,000）
PicUrlstring商品圖片 URL
ShipPeriodListint[]配送週期（天），複選；語意與型別對應 Create Request 的 ShipPeriodList
ShippingCountModeenum（string）配送次數設定模式；語意與型別對應 Create Request 的 ShippingCountMode，值域見 3.2 節
ShipLimitCountint配送次數上限；ShippingCountMode=Unlimited 時為 -1；語意對應 Create Request 的 ShipLimitCount
AllowOneTimePurchasebool是否允許消費者選擇「單次購買（不訂閱定期購）」；語意對應 Create Request 的 AllowOneTimePurchase
IsGiftEnabledbool贈品設定開關；由 RegularProductPromotionRules 是否有內容推導而來（有規則=true），語意對應 Create Request 的 IsGiftEnabled，供編輯畫面回填「贈品設定開關」UI 狀態使用
ShippingListstring[]配送方式說明清單
PayListstring[]付款方式說明清單
PlanDateBegindatetime?方案生效開始時間；null=無下限
PlanDateEnddatetime?方案生效結束時間；null=永久有效
RegularProductPromotionRulesList<RegularProductPromotionRule>贈品活動規則清單；查無規則時為空陣列 []，結構見 3.3 節

3.2 ShippingCountMode enum 值定義

值意義搭配 ShipLimitCount
Unlimited無上限，持續配送到消費者自行取消訂閱為止固定為 -1
CustomerChoice有上限，但配送次數由消費者自己選擇配送次數上限
Fixed固定次數，配滿即自動終止，消費者不能自選固定配送次數

3.3 RegularProductPromotionRule（RegularProductPromotionRules 陣列元素）

欄位型別說明
Typeenum（string）活動類型；本次僅會回傳 "Gift"
TriggerModeenum（string）觸發模式；本次僅會回傳 "Interval"
Intervalint每 N 期觸發一次（配送每滿 X 次送贈品的 X）
OutOfStockActionenum（string）贈品缺貨處理："Proceed"（照常建單）／"SkipPeriod"（該期不建立訂單）
RegularProductPromotionGiftItemListList<RegularProductPromotionGiftItem>本次觸發要送出的贈品清單，結構見下方

RegularProductPromotionGiftItem（RegularProductPromotionGiftItemList 陣列元素）

欄位型別說明
GiftTypeIdlong贈品序號，即該贈品自己的 SalePageId
Qtyint本次送出數量
範圍限定：本 API 僅回傳 v2 原始欄位（GiftTypeId／Qty），不會額外查詢 SCM 補上贈品的 SKU 名稱／圖片；若畫面需要顯示贈品名稱或圖片，前端需自行以 GiftTypeId 再呼叫既有商品查詢機制取得。

4. 失敗

失敗時 HTTP 狀態碼會依情境不同而異，並由 GlobalExceptionHandler 統一組出以下結構：

欄位型別說明
Statusstring固定為 "Failure"
Dataobject一般業務錯誤時為 null
ErrorMessagestring錯誤訊息文案，可直接顯示給使用者
TimeStampdatetime伺服器回應時間
{ "status": "Failure", "data": null, "errorMessage": "查無此定期購方案", "timeStamp": "2026-08-03T17:30:00" }

4.1 常見錯誤情境對照（ErrorMessage 內容參考，非結構化代碼）

觸發情境HTTP 狀態碼ErrorMessage（參考文案，實際文案以後端為準）前端建議處理
planId 未帶或 <= 0400 Bad Request「shopId 或 planId 無效」提示參數錯誤，通常代表前端網址組錯，不應開放使用者手動輸入此值
登入 Session 逾時／未登入401 Unauthorized「帳號驗證失敗」（依系統既有文案）導回登入頁
查無此方案序號（下游回傳查無資料）400 Bad Request「查無此定期購方案」提示「查無此定期購方案」，可導回列表頁
下游服務逾時／連線失敗400 Bad Request（由 RegularProductHttpClient 轉譯）依下游實際錯誤訊息或預設文案提示稍後再試

以上文案為依現有實作推導的參考值，實際 ErrorMessage 文案需與 OSM 後端 Service 層核對後定案；前端不應寫死比對整段文案字串。

5. 補充說明

  • 本 API 為 BFF（Backend for Frontend）代理層：RegularProductController.GetDetail → RegularProductService.GetDetail → RegularProductHttpClient.GetDetail → 下游 v2 API GET /api/regular/products/plan/{planId}。
  • 下游 v2 API 已改用標準 HTTP 狀態碼（400／404）表達業務失敗，SMS 端 RegularProductHttpClient 會攔截 Flurl 拋出的 FlurlHttpException，統一轉換為 SMS 慣用的 ApplicationException + ErrorMessage 文案，前端不需要、也不會感知下游細節。
  • RegularProductPromotionRules 為唯讀查詢結果：此 API 僅供編輯畫面回填顯示，若要修改贈品活動規則，仍須透過既有 Api/RegularProduct/Create（或未來的 Update API）送出完整規則。
