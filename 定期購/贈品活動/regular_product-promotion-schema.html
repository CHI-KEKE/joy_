🗃 新增欄位定義

ALTER TABLE regular_product ADD COLUMN rpd_plan_date_begin timestamp NULL, -- 定期購方案生效開始時間 ADD COLUMN rpd_plan_date_end timestamp NULL, -- 定期購方案生效結束時間（NULL = 永久有效） ADD COLUMN rpd_promotion_json jsonb NOT NULL DEFAULT '[]'; -- 定期購活動內容（JSON 陣列） CREATE INDEX idx_regular_product_rpd_date_range ON regular_product (rpd_plan_date_begin, rpd_plan_date_end); CREATE INDEX idx_regular_product_rpd_promotion_json ON regular_product USING gin (rpd_promotion_json);
欄位型別Null說明
rpd_plan_date_begin timestamp 可為 NULL 控制「定期購訂閱」本身是否開放讓會員訂閱的起始時間，屬於方案層級，比商品層級的 rpd_sale_date_begin／rpd_sale_date_end 更上層。即使商品仍在一般販售期間內，定期購訂閱視窗仍可獨立提前關閉或延後開放；rpd_sale_date_* 維持原本「商品本身是否可見／可購買」的用途不變
rpd_plan_date_end timestamp 可為 NULL 定期購訂閱視窗結束時間；NULL 表示永久開放訂閱，無到期日
rpd_promotion_json jsonb NOT NULL DEFAULT '[]' 該定期購商品設定的活動規則陣列，可同時包含贈品／折扣／點數多筆規則，見下一節
rpd_promotion_json 使用 jsonb + GIN index，便於未來以 rpd_promotion_json @> '[{"type":"GIFT"}]' 查詢「哪些設定含贈品規則」等後台統計需求。編輯時採整段陣列覆寫（非局部 patch），驗證與 id 唯一性交由 Application Layer 處理，DB 端不做 CHECK constraint（jsonb 欄位無法有效表達分支驗證規則）。

🎁 rpd_promotion_json — 活動內容 JSON Schema

以陣列保存該定期購設定的所有活動規則。單一 JSON 物件即可描述「多期數觸發」與「多贈品品項」，不需要為每個期數或每個贈品品項各存一列。

[ { "id": "promo-1", // 本設定列內唯一 id，訂單觸發時快照用來回溯來源規則 "type": "GIFT", // GIFT | DISCOUNT | POINT（未來可擴充 COUPON / FREE_SHIP） "triggerMode": "INTERVAL", // INTERVAL | SEQUENCE | THRESHOLD "interval": 3, // INTERVAL 模式：每 N 期觸發一次（第 3, 6, 9... 期） "outOfStockAction": "PROCEED", // GIFT 專用：贈品缺貨處理，PROCEED=照常建單／SKIP_PERIOD=不建立訂單 "items": [ // GIFT 專用：同一次觸發可送多個不同贈品，各自數量獨立 { "pageId": 50001, "sku": "SKU-GIFT-123", "name": "保溫杯", "picUrl": "https://cdn.../a.jpg", "qty": 2 }, { "pageId": 50002, "sku": "SKU-GIFT-456", "name": "環保袋", "picUrl": "https://cdn.../b.jpg", "qty": 1 } ] }, { "id": "promo-2", "type": "DISCOUNT", "triggerMode": "SEQUENCE", "shipSequences": [4, 7, 9], // SEQUENCE 模式：指定多個期數，同一物件即可描述「第4、7、9期」，不需拆多列 "discountType": "AMOUNT", // AMOUNT（固定折抵）/ PERCENT（折數） "discountValue": 10.000 }, { "id": "promo-3", "type": "POINT", "triggerMode": "THRESHOLD", "fromSequence": 3, // THRESHOLD 模式：從第 N 期起，之後「每一期」都觸發（無需窮舉期數，亦適用無限期方案） "pointValue": 20 // 第 3 期起，每期加贈 20 點 } ]

outOfStockAction 可選值

值說明
PROCEED照常建單：訂單照常成立，會員收到商品及有庫存的贈品（缺貨贈品不出貨，不影響商品訂單成立）
SKIP_PERIOD不建立訂單：本期視為異常不建立，會員收不到該期商品，下期恢復正常建單

📐 對照使用者需求範例

商業需求JSON 表達
每 3 期送贈品（可多品項不同數量）type=GIFT, triggerMode=INTERVAL, interval=3, items=[{sku:123,qty:2},{sku:456,qty:1}]
指定第 4、7、9 期折 10 元type=DISCOUNT, triggerMode=SEQUENCE, shipSequences=[4,7,9], discountValue=10
每滿 3 期送 20 點type=POINT, triggerMode=INTERVAL, interval=3, pointValue=20
第 3 期以後，之後每一期都送 20 點（非每 3 期一次，是從第 3 期起連續每期）type=POINT, triggerMode=THRESHOLD, fromSequence=3, pointValue=20

✅ 型別欄位規則（Application Layer 驗證，非 DB Constraint）

條件規則
triggerMode = INTERVALinterval 必填（>0），shipSequences、fromSequence 不可出現
triggerMode = SEQUENCEshipSequences 必填且非空陣列，interval、fromSequence 不可出現
triggerMode = THRESHOLDfromSequence 必填（>0），interval、shipSequences 不可出現；觸發條件為 期數 >= fromSequence，無終止期數（除非本設定列本身有 rpd_ship_limit_count 限制）
type = GIFTitems 必填且非空陣列，每筆需有 sku／qty（qty > 0）；outOfStockAction 必填，僅允許 PROCEED／SKIP_PERIOD
type = DISCOUNTdiscountType、discountValue 必填
type = POINTpointValue 必填（>0）
上限驗證（GIFT 專用，對應畫面規則）items.length <= 10；每筆 1 <= qty <= 10；sum(items[].qty) <= 50
期數上限驗證若 rpd_ship_limit_status = 2（有限制）：interval <= rpd_ship_limit_count；shipSequences 內所有值 <= rpd_ship_limit_count；fromSequence <= rpd_ship_limit_count

🔭 未來設計討論（非本次實作範圍，先記錄設計方向）

每期實際觸發的贈品/折扣/點數快照紀錄

rpd_promotion_json 只是「規則定義」；當某一期實際觸發規則（例如送出贈品）時，需要有地方記錄「這期實際觸發了什麼、狀態如何」，供後台/客服查詢。

方向：延伸既有 regular_order_detail（rod_*），不新建表，與 regular_product 這次的做法一致：

ALTER TABLE regular_order_detail ADD COLUMN rod_promotion_snapshot_json jsonb NULL; -- 該期實際觸發的活動快照（贈品/折扣/點數），建單當下寫入；未觸發任何規則時為 NULL

顆粒度延續既有 rod_gift_ts_code（該期贈品獨立建單後的訂單編號）的精神，rod_promotion_snapshot_json 記錄「這期觸發了哪些規則、內容是什麼、各品項狀態如何」：

[ { "promoId": "promo-1", // 回溯 rpd_promotion_json 裡的 id "type": "GIFT", "items": [ { "sku": "SKU-GIFT-123", "name": "保溫杯", "qty": 2, "status": "SUCCESS" }, { "sku": "SKU-GIFT-456", "name": "環保袋", "qty": 1, "status": "OUT_OF_STOCK" } ] } ]
  • 贈品實際訂單號仍用既有 rod_gift_ts_code 追蹤：此假設已推翻（見 5.2），贈品未來會合併進商品本身那張訂單一起下單，rod_gift_ts_code（獨立贈品訂單編號）用途需重新檢視，可能需廢止或改設計，待建單流程定案後處理。
  • rod_promotion_snapshot_json 只負責記錄「規則內容與各品項狀態」，供客服/後台查詢用，不再依賴獨立訂單號欄位。
  • 折扣／點數觸發時，同一 JSON 陣列可放 type=DISCOUNT／POINT 的快照物件，欄位比照 rpd_promotion_json 的規則物件精簡對應。

✅ 優點

  1. 與 regular_product 加 rpd_promotion_json 的做法一致，架構風格統一、學習成本低
  2. 查詢單一期別的完整資訊（含贈品內容）不需 JOIN，一次 SELECT 拿到
  3. 不新增表，維運（DDL、遷移、權限）成本最低

⚠️ 缺點

  1. rod_gift_ts_code（訂單號）與 rod_promotion_snapshot_json（內容快照）兩個欄位分別描述同一件事，未來若沒同步更新容易兜不起來
  2. 若要做「這個 SKU 這個月總共送出幾件」這類跨期統計，得對 regular_order_detail（本身是高頻成長表）整表掃 JSON，效能較差、無法建 index 到單一品項層級
  3. 更新單一品項狀態（例如缺貨→事後補貨成功）要整段 JSON 讀出再寫回，不能像關聯表一樣單列 UPDATE
結論與保留退路：現階段沒有明確的「跨 SKU / 跨期贈品統計報表」需求，先採用上述擴充欄位方案即可（避免過度設計）。rod_promotion_snapshot_json 的 JSON 內容刻意讓每個 items[] 都帶獨立 status，未來若真的出現統計需求，可以直接寫 migration script 把既有 JSON 資料展開匯入成獨立明細表，不會是死路。

5.2 建單流程如何判斷 outOfStockAction（Worker 設計方向）

現況確認：nine1.regularpurchase.v2.worker 的 RegularCreateOrderJob.cs 目前完全沒有贈品相關程式碼，只有「呼叫一次下游 mweb 建單 API、整單 Success/Fail」的商品訂單流程，贈品判斷需全新設計。

討論結論：

  1. 贈品合併進同一張訂單
    同一次 API 呼叫、同一張訂單，不另外建立獨立的贈品訂單。
  2. 判斷時機在呼叫建單 API 之前
    Worker 先讀取本方案 rpd_promotion_json 中 GIFT 規則的 outOfStockAction：
    PROCEED 不做贈品庫存 pre-check，直接建單（各贈品品項是否出貨，交由下游 mweb 訂單建立結果決定；細節待與 mweb API 對接規格確認）。
    SKIP_PERIOD 建單前先做贈品庫存 pre-check，只要任一贈品品項庫存不足，本期就不建立訂單（視為異常），下一期恢復正常排程。
  3. 待確認：排程影響
    SKIP_PERIOD 情境下，本期「不建立訂單」是否計入 rgo_ship_count（影響下一期配送日期的排程計算），此細節待建單流程子項目實作時再與現有排程邏輯對齊。

🔗 商品頁（pageId）與定期購方案的關聯設計

現況：全有全無擋法，非時間區間判斷

既有 RegularProductRepository.ExistsByProductAsync(shopId, pageId) 的檢查邏輯：

SELECT COUNT(1) FROM regular_product WHERE rpd_shop_id = @ShopId AND rpd_page_id = @PageId AND rpd_status = 1 LIMIT 1

只要該 pageId 底下存在任一筆 rpd_status = 1（啟用中）的設定，就視為「已被設定」而擋下新增。此方法被兩處呼叫：

呼叫者對應端點時機
ValidateProductAsyncPOST /api/regular/products/validate新增畫面輸入商品序號當下的即時驗證
AddProductAsyncPOST /api/regular/products表單送出、正式 INSERT 前的伺服器端最終防呆

且新增當下 RpdStatus 是寫死 = 1（AddProductAsync 內），EditProductAsync 不會改動此欄位，目前程式碼中沒有任何路徑會把 rpd_status 改回非啟用。現況設計是「一個 pageId 一旦被設定過，就永久佔用、沒有結束機制」，與時間區間完全無關。

未來目標：改為時間區間 overlap 判斷

隨著本次新增 rpd_plan_date_begin／rpd_plan_date_end，方案與商品的關聯改為：一個 pageId 可以被多個 regular_product 設定列關聯，但同一 pageId 底下，不同設定列的生效區間不可重疊（overlap）。

SELECT COUNT(1) FROM regular_product WHERE rpd_shop_id = @ShopId AND rpd_page_id = @PageId AND rpd_status = 1 AND rpd_plan_date_begin < COALESCE(@NewEnd, TIMESTAMP '9999-12-31') AND COALESCE(rpd_plan_date_end, TIMESTAMP '9999-12-31') > @NewBegin

NULL 視為「無限遠的未來」參與比較，讓永久有效方案（rpd_plan_date_end = NULL）也能正確納入 overlap 判斷。

✅ 本次範圍定案：生效時間為必填，不支援「永久有效」

依 VSTS #643392（EPIC：定期購支援贈品_202607）需求文字明確載明「生效時間：必填，無預設值」「生效結束時間須晚於生效開始時間」，未提及可留空／永久有效。因此本次範圍定案如下：

  1. API／畫面層強制 PlanDateBegin／PlanDateEnd 皆為必填，不接受 null；新增/編輯方案時，若任一欄位為空，前端與後端皆須擋下並提示「此為必填欄位」。
  2. regular_product.rpd_plan_date_end 於 DB 層仍保留可為 NULL 的彈性（欄位定義不變），僅是本次透過 API／UI 驗證層強制不得傳入 null，避免因應未來其他建立管道需要用到「永久有效」語意時，還要再異動 DB schema。
  3. 前一版「永久有效方案會卡死該 pageId」的 side effect 討論，本次不會發生（因為不允許建立 rpd_plan_date_end = NULL 的方案），改列為下方備註，供日後若真的要開放永久方案時參考。
  4. 上方 overlap 判斷式維持不變（仍相容 NULL 比較邏輯），作為未來若開放永久方案時可直接沿用的判斷基礎，不需重新設計。
備註（非本次實作範圍，僅記錄以利未來查閱）：若未來確實開放「效期永久」的方案（rpd_plan_date_end = NULL），則會出現「一個 pageId 一旦被設定為永久有效方案，且沒有下架/結束方案的操作入口，該 pageId 就無法再被任何其他方案關聯」的 side effect，屬於業務上可接受、且與現況（6.1）行為一致的設計，但仍需額外設計「方案下架」功能才能解除卡死狀態。

🏷️ 6.4 商品頁如何辨別「是否為定期購商品」——不需新增標記欄位

延伸第 10.5 節「贈品項目需標記為定期購使用」的討論，特別釐清商品頁本身是否也需要類似的標記機制。查證 NineYi.Sms 既有程式碼後，結論是：不需要，既有欄位＋即時查詢即可滿足，這與贈品品項的標記需求（10.5）是兩件不同的事。

商品「是否為定期購使用」實際上分兩層意思：

層級意思判斷依據資料位置
靜態屬性（商品資格）這個商品的交期類型是否為「定期購」，決定它能不能被設定進定期購方案商品頁本身的交期欄位，既有 SaleProductShippingTypeDefEnum.RegularOrder = 7（BusinessLogic/BE/SaleProducts/SaleProductShippingTypeDefEnum.cs）NineYi.Sms 商品資料（既有欄位，非本次新增）
動態狀態（目前是否被關聯）這個商品目前實際有幾組生效中的定期購方案需即時查詢 nine1.regularpurchase.v2 的 regular_product 表（rpd_page_id）nine1.regularpurchase.v2 端資料庫，不在 NineYi.Sms 本地
  • 「商品交期＝定期購」既有欄位已可作為新增方案時「商品資格檢核」的依據（對照 VSTS #643392 需求「檢核商品條件：商品交期為『定期購』」），本次規劃無需新增任何商品層級的標記欄位。
  • 「商品目前是否有生效中的方案」屬於動態關聯資訊，不應在 NineYi.Sms 本地另存一個標記欄位去追蹤，正確作法是透過 9.4／9.5 規劃的查詢 API 即時向 nine1.regularpurchase.v2 查詢，避免雙邊資料不同步（例如方案於 v2 端被刪除，但 SMS 端標記忘了同步清除）的風險。
  • 此結論與 10.5 節「贈品項目需可辨別為定期購商品使用」不是同一件事：10.5 討論的是贈品品項（活動小舖庫存商品）需要被標記為「被定期購佔用」，用途是給庫存/活動小舖系統識別，目前確實沒有現成機制，10.5 的缺口分析維持不變，仍需另外向需求方確認範圍；本節（6.4）僅釐清「商品頁本身」不需要比照辦理。

6.5 釐清順序：新增定期購方案「不會」新增商品頁，是反過來引用既有商品頁

延伸 6.4 節，特別澄清一個常見的順序誤解：「新增定期購方案」這個動作，完全不涉及新增/建立商品頁，商品頁必須是早就已經存在、且交期類型已設定為「定期購」的既有資料，定期購方案只是去引用它。

【第一步：商品在 SMS 早就已經存在（既有商品管理流程，非本次新增）】 營運人員在「商品管理」建立一般商品頁時 → 選擇「交期」欄位 = 「定期購」（ShippingTypeDef = 7，既有選項，非本次新增） → 這個商品頁就此被標記為「可設定定期購方案的商品」 ↓ 【第二步：之後，才去「新增定期購方案」畫面，設定既有商品要怎麼跑定期購】 操作人員輸入「商品序號」（ProductNo，就是這個既有商品的 SalePageId） → 呼叫 9.2 驗證 API → 查詢這個 pageId 的 ShippingTypeDef 是否 = 7 → 是 → 才允許繼續設定配送週期/次數/贈品等 → 不是 → 擋下並提示「此商品交期非定期購，無法設定」
  • 確認「是否為定期購商品」的時機，不是商品頁建立當下，而是「新增定期購方案、輸入商品序號當下」——商品頁本身的「交期＝定期購」屬性，是在商品建立/編輯階段（既有商品管理功能）就已經設定好的既有欄位，定期購方案這邊只負責讀取、驗證，不負責設定。
  • 這個「先建立好既有資源、再由定期購方案引用、不會順便新建」的模式，與第 11 章「贈品」的處理方式完全一致（贈品也必須先在既有贈品管理頁面建立好，定期購方案只負責引用，不會呼叫 CreateSaleProductGift 去新建贈品），兩者可互相對照理解。
  • 對應既有 API：Api/SalePage/Get/{id}（SalePageController.Get → SalePageService.Get）已可一次查到 ShippingTypeDef（交期）、SellingStartDateTime／SellingEndDateTime（商品銷售起訖時間，用於比對 PlanDateBegin／PlanDateEnd）、ValidFlag（商品頁是否有效）等驗證所需欄位，9.2 節規劃的驗證 API 可直接複用此既有查詢，不需另外設計商品頁資料結構。

需求「2. 贈品設定」與「3. 新增贈品選項流程」皆提到「需可辨別此贈品為定期購商品所使用」。此暗示贈品品項需要某種標記／分類機制，讓其他系統（如活動小舖／庫存管理）能識別「此贈品被定期購佔用」。目前文件僅將贈品資料視為 rpd_promotion_json 的內容快照，未討論此標記要寫在哪裡、由哪個系統負責維護，可能牽涉跨系統的庫存鎖定邏輯，需另外向需求方確認範圍（純顯示用 tag，或涉及庫存預留機制）。

10.6 關聯需求：商品頁狀態依定期購方案數量鎖定（依賴 #649890，本文件未涵蓋）

🎁 贈品定義、新增機制與定期購方案的關聯

延伸第 10.1、10.5 節的缺口，本章查證 NineYi.Sms 既有「贈品」相關程式碼，釐清三件事：贈品目前怎麼被定義／怎麼被新增／怎麼分類活動贈品，以及定期購方案要如何跟既有贈品機制關聯。

11.0 先搞懂資料階層：SalePage 是商品頁，SaleProduct 是頁面底下的銷售項目

在談贈品之前，必須先釐清 NineYi.Sms 商品資料的階層關係，否則容易誤解「贈品」跟「一般商品」的資料是怎麼疊在一起的。

SalePage（商品頁，SalePage_Id） —— 一個「頁面」：決定消費者看到的標題、圖片、售價、上下架時間 │ └─ SaleProduct（頁面底下掛的銷售項目，SaleProduct_SalePageId → 指回 SalePage_Id） —— 關鍵：一個 SalePage 底下可以掛「多筆」SaleProduct！ —— 用旗標欄位區分這筆 SaleProduct 在頁面中扮演的角色： SaleProduct_IsMajor = true → 本頁的「主商品」 SaleProduct_IsGift = true → 本頁綁定的「滿額贈贈品」項目 SaleProduct_IsExtra = true → 本頁的「加價購」項目 SaleProduct_IsOptionalGift = true → 本頁的「任選贈品」項目

依 SaleProductConfiguration.cs 的 FK 設定 HasRequired(a => a.SalePage).WithMany(b => b.SaleProduct)，證實這是「一對多」：一個 SalePage 可以對應多筆 SaleProduct。

延伸出兩種完全不同的「送贈品」情境，容易搞混，先在這裡分清楚：

情境白話說法資料上怎麼實現是否需要「另外建立」一個贈品商品頁
A. 買這個商品就附贈（商品贈品／買就送）買 A 商品，加送隨附的小贈品，贈品本身不是拿來單獨賣的同一個 SalePage（就是 A 商品自己的頁面）底下，多掛一筆 SaleProduct（IsMajor=false, IsGift=true 或 IsOptionalGift=true）不需要贈品資訊直接掛在原商品頁下面，沒有獨立序號
B. 活動贈品（滿額贈／滿件贈／贈品券兌換／本次定期購要用的）贈品是「共用池」概念，可以被很多個不同活動／方案引用，本身要有獨立庫存、獨立管理贈品是它自己獨立的一個 SalePage（有自己的 SalePage_Id），其下掛一筆 SaleProduct（IsMajor=true，因為對「贈品」這個頁面而言它自己就是主件），並透過 SaleProductGiftType = PromotionFreeGift 標記這個頁面是拿來當「活動贈品」用需要必須先在「贈品管理」頁面建立好，取得屬於它自己的 SalePageId
定期購贈品屬於情境 B：因為同一個贈品要能被 X 期觸發、被多組定期購方案引用，甚至未來可能同時被滿額贈活動共用，所以走的是「獨立商品頁」的活動贈品機制，不是掛在原商品底下的買就送。

SaleProductGiftUpdateEntity.SaleProductGiftType（string 列舉值）是判斷贈品類型的欄位，前端下拉選單（saleProductGiftEdit.controller.ts）目前提供兩種類型：

SaleProductGiftType 值中文名稱說明

11.3 既有「批次驗證贈品序號」機制可直接參考（呼應 10.1 缺口）

SaleProductService 已有現成的批次驗證商品頁序號是否合法的 pattern：

// 驗證是否為合法的活動贈品
public SalePageIdCheckValidResultEntity CheckIsPromotionFreeGiftValid(long shopId, List<long> salePageIds)
{
    var data = this._saleProductRepository.GetPromotionFreeGiftSalePageId(salePageIds, shopId);
    var exceptIds = salePageIds.Where(a => data.Contains(a) == false);

    return new SalePageIdCheckValidResultEntity
    {
        FailCount = exceptIds.Count(),
        FailIds = exceptIds.ToList(),
        SuccessCount = salePageIds.Count - exceptIds.Count()
    };
}
  • SalePageIdCheckValidResultEntity（FailCount／FailIds／SuccessCount）這個既有回傳結構，與 10.1 節規劃的「贈品序號驗證／查詢」API 需求高度吻合，10.1 建議新增的 Api/RegularProduct/GiftItems/Validate 可直接比照此架構實作。
  • 驗證邏輯：判斷傳入序號是否存在、且 SaleProductGiftType = PromotionFreeGift（活動贈品），不合格者列入 FailIds。
  • 重複序號的靜默略過規則（VSTS 需求特別要求）需要額外補在 RegularProductService 這層，因為既有 CheckIsPromotionFreeGiftValid 本身不處理輸入去重，此為本次新增邏輯需自行實作的部分。
  • 驗證成功後，畫面需顯示的圖片/名稱/庫存數量，可透過既有 GetSaleProductGift 或 GetSaleProductGiftList 取得，不需重新設計欄位。

11.4 贈品與定期購方案的關聯方式（資料流向釐清）

依前述機制，定期購方案與贈品的關聯關係如下：

  1. 贈品本身的建立與維護，完全沿用既有 SaleProduct 贈品機制（SaleProductGiftType = PromotionFreeGift），本次規劃不需要在 NineYi.Sms 新增另一套贈品建立流程。
  2. 定期購方案（regular_product）只儲存贈品的「引用關係」：rpd_promotion_json 內 items[] 陣列僅記錄贈品的 pageId／sku／name／picUrl／qty（見本文件第 3 節），這些內容是新增方案當下向既有贈品資料查詢後寫入的快照，並非另建一份贈品主檔。
  3. 「新增贈品選項流程」（10.1）的批次驗證，驗證的對象就是既有的活動贈品商品頁，通過驗證後，只是把該贈品的 pageId／基本資訊組進 Promotions JSON，不會呼叫 CreateSaleProductGift 去新建贈品——若營運人員要用的贈品序號不存在，必須先到既有「贈品管理」頁面建立好該贈品，定期購新增畫面只負責「引用」而非「建立」。
  4. 呼應 10.5 節缺口：既有 SaleProductGiftType 分類欄位只能區分「商品贈品」vs「活動贈品」兩種既有用途，無法標記「此贈品目前被定期購方案佔用」，這是本次真正的缺口所在——若庫存/活動小舖系統需要辨識「此贈品被定期購鎖定」，需另外設計標記機制（例如新增 SaleProductGiftType = RegularOrderGift 分類，或另建一張引用關聯表記錄「哪些贈品被哪些 regular_product 引用」），10.5 節的待確認事項維持不變，本節補充的是「可行方案方向」而非最終定案。

11.5 完整情境還原：操作人員從 0 到 1 設定「定期購送贈品」的實際步驟

把 11.0-11.4 串成一個完整、好懂的操作情境：

【第一步：先在「贈品管理」頁面建立好活動贈品（既有功能，非本次新增）】 操作人員開啟 EditGift.cshtml（新增贈品視窗） → 贈品類型選「活動贈品(滿額贈/滿件贈/贈品券兌換)」= PromotionFreeGift → 填寫 Title／OuterId／庫存／圖片／物流付款方式等 → 送出 → 呼叫 CreateSaleProductGift → 後端建立一個全新、獨立的 SalePage（連帶掛一筆 IsMajor=true 的 SaleProduct） → 取得這個贈品自己的 SalePageId（例如 50001） ↓ 【第二步：到「新增定期購方案」畫面，引用剛剛建立好的贈品】 操作人員開啟贈品設定： IsGiftEnabled = 開啟 ↓ 在「新增贈品選項」流程貼上贈品序號 50001（可一次貼多筆，最多 10 筆／次） ↓ 前端送出查詢 → 呼叫 10.1 節規劃的驗證 API（比照既有 CheckIsPromotionFreeGiftValid 架構） → 後端逐筆檢查： a. 序號是否存在 b. 該序號的 SaleProductGiftType 是否為 PromotionFreeGift（活動贈品） c. 是否與本批次或既有清單重複（重複則靜默略過，不提示） → 序號有誤（不存在 / 類型不對）→ 彈窗列出，供「繼續新增」或「重新確認」 ↓ 驗證通過的序號，連同查到的名稱／圖片／庫存，寫入畫面上的「贈品內容」清單 → 操作人員設定每個贈品的「數量」（qty） ↓ 【第三步：設定觸發條件並儲存方案】 設定「配送每滿 X 次，送贈品」→ 對應 rpd_promotion_json 的 interval 設定「缺貨處理」→ 對應 outOfStockAction ↓ 儲存方案 → 通過 6.2 overlap 檢查等驗證後 → 將上述贈品清單（pageId/sku/name/picUrl/qty）連同 X／缺貨處理， 整包寫入 regular_product.rpd_promotion_json（快照，不建立新贈品主檔）

這個流程明確回答三個常見疑問：

  • Q：定期購的贈品是不是要先額外建立活動贈品？
    A：是的，必須先建立。 定期購方案的新增畫面只負責「輸入序號→驗證→引用」，完全不會幫你新建贈品；如果序號對應的贈品還沒建立，或建立時類型選錯（選了「商品贈品」而非「活動贈品」），驗證都會失敗。
  • Q：既有的一般商品頁能不能直接變成贈品？
    A：不能直接變身。 贈品是它自己獨立的一個 SalePage（獨立序號、獨立庫存），跟一般販售商品是兩筆分開的商品頁資料；「一般商品」與「贈品」唯一的橋樑是操作人員手動重新建立一筆贈品，資料上沒有「一鍵轉換」的機制。
  • Q：贈品序號、SalePageId、SaleProductId 是什麼關係？
    A：贈品序號＝該贈品自己的 SalePageId。這個 SalePage 底下掛一筆 SaleProduct（因為對贈品頁面而言，它自己就是主件，IsMajor=true），SaleProductId 只是這筆內部銷售項目的識別碼，操作人員平常看到、填寫、引用的都是 SalePageId。
