# 思考紀錄：定期購暫停後是否還會建單？

> 日期：2026-06-25  
> 背景：.NET Core 新架構 RegularCreateOrderJob

---

## 問題

當消費者將定期購設定為「暫停」（設定 `rgo_pause_date`），後續的排程是否還會自動幫他建單？

---

## 結論

**取決於暫停設定的時間點，分兩種情況：**

| 時機 | 結果 |
|------|------|
| 暫停時間在 **Step③ 執行之前**（配送日 D-2 的 10:15 前） | ✅ 不會建單 |
| 暫停時間在 **Step③ 執行之後**（detail 佔位已建立） | ⚠️ 還是會建單 |

---

## 原因分析

### Step③（建立 detail 佔位）— 有檢查 pause_date ✅

```csharp
// GetOrdersForDetailGenerationAsync
&& (rgo.RgoPauseDate == null || rgo.RgoNextShipDate < rgo.RgoPauseDate)
```

- 若 `rgo_next_ship_date >= rgo_pause_date` → **不建立 detail**
- 沒有 detail → Step④ 找不到資料 → 不打 API → 不建單

### Step④（打 API 建真實訂單）— **沒有**檢查 pause_date ⚠️

```sql
WHERE rod.rod_status = 1
  AND rod.rod_create_order_status IN (0, 2)
  AND rod.rod_ship_date > today
  AND rod.rod_ship_date <= today + 2
  -- ← 沒有 JOIN rgo 再檢查 rgo_pause_date
```

- detail 一旦存在，Step④ 就會照樣撈到並呼叫 `SubscriptionOrderAutoGen` API
- 暫停設定無法攔截已存在的 detail

---

## 時間軸示意

```
配送日 = D

D-2  10:15    Step③ 建立 detail
              ↑
              這個時間點之前暫停 → 不建 detail → 安全 ✅

D-2  10:15之後 → 使用者設定暫停（但 detail 已存在）

D-1  10:15    Step④ 撈到 detail → 呼叫 API → 建單 ⚠️

D    10:15    Step④ 最後重試機會
```

---

## 與舊架構的差異

此行為**與 PHP 舊架構完全相同**。

PHP 的 `take_order_api()` 也沒有對 `regular_order_detail` 補查 `pause_date`，只有 `generate_regular_order_detail()` 有檢查。翻寫 .NET 時沿用了相同設計。

---

## 潛在問題

若消費者在 D-2 當天設定暫停，可能不知道這期的訂單仍然會被建立、並且被扣款。這在使用者體驗上是一個需要注意的邊界情境。

---

## 若要修正

在 Step④ 的 SQL 查詢加上 pause_date 的 JOIN 條件：

```sql
JOIN regular_order rgo ON rod.rod_rgo_pk = rgo.rgo_pk
WHERE ...
  AND (rgo.rgo_pause_date IS NULL OR rgo.rgo_next_ship_date < rgo.rgo_pause_date)
```
