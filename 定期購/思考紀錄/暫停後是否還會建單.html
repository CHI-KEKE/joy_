🔍 思考紀錄：定期購暫停後是否還會建單？

日期：2026-06-25 ・ 架構：.NET Core NMQv3 Worker ・ RegularCreateOrderJob

問題

當消費者將定期購設定為「暫停」（寫入 rgo_pause_date）， 後續的排程是否還會自動幫他建立新的購買訂單？

結論

✅
暫停時機在 Step③ 之前
（配送日 D-2，10:15 前設定）
不會建單
⚠️
暫停時機在 Step③ 之後
（detail 佔位已建立後才暫停）
還是會建單

原因分析

Step③ 建立 detail 佔位 — 有檢查 pause_date ✅

// GetOrdersForDetailGenerationAsync（LINQ）
&& (rgo.RgoPauseDate == null || rgo.RgoNextShipDate < rgo.RgoPauseDate)

若 rgo_next_ship_date >= rgo_pause_date，此訂單不會被撈出 → 不建立 detail → Step④ 找不到資料 → 不打 API → 完全不建單。

Step④ 打 API 建真實訂單 — 沒有檢查 pause_date ⚠️

-- GetDetailsForApiCallAsync（Raw SQL）
WHERE spi.spi_enable_regular = 1
  AND spi.spi_regular_provider = 'Nine1V2'
  AND rgo.rgo_status <> 3
  AND rod.rod_status = 1
  AND (rod.rod_create_order_status = 0 OR rod.rod_create_order_status = 2)
  AND rod.rod_ship_date > today
  AND rod.rod_ship_date <= today + 2
  -- ← 沒有再 JOIN rgo 檢查 rgo_pause_date

detail 只要存在，Step④ 就會照樣撈到並呼叫 SubscriptionOrderAutoGen API。 暫停設定在這個階段無法攔截已建立的 detail。

執行時間軸

D-2 10:15 之前
使用者設定暫停（rgo_pause_date = D 或更早） 安全
Step③ 執行時撈不到此訂單 → 不建 detail → 不建單
D-2 10:15
Step③ 執行：建立 detail 佔位（rgo_pause_date 檢查在此）
D-2 10:15 之後
使用者設定暫停（但 detail 已建立） 危險
D-1 10:15
Step④ 執行：找到已存在的 detail → 呼叫 API → 訂單建立、扣款
D 10:15
Step④ 最後重試機會（若 D-1 失敗）

與舊架構（PHP）的差異

此行為與 PHP 舊架構完全相同。
PHP 的 take_order_api() 同樣沒有對 regular_order_detail 補查 pause_date，只有 generate_regular_order_detail() 有檢查。 翻寫 .NET 時沿用了相同設計，並非新引入的問題。

潛在使用者體驗問題

若消費者在 D-2 當天（排程執行後）才設定暫停， 可能誤以為這期不會被扣款——但實際上訂單仍然會被建立並扣款。 這是一個需要在產品設計上說明清楚的邊界情境。

若要修正

在 Step④ 的 SQL 查詢加上 pause_date 的條件：

-- 在 GetDetailsForApiCallAsync 加上：
JOIN regular_order rgo ON rod.rod_rgo_pk = rgo.rgo_pk
WHERE ...
  AND (rgo.rgo_pause_date IS NULL
       OR rgo.rgo_next_ship_date < rgo.rgo_pause_date)
