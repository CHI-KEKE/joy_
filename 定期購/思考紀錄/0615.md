## Q2：GetDetailsForApiCallAsync 的篩選條件意義是什麼？

```csharp
&& spi.SpiRegularProvider == Nine1V2Provider
&& rgo.RgoStatus != 3
&& rod.RodStatus == 1
&& (rod.RodCreateOrderStatus == 0 || rod.RodCreateOrderStatus == 2)
&& rod.RodShipDate > today
&& rod.RodShipDate <= upperDate
```

| 條件 | 語意 | 說明 |
|------|------|------|
| `SpiRegularProvider == Nine1V2Provider` | 只處理 Nine1 V2 供應商 | 排除其他金流商的定期購 |
| `RgoStatus != 3` | 主計畫狀態不是「終止」 | 當時誤判，見 Q3 |
| `RodStatus == 1` | detail 正常（未廢棄） | `2=廢棄, 3=Pending, 9=刪除` |
| `RodCreateOrderStatus == 0 or 2` | 尚未建單 or 曾失敗 | `1=成功`，所以排除已成功的 detail |
| `RodShipDate > today` | 未到期 | 避免處理過去的 detail |
| `RodShipDate <= upperDate` | 未來 N 天內 | 只抓即將出貨的區間 |

## Q3：`GetDetailsForApiCallAsync`（Step④）的 RgoStatus 條件應用 `!= 3` 還是 `== 1`？

**A：Step④ 應維持 `!= 3`，與 PHP 一致。**

PHP `get_new_order_to_establish`（Step④）使用：
```sql
AND rgo_status <> 3
```

兩個 Step 的條件不同是**故意的設計**：

| Step | 條件 | 原因 |
|------|------|------|
| Step③ 建 detail | `rgo_status = 1` | 只對進行中的計畫建新 detail，暫停中不建 |
| Step④ 打 API | `rgo_status <> 3` | detail 已存在就繼續打 API，即使主計畫此時變暫停也應完成 |

邏輯：**暫停只阻止建立新 detail，不阻止已建立的 detail 完成建單。**

曾誤改為 `== 1`，已還原。

## Q4：GetOrdersForDetailGenerationAsync 的 RgoPauseDate 條件是否正確？

**A：原始 null check 是必要的，不應移除。**

Entity 是 `DateOnly?`（nullable），代表 DB 欄位允許 NULL。若某筆資料的 `rgo_pause_date` 為 NULL，直接比較：

```csharp
// ❌ 錯誤（NULL 比較在 SQL 永遠是 false，NULL 的訂單永遠撈不到）
&& rgo.RgoNextShipDate < rgo.RgoPauseDate
```

正確寫法：
```csharp
// ✅ 正確
&& (rgo.RgoPauseDate == null || rgo.RgoNextShipDate < rgo.RgoPauseDate)
```

雖然 PHP DB 設計初始值為 `2099-12-31`（非 NULL），但 EF scaffold 偵測為 nullable，為安全起見保留 null check，已還原。

## Q8：如果是最後一期失敗，仍會遞延 RgoNextShipDate 嗎？

**A：會。**

`UpdateExpiredFailAsync` 沒有檢查 `ship_count vs ship_limit_count`，無條件推進：

```csharp
rgo.RgoNextShipDate = rgo.RgoNextShipDate!.Value.AddDays(rgo.RgoShipPeriod);
rgo.RgoInSchedule   = false;
// ← 沒有終止判斷
```

但不會造成問題，因為 Step③ `ship_count(2) < limit(3)` 仍成立 → 建立重試 detail → 成功後 `ship_count = 3 >= limit` → 自動終止。

副作用：最後一期失敗後，重試日期延後一個週期，屬於既有設計。

## Q9：如果 API 一直失敗，是否會無限循環廢棄 detail 並遞延？

**A：理論上是的。**

```
detail 建立（rod_status=1）
    ↓
API 失敗 → rod_status=2（廢棄），rgo_create_order_status=2
    ↓
Step②：next_ship_date < today → 廢棄舊 detail，next_ship_date += period
    ↓
Step③：ship_count(2) < limit(3) → true → 建立新 detail
    ↓
API 再次失敗 → ♻️ 無限循環
```

`ship_count` 只有 API **成功**才會 +1，只要失敗就永遠不增加，無法觸發自動終止條件。

PHP 也是相同行為，**無重試上限機制**，依賴客服人工介入或 API 最終成功來中止。

> **技術債待記錄：** 可考慮加入重試上限或自動終止保護，但超出本次重構範圍（目標為 1:1 還原 PHP 行為）。

## Q11：RgoShipLimitCount = 0 表示無上限嗎？

**A：是的，`0` 代表無限期訂閱。**

查詢條件佐證：
```sql
rgo_ship_limit_count = 0 OR rgo_ship_count < rgo_ship_limit_count
```
`= 0` 時直接 pass，等同「不限期數」。

成功後終止判斷：
```csharp
if (rgo.RgoShipLimitCount > 0 && rodShipSequence >= rgo.RgoShipLimitCount)
    rgo.RgoStatus = 3; // 自動終止
```
`RgoShipLimitCount == 0` → 條件永遠不成立 → 永不自動終止，需人工取消。

- `0` = 無限期，訂閱型（直到手動取消）
- `> 0` = 固定期數，到期自動終止

## Q12：RgoPauseDate 是什麼，怎樣會被設定？

**A：`rgo_pause_date` 是「暫停截止日」，初始值為 `2099-12-31`。**

生命週期：

| 時機 | pause_date | rgo_status |
|------|-----------|-----------|
| 建立 | `2099-12-31` | `1` |
| 客戶申請暫停 | `[指定日期]` | `2` |
| 客戶恢復訂閱 | `2099-12-31` | `1` |

篩選條件 `rgo_next_ship_date < rgo_pause_date` 的行為：

| 情境 | pause_date | next_ship_date | 結果 |
|------|-----------|---------------|------|
| 正常 | `2099-12-31` | 任何合理日期 | ✅ 恆成立 |
| 預排暫停（status=1）| `2025-08-01` | `2025-07-15` | ✅ 尚未到暫停日 |
| 預排暫停（status=1）| `2025-08-01` | `2025-09-01` | ❌ 已超過暫停日，不建單 |
| 暫停中（status=2）| 任何 | 任何 | ❌ status=2 已被 rgo_status 條件擋住 |

設計用意：支援「預排暫停」，客戶可預設從未來某天起暫停，status 維持 1，但 next_ship_date 超過 pause_date 後自動不建單。

## Q13：rgo_in_schedule 的用途是？

**A：唯一用途是防止同一期重複建立 detail（幂等保護）。**

- Step③ 建立 detail **之前** 設為 `1`（鎖定）
- 以下情況設回 `0`（解鎖）：
  - Step④ API 成功 → 推進日期時一併解鎖
  - Step② 過期失敗推進 → 推進日期時一併解鎖
  - 客服手動恢復訂閱

鎖定期間，`GetOrdersForDetailGenerationAsync` 的 `RgoInSchedule == false` 條件會把該主計畫過濾掉，確保當天不會重複建立第二筆 detail。

## Q15：TakeOrderApiAsync（Step④）發現哪些問題？

**A：發現兩個問題，均已修正。**

## Q16：CrlStatus 的用意是什麼？

**A：純粹是 API 呼叫歷程 Log，記錄「此次打 API 成功或失敗」，供事後查詢監控用，不影響 Job 流程控制。**

- 排查特定 detail 的失敗原因

## Q17：Pending 狀態的 detail 還有機會被 Step④ 重試嗎？

**A：不會，Pending 由獨立排程 `regular_order_pending_housekeeper` 處理。**

`GetDetailsForApiCallAsync` 條件：
```csharp
&& (rod.RodCreateOrderStatus == 0 || rod.RodCreateOrderStatus == 2)
```

Pending 時 `rod_create_order_status = 1`，不在條件內，Step④ 永遠不會再撈到。

Pending 後續流程由 `regular_order_pending_housekeeper` 負責：等付款完成後再推進主計畫的 `ship_date / next_ship_date / ship_count`。

| ✅ 成功 | ✅ 填入 | 訂單已建立 |

## Q19：PHP 與 .NET Core 雙軌並存期間，會有兩套排程重複處理同一筆資料嗎？

**A：確實會，因為 PHP 排程沒有 provider 過濾。**

- .NET Core 排程：有 `SpiRegularProvider == "Nine1V2"` 過濾，只處理切換後的 shop
- PHP 排程：完全沒有 provider 過濾，對所有 shop 都會處理

當某間店的 `spi_regular_provider` 改為 `"Nine1V2"` 後，.NET 開始處理，但 PHP 不知道，**兩套排程會同時對同一個 MySQL DB 的同一批資料動手**。

### 解決方案比較

| 方案 | 說明 | 優點 | 缺點 |
|------|------|------|------|
| 改 PHP SQL | 在 5 支排程查詢加 `AND spi_regular_provider != 'Nine1V2'` | 改一次，所有 shop 切換自動生效 | 需改 PHP 程式碼 |
| rgo_pause_date + migration log | 切換時把 MySQL `rgo_pause_date` 壓為過去日期，紀錄原始值 | 不改程式 | 每次切換 shop 需執行腳本，有操作風險 |

### 需修改的 5 支 PHP 函式

1. `regular_order.php::get_order_to_generate_new_one`（Step①/Step③）
2. `regular_order.php::get_fail_order_to_update_next_ship_date`（Step②）
3. `regular_order_detail.php::get_new_order_to_establish`（Step④）
4. `regular_order_detail.php::get_total_regular_order_active_by_date`（Step⑤）
5. `regular_order_detail.php::find_pending_order_by_date`（pending housekeeper）

其中 1~3 已有 `LEFT JOIN shop_info`，只需加一行條件；4~5 需補上 JOIN。

> **待確認：** 尚需詢問 PHP 原團隊是否有其他地方（API、觸發器）也需一起加過濾。

## Q20：ERP MSSQL 的 `RegularOrder` 表與 PHP MySQL 的 `regular_order` 是同一張表嗎？

**A：完全不同，分屬不同架構。**

| | ERP DB（MSSQL）`RegularOrder` | PHP DB（MySQL）`regular_order` |
|--|-------------------------------|-------------------------------|
| 寫入時機 | 用戶結帳成功時，由 mweb `CreateRegularOrderProcessor` 寫入 | 由 PHP `create-order-housekeeper` 建立 |

**我們這次重構的排程只操作 MySQL，與 ERP MSSQL 無關。**

## Q21：`SubscriptionOrderAutoGen` API 在 mweb 內部實際做了什麼？

## Q22：`regular_order_detail` 一筆訂閱計畫會有幾筆？如何查詢所有期數？

**A：每期建單產生一筆，查詢時應用 `rod_rgo_pk`，不能用 TG code。**

每期的排程建單都會產生一張**全新的 TG 訂單**，因此每筆 detail 的 `rod_tg_code` 都不同（只有第 1 期沿用首單的 `rgo_source_tg`）。

### 正確查法

```sql
-- ❌ 錯誤：by TG 查只會得到對應期數的那一筆
SELECT * FROM regular_order_detail WHERE rod_tg_code = 'TG260602L00036';

-- ✅ 正確：by rgo_pk 查所有期數
SELECT rod_pk, rod_ship_sequence, rod_ship_date, rod_tg_code,
       rod_create_order_status, rod_status
FROM regular_order_detail
WHERE rod_rgo_pk = 199
ORDER BY rod_ship_sequence;
```

### 正常資料範例（5 期訂閱，3 天一期）

| 期數 | rod_ship_date | rod_create_order_date | rod_tg_code | 狀態 |
|------|--------------|----------------------|-------------|------|
| 1 | 2026-06-04 | 2026-06-02 | TG260602L00036（= rgo_source_tg）| ✅ |
| 2 | 2026-06-07 | 2026-06-05 | TG260605L00025 | ✅ |
| 3 | 2026-06-10 | 2026-06-08 | TG260608L00023 | ✅ |
| 4 | 2026-06-13 | 2026-06-11 | TG260611L00021 | ✅ |
| 5 | 2026-06-16 | 2026-06-14 | TG260614L00020 | ✅ |

規律驗證：
- 間隔 3 天（定期購_3天）✅
- 每次提前 2 天建單（`rod_ship_date - 2 = rod_create_order_date`）✅
- 每期獨立 TG ✅

## Q23：首期訂單會打 `SubscriptionOrderAutoGen` 嗎？

```php
$regular_order_detail->rod_tg_code = $TGCode;  // 首單 TG，直接填入

```

主計畫也同步初始化為已成功狀態：
```php
$regular_order->rgo_ship_count          = 1;   // 已算入第 1 期
$regular_order->rgo_create_order_status = 1;   // 直接成功
```

**只有第 2 期以後才需要由日排程呼叫 `SubscriptionOrderAutoGen` 建立新 TG。**

---

## Q24：第 2 期以後是每次在出貨日前 2 天建 detail、同時打 API 嗎？

**A：是的，Step③ 建 detail 與 Step④ 打 API 在同一次 Job Run 內連續完成。**

```
每日排程觸發
    │
    ├─ Step③：查 rgo_next_ship_date == today + 2 → 建立 rod（cos=0）
    │
    └─ Step④：查 rod_ship_date <= today+2 AND rod_ship_date > today
               → 剛建的 cos=0 rod 符合條件 → 打 API → Stripe 扣款 → 拿到新 TGCode
```

Step④ 的條件是 `<= 2` 而非 `= 2`，目的是支援**失敗重試**：
- D-2：首次打 API，若失敗（cos=2）
- D-1：隔天 Step④ 再撈到這筆（此時 DATEDIFF=1）繼續重試
- D-0：`rod_ship_date > today` 條件不符，不再重試，Step② 廢棄此期

---

## Q25：排程建單的同時就會扣款嗎？

**A：是的，Step④ 打 `SubscriptionOrderAutoGen` 時 mweb 會直接對 Stripe 發起扣款。**

第 2 期以後的扣款依賴首單儲存的 token：
```
rgo_pay_token ← 首單時存入的 Stripe 加密 token（create_order_housekeeper 寫入）
```

`SubscriptionOrderAutoGen` 內部 `GetRegularOrderProcessor` 取出此 token 後，`CreateTradesOrder` 直接對 Stripe 發起扣款，**不需要消費者操作**。

Pending 狀態（`WaitingToPay`）代表 Stripe 非同步確認中（如 3D 驗證），訂單已建立但等 `pending_housekeeper` 確認付款後再推進計畫。

---

## Q26：出貨日前 2 天就扣款，當天才出貨嗎？

**A：是的，這是設計意圖。**

```
D-2：Step③ 建 detail → Step④ 打 API → Stripe 扣款成功 → TG/TS 建立完成
D-1：（D-2 失敗才重試）
D-0：物流/倉儲看到訂單 → 出貨
```

提前 2 天建單的原因：
1. **扣款緩衝**：D-2 失敗還有 D-1 可重試
2. **倉儲備貨**：訂單提前 2 天建立，倉儲有時間備料
3. **Pending 處理**：有足夠時間在出貨前確認付款

---

## Q27：首單的出貨日是何時？

**A：首單出貨日 = 消費者下單日 + 2 天。**

```php
// create_order_housekeeper.php
$ship_date_from_create_count = 2;
$regular_order->rgo_ship_date = Date('Y-m-d',
    strtotime($FirstOrderDate . '+2 day'));
$regular_order_detail->rod_ship_date = Date('Y-m-d',
    strtotime($FirstOrderDate . '+2 day'));
```

與後續每期邏輯一致：**建單日 + 2 天出貨**。

## Q28：設定 ship_period=1（每天一期）可以用來測試嗎？

**A：完全可行。**

`ship_period=1` 時：
- Step③：`rgo_next_ship_date == today + 2`，每天都有一筆符合
- Step④：每天觸發一次 API 建單
- 每次成功後：`rgo_next_ship_date += 1 天` → 明天又觸發

邏輯完全正常，適合快速驗證完整定期購流程（建 detail → 打 API → 推進日期 → 再建 detail）。

---

## Q29：誰負責出貨？排程系統有參與出貨嗎？

**A：排程系統完全不負責出貨，出貨由正常訂單流程（ERP / 倉儲）處理。**

| 工作 | 負責方 |
|------|--------|
| 建立定期購計畫（rgo） | `create_order_housekeeper` |
| 建立每期 detail（rod） | `regular_create_housekeeper` Step③ |
| 建立 TG/TS 訂單 | `regular_create_housekeeper` Step④（打 API）|
| 扣款 | mweb `SubscriptionOrderAutoGen` → Stripe |
| **出貨** | **ERP / 倉儲系統（與一般訂單完全相同）** |

排程做完 Step④ 後，這張 TG/TS 訂單就進入正常訂單系統，後續流程與消費者自行下單**完全一樣**，定期購系統不再介入。
