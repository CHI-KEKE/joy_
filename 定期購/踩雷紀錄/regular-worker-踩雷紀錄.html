MINE #01
時區手動換算（AddHours(8)）+ DateTimeKind 誤標
嚴重度：中
RegularCreateOrderJob.cs · RegularOrderFailedNotifyJob.cs · RegularOrderStockNotifyJob.cs · RegularOrderDetailRepository.cs · RegularOrderRepository.cs（共 15＋ 處）

現象

全專案唯一的「取得台灣時間」方式是 DateTime.UtcNow.AddHours(8)，只有 RegularOrderInitJob.cs 一處例外使用了正規的 TimeZoneInfo.ConvertTimeFromUtc。

// 典型寫法，散落在 15+ 處
var today = TryParseExecuteDate(data) ?? DateOnly.FromDateTime(DateTime.UtcNow.AddHours(8));
rod.RodCreateTime = DateTime.UtcNow.AddHours(8);
queue.NqSendTime  = DateTime.UtcNow.AddHours(8);

根因

AddHours(8) 只改變數值，不會改變 DateTime.Kind。結果是「數值看起來像台灣時間，但 Kind == Utc」——一個自相矛盾的資料狀態。

⚠
若日後這個值被 EF Core / Npgsql 寫入 timestamptz 欄位，或被任何程式呼叫 .ToUniversalTime()／.ToLocalTime()，框架會依 Kind==Utc 判斷「這已經是 UTC」，導致再轉換一次、多／少 8 小時。這正是「後台顯示的訂單時間跟客服看到的對不上」這類靈異 bug 的典型成因。

引爆條件

目前尚未爆發（因為下游系統也一致地把這個值當作「台灣時間」使用），但只要：① 換 DB provider 或欄位型別、② 有新同事依 Kind 寫轉換邏輯、③ 未來新增非 UTC+8 市場，三者任一發生就會引爆。

建議修法

  • 抽出 IClock / IMarketTimeZoneResolver 服務，統一用 TimeZoneInfo.ConvertTimeFromUtc 取代所有 AddHours(8)
  • 轉換後明確 DateTime.SpecifyKind(value, DateTimeKind.Unspecified) 再寫入 DB，避免被誤判
  • 統一 15＋ 處呼叫點，消除與 RegularOrderInitJob.cs 兩套邏輯並存的不一致
MINE #02
出貨日當天完全不重試，隔天才判定過期
嚴重度：中高
RegularOrderDetailRepository.cs → GetDetailsForApiCallAsync / AbandonExpiredDetailsAsync

現象

建單重試視窗使用「嚴格大於」today，出貨當天不在窗口內：

// Step④ 重試查詢條件
rod.RodShipDate > today && rod.RodShipDate <= today.AddDays(2)

// Step② 過期廢棄條件（隔天才成立）
rgo.RgoNextShipDate < today

案例走讀（出貨日 D = 8/1）

7/30 (D-2)
Step④ 嘗試建單 FAIL
條件 8/1 > 7/30 && 8/1 ≤ 8/1 成立 → 呼叫 API，假設失敗，rod_create_order_status = 2
7/31 (D-1)
Step④ 再次嘗試 FAIL
條件 8/1 > 7/31 && 8/1 ≤ 8/2 成立 → 再次呼叫 API，假設又失敗
8/1 (D)
出貨日
Step④ 不會嘗試 SKIPPED
條件 8/1 > 8/1 為 False → 不在查詢範圍。Step② 條件 8/1 < 8/1 也是 False → 還沒被判過期。這天完全沒有任何動作。
8/2 (D+1)
Step② 判定過期並廢棄 RESOLVED
條件 8/1 < 8/2 成立 → rod_status=2（廢棄），rgo_next_ship_date += ship_period 推進下一期
⛔
使用者在「應出貨當天」不會收到最後一次補救嘗試，也不會立即收到失敗通知——通知與廢棄動作要等 D+1 才處理，等於出貨日當天是個空窗期。

建議修法

  • 若業務上希望出貨日當天仍嘗試最後一次，重試視窗應改為 rod.RodShipDate >= today
  • 若維持現行設計，至少應在 D 當天發出「即將於今日出貨但尚未成功」的即時告警，不要等到 D+1
MINE #03
Pending 未解決 → 主計畫永久卡死，不再進下一期
嚴重度：嚴重
RegularCreateOrderJob.cs → TakeOrderApiAsync · RegularOrderRepository.cs → SetInScheduleAsync / UpdateAfterApiSuccessAsync / UpdateExpiredFailAsync · RegularCheckPendingPaymentJob.cs

現象

API 回傳 OrderSlaveFlowStatus == "WaitingToPay" 時，只更新了 detail (rod)，完全沒有更新主計畫 (rgo)：

else if (isPending)
{
    await _detailRepo.UpdateAfterApiPendingAsync(...);
    // ⚠️ 沒有呼叫 _orderRepo，rgo_in_schedule 沒有被解鎖
}

根因

Step③ 建 detail 前會鎖住主計畫排程：

rgo.RgoInSchedule = true; // SetInScheduleAsync，Step③ 建 detail 前呼叫

而這把鎖只有兩處會解開，Pending 兩者都不符合：

解鎖時機觸發條件Pending 符合？
UpdateAfterApiSuccessAsyncAPI 真正回傳成功✗ 不符合
UpdateExpiredFailAsync（Step②，D+1）rgo_create_order_status == 2（失敗）✗ 不符合

而 Step③ 產生下一期 detail 的查詢條件要求 rgo_in_schedule == false——鎖永遠打不開，下一期就永遠不會被建立。

案例走讀（MY 商店，出貨日 D = 8/1）

7/30 10:15
(D-2)
Step④ 呼叫 API PENDING
回傳 WaitingToPay → rod_status=3，rgo_in_schedule 維持 true（鎖住）
7/30 10:45 / 11:15
CheckPendingPaymentJob 檢查兩次 未解決
SCM 查無結果或超時，假設兩次都沒有 resolve
7/31 起
永遠查不到這筆 STUCK
GetPendingDetailsAsync 只抓「今天」標記為 Pending 的資料（RodDaemonActiveTime 停在 7/30，不會每天更新），隔天起條件永遠對不上
此後每一期
主計畫完全停滯 DEAD
Step③ 因 rgo_in_schedule=true 永遠跳過此計畫；Step② 因 rgo_create_order_status≠2 也不會廢棄。該會員的定期購從此不會再建立任何一期新訂單，且無任何告警
⛔
市場風險放大：Pending 確認 Job（regular-order-pending-job-daily-1/2）目前只部署在 MY 市場（values-my-*.yaml），TW / HK 完全沒有這組 CronJob。若 TW / HK 商店的付款流程曾經走到 WaitingToPay 分支（程式邏輯是共用的，理論上可能發生），該筆訂單會立即且永久卡死，因為連「當天兩次檢查」的補救機會都不存在。

建議修法

  • Pending 分支也要像失敗一樣有「N 天後仍未解決 → 視同失敗，解鎖 rgo_in_schedule 並推進/終止週期」的兜底邏輯
  • GetPendingDetailsAsync 不應只查「今天」，應改為查詢「所有仍為 rod_status=3」的明細，不限定當天，避免超過檢查視窗就永久遺失
  • 確認 TW / HK 是否真的不會產生 WaitingToPay；若可能發生，需比照 MY 補上 RegularCheckPendingPaymentJob CronJob
  • 新增監控：統計 rod_status=3 且建立時間超過 N 天的筆數並告警
