2Config Key 命名規則

程式內部固定組字規則（CircuitBreakerManager.cs / CircuitBreakerService.cs）：

ControllerName、ActionName 由 Attribute 執行當下動態取得；RecognizeType 在 Attribute 內寫死為 "SupplierId"。

{Execmode}.{Key}
例：Prod.ExceededTimesLimiter.SalePageLite.GetMain.SupplierId
關於「三階段開關」：這是 Config 治理表單上對此 Key 的分類標籤（管控上版審核流程，例如 Off → 灰度 → 全開三個佈署階段的變更管理方式）。 但程式碼本身只認單純布林 Enabled，沒有內建百分比灰度邏輯 —— Config 治理層面走三階段審核，但程式執行層面一旦設為 true 即為全量生效（依 SupplierId 個別計次）。

3Config Value 格式

Enabled|MaxTimes|CacheSeconds|LockedSeconds
欄位說明
Enabled是否啟用限流（true / false）
MaxTimesCacheSeconds 週期內允許的最大呼叫次數

意義：每個供應商 60 秒內最多呼叫 200 次，超過即鎖定該供應商 30 秒。

5兩個 Repo「ExceededTimesLimiter 限流機制」本身的邏輯/機制比較

聚焦在限流這套機制自己的演算法與行為（非兩邊技術框架的一般性差異），逐檔逐行比對後的結論如下。

5.1 結論先講：核心演算法「完全一致」

NineYi.Scm.Api（ExceededTimesLimiterManager.cs）與 NineYi.Scm.ApiV2（ExceededTimesLimiterService.cs）這兩支「限流判斷主邏輯」程式碼，逐行比對後除了類別/介面命名（Manager ↔ Service）與 namespace 不同以外，演算法、參數、常數、判斷順序全部一模一樣，屬於「同一套邏輯被複製貼上到兩個 Repo 各自維護」，不是各自獨立設計的兩套機制：

判斷步驟Api（Manager）ApiV2（Service）是否一致
是否為 API Gateway 流量（N1-TRACE-ID）有檢查，沒有就直接放行有檢查，沒有就直接放行✅ 一致
Enabled=false 時的行為直接 return，不限流直接 return，不限流✅ 一致
CacheKey 組成規則{Controller}:{Action}-2024102801:SupplierId:{值}{Controller}:{Action}-2024102801:SupplierId:{值}✅ 一致（連版本戳記數字都相同）
計次時間窗口對齊演算法GetAdjustDateTimeByIntervalSeconds同名同邏輯函式，程式碼逐行相同✅ 一致
計次方式Redis IncrBy + Cache.DefaultExpire（預設10800秒）同左✅ 一致
鎖定判斷/設定鎖定IsLocked / SetLocked，MemoryCache(1秒)+Redis(LockedSeconds)雙層同左，程式碼逐行相同✅ 一致
例外拋出ExceededTimesLimiterException(..., NoMoreElmah)同左✅ 一致
Redis Timeout 處理catch RedisTimeoutException → 降級放行同左✅ 一致

5.2 真正有差異的地方：設定來源的「取得管道」不同

限流的「行為判斷」一樣，但取得 Enabled/MaxTimes/CacheSeconds/LockedSeconds 設定值的底層管道在兩邊有實質差異：

項目NineYi.Scm.Api（CircuitBreakerManager.cs）NineYi.Scm.ApiV2（CircuitBreakerService.cs）
查詢 DB 用的連線讀寫主連線（ERP，未指定 ReadOnly）明確指定 [WithKey("ReadOnly")]，強制走唯讀複本（ERP.ReadOnly）
DB Repository 對 ValidFlag 的篩選寫法LINQ where 手動寫 ValidFlag == true使用共用擴充方法 .Valids()
設定快取 CacheKey 版本戳記無日期版號，TypeName = "ExceededTimesLimiterSettings"有日期版號，TypeName = "ExceededTimesLimiterSettings-20200826"
GetCacheKey 例外處理細緻度找不到對應 type 直接 throw ArgumentException多包一層 try/catch，額外攔截 IndexOutOfRangeException
Config Key 讀取呼叫呼叫方式、Key 命名規則、預設值完全相同
影響評估：
  • DB 連線差異（主連線 vs 唯讀複本）是唯一具備實質運維意義的差異：ApiV2 查供應商客製設定固定走唯讀複本，若 DB 有主從複寫延遲，剛異動完的供應商設定在 ApiV2 這邊可能短暫「還沒同步到唯讀庫」；Api 走主連線則異動後立即可見。不過外層還有 5~10 秒的 MemoryCache/RedisCache，實務影響遠小於快取本身造成的延遲。
  • 設定快取的版本戳記純粹是各自程式碼上版時用來手動 cache-busting 的工程慣例，不影響限流判斷結果。
  • 兩邊的四把 Config Key 皆各自獨立維護在各自服務的 AppSettings*.config 內，互不共用、也不會互相同步——開 SalePageLite.* 兩把 Key 要改 NineYi.Scm.Api 的 config，開 SalesOrderGetLite.Get / ShippingOrder.Get 則要改 NineYi.Scm.ApiV2 的 config。
總結一句話：兩個 Repo 的限流「機制」是同一套演算法的平行複製（行為 100% 一致），差異只在「設定來源查詢時走的 DB 連線（主 vs 唯讀）」與「快取版本戳記的工程慣例」，並不影響限流本身的邏輯正確性。

  1. 這是針對供應商 SupplierId=1614 的個別覆蓋設定（GroupName='ExceededTimesLimiter' + Key='SalesOrderGetLite.Get'），對應到 SalesOrderGetLiteController.Get 這支 API。
  2. Value 欄位內容 SupplierId=true|200|1|0：程式用 ; 切開多筆設定，再找出以 {RecognizeType}=（此處固定為 "SupplierId"）開頭的那段，取出後半段 true|200|1|0 交給 ExceededTimesLimiterSettingsEntity.Parse()： Parse 後對應 Enabled=true、MaxTimes=200、CacheSeconds=1、LockedSeconds=0。
  3. 實際行為意義：
    • Enabled=true → 此供應商的這支 API 有開啟限流。
    • MaxTimes=200、CacheSeconds=1 → 在每 1 秒的時間窗口內，最多允許呼叫 200 次。
    • LockedSeconds=0 → 程式判斷 if (settings.LockedSeconds > 0 && IsLocked(...)) 與 if (settings.LockedSeconds > 0) SetLocked(...)：當 LockedSeconds 為 0 時，鎖定機制完全不會被觸發。超過 200 次/秒時該次請求仍會被擋下回傳 429，但不會額外設定「鎖定」，下一個 1 秒窗口一到計數器立即歸零重算，沒有額外的延長鎖定期。
    • 換句話說，這是一個「純粹瞬間流量閥門」設定：只擋單一秒內超過 200 次的部分請求，不會像 LockedSeconds>0 那樣把供應商「多鎖一段時間」。
  4. 與全域 Config Key 的關係：因為 SupplierId=1614 在 DB 已有此筆有效資料（ValidFlag=1），CircuitBreakerService.GetExceededTimesLimiterSettings 會優先採用這筆 DB 設定，完全不會去讀取全域 Prod.ExceededTimesLimiter.SalesOrderGetLite.Get.SupplierId 這把 Config Key（除非未來此筆資料 ValidFlag 改為 0，才會 fallback 回全域 Key）。
  5. UpdatedTimes=1 且 UpdatedDateTime 晚於 CreatedDateTime → 顯示這筆設定建立後曾被異動過一次（例如原本門檻不同，後來調整為目前的 200|1|0）。

8判斷細節補充

  1. 只認 API Gateway 流量：Header 沒有 N1-TRACE-ID 直接略過整個限流檢查。
  2. 設定優先序：供應商個別設定（DB）＞ Config Key（AppSetting，即本文四把 Key）＞ 程式碼內建預設值 false|3|1|30。
  3. CacheKey 組成：{Controller}:{Action}-{版本號}:SupplierId:{值}:{整秒對齊時間}，不同供應商 / 時間窗口互不干擾。
  4. 鎖定機制：超過 MaxTimes 後額外設 Locked cache，鎖定 LockedSeconds 秒內不論次數一律擋下。
  5. 快取層：Redis（ICacheProvider）+ In-Process MemoryCache 雙層快取，降低 Redis 壓力。
  6. 降級處理：Redis Timeout 時視為放行（不因快取異常誤擋合法請求）。

10原理：限流是「令牌桶」還是別的機制？

這章節深入拆解 ExceededTimesLimiterManager.cs（Api）／ExceededTimesLimiterService.cs（ApiV2）內部真正的計數演算法，回答一個常見疑問：這個限流器是類似「令牌桶（Token Bucket）」的概念嗎？

10.1 結論：不是令牌桶，是「固定時間窗口計數器」＋「鎖定懲罰期」

令牌桶的特色是令牌會持續、平滑地產生／回補，允許一定程度的突發流量被平均攤提。但這裡完全不同，程式碼實際做的事情是：

  1. 把「目前時間」對齊（無條件捨去）到 CacheSeconds 的整數倍，變成一個「時間窗口字串」。
  2. 用 {Controller}:{Action}-版本號:{RecognizeType}:{RecognizeKey}:{窗口字串} 當 Cache Key，對這把 Key 做 Redis IncrBy(1)。
  3. 若這把 Key 目前累加值 > MaxTimes，就丟例外擋下（HTTP 429）。

這是標準的 Fixed Window Counter（固定窗口計數器）：每個窗口都是獨立、歸零重算的計數器，並非連續平滑供應的令牌。

10.2 窗口字串怎麼算出來的？（不是查詢區間，是直接算出 Key 名稱）

很多人會誤以為做法是：先建立一把 Key 存 {start, end, count}，每次請求進來都要判斷「now 是否落在 start~end 之間」。實際完全不是這樣——真正的做法是反過來：

核心觀念：每次請求進來，都直接用「現在時間」重新算一次「我現在應該對應到哪一個窗口字串」，再拿這個字串直接當 Cache Key 名稱去 +1。
同一個窗口內，任何時間點算出來的字串都完全相同 → 天生命中同一把 Key，自然累加成同一顆 counter；
換了窗口，算出來的字串就不同 → 天生是全新一把 Key，counter 從 0 重新開始。
「是否落在同一個區間」這件事，是靠字串是否相同隱含決定的，不需要額外寫一道 if 判斷 start~end。 
GetAdjustDateTimeByIntervalSeconds(now, CacheSeconds)
例：CacheSeconds = 30
17:42:52.025  →  "20260814174230"
17:42:58.999  →  "20260814174230"   ← 同一個 30 秒區間內，任何時間算出來都一樣
17:43:01.100  →  "20260814174300"   ← 過了 30 秒邊界，變成新字串

完整 Cache Key 範例（對應正式資料 SupplierId=1614, SalesOrderGetLite.Get）：
SalesOrderGetLite:Get-2024102801:SupplierId:1614:20260814174230

另外，程式裡設定的 Cache 過期秒數（Cache.DefaultExpire，預設 10800 秒 = 3 小時）跟「窗口大小 CacheSeconds」是完全不同的兩件事：CacheSeconds 決定窗口字串多久換一次（限流的計算週期），expiredSeconds 只是這把 Key 在 Redis/Memory 裡多久沒人動就自動被資源回收，不影響限流邏輯本身。

10.3 疊加的第二層：獨立的「鎖定（Locked）」懲罰機制

這是與單純固定窗口限流最大的不同之處——超過額度時，不是「這次擋下、下個窗口自動恢復」，而是可以額外觸發一段更長的鎖定期，鎖定期間即使窗口已經換了、次數已經歸零，一樣照擋：

if (settings.LockedSeconds > 0 && IsLocked(cacheEntity))
    throw ...;                    // 已被鎖定，直接擋，連新窗口都不給機會

if (tryTimes > settings.MaxTimes)
{
    if (settings.LockedSeconds > 0)
        SetLocked(cacheEntity, settings.LockedSeconds);   // 觸發鎖定
    throw ...;
}

SetLocked 寫入的是另一把獨立 Cache Key（{Fullkey}:Locked），跟計次用的窗口 Key 完全分開，存活 LockedSeconds 秒。這其實比較接近「熔斷器（Circuit Breaker）懲罰期」的概念，而非單純限流——超標一次就懲罰性地鎖住一段時間。這也解釋了為什麼正式資料 SupplierId=true|200|1|0（LockedSeconds=0）代表完全不啟用鎖定懲罰：單純靠固定窗口本身每秒重置在限速，超過當秒就擋，下一秒立刻恢復，沒有額外連坐處罰。

10.4 快取層：Memory + Redis 雙層，鎖定旗標查詢有最終一致性延遲

GetMemoryOrRedisCacheData / SetMemoryOrRedisCacheData 是另一個關鍵細節：寫入時同時寫 Memory（本機行程內，短 TTL）與 Redis（跨主機共享）；讀取「是否已鎖定」時先查 Memory，沒有才查 Redis，查到才回填 Memory（固定 TTL 1 秒）。這代表鎖定狀態的查詢有最多 1 秒的最終一致性延遲，多台主機間鎖定生效可能有些微時間差，是效能與一致性的取捨。但真正用來計數判斷是否超標的 IncrBy（次數本身）是直接打 Redis，跨主機即時共享、準確累加，不受此 1 秒延遲影響。

10.5 固定窗口的已知缺陷：邊界瞬間可能出現 2 倍流量

固定窗口計數器有一個業界公認、最經典的缺陷：窗口邊界瞬間可能被打出「雙倍流量」，且不需要多高深的技巧，只要剛好卡在邊界附近呼叫就會發生。

情境舉例（以正式資料 SupplierId=true|200|1|0，即每秒最多 200 次為例）：
  • 供應商在 17:42:52.700 ~ 17:42:52.999 這 300 毫秒內，連續打了 200 次 → 命中同一把窗口 Key，第 201 次被擋下（符合預期）。
  • 窗口緊接著跳到 17:42:53，Cache Key 字串變成全新的一把，counter 從 0 重新開始 → 供應商在 17:42:53.000 ~ 17:42:53.300 這 300 毫秒內又連續打了 200 次，完全不會被擋。
  • 結果：17:42:52.700 ~ 17:42:53.300 這短短 600 毫秒的真實時間窗口內，實際流量是 200 + 200 = 400 次，是設定值 MaxTimes=200 的整整 2 倍。若刻意抓準整秒邊界規律性地打，甚至能長期維持在理論上限的 2 倍，而不觸發任何一次例外。

根本原因：固定窗口的判斷邏輯只看「單一窗口內部自己的累加值」，完全不知道、也不管「上一個窗口尾巴」跟「這個窗口開頭」黏在一起看，真實流量密度是多少——窗口與窗口之間是互相獨立、互不參照的兩把不同 Cache Key，沒有任何機制平滑銜接。

對比其他限流演算法：

  • 滑動窗口（Sliding Window）：判斷「以現在為結尾往回推 1 秒」的總次數（而非整秒對齊），邊界跨秒也會被抓到，不會有 2 倍漏洞。
  • 令牌桶（Token Bucket）：令牌連續、平滑地以固定速率回補，不存在「整秒歸零重來」這種懸崖式重置，突發流量最多只能用完當下累積的桶內存量。

實務影響評估：影響大小主要看 CacheSeconds 設多大——像 SalesOrderGetLite.Get 這種 CacheSeconds=1 的短窗口，邊界效應相對有限（頂多是 1 秒內的瞬間尖峰，且攻擊者要精準卡秒、長期穩定命中並不容易）；若未來有 API 把 CacheSeconds 設得很大（例如 30、60 秒），邊界翻倍的絕對量會更可觀，且更容易被刻意規避，屆時需要重新評估是否改用滑動窗口或令牌桶。

總結一句話：這是「固定時間窗口計數器」（非令牌桶、非滑動窗口），窗口用時鐘整除對齊直接算出 Key 名稱；超標時可疊加一段獨立的鎖定懲罰期（類熔斷器概念）；計數用 Redis 共享確保多主機一致，鎖定旗標查詢則走 Memory+Redis 雙層快取以求效能——用極簡單的實作與極低的效能開銷，換取「窗口邊界理論上最多 2 倍瞬時流量」的已知工程取捨，而非程式錯誤。

11.3 為什麼網址完全沒變、呼叫端完全無感？

ASP.NET Web API 的 Attribute Routing 在啟動時，會把專案裡所有 Controller 一起掃描一遍，蒐集每一個 [RoutePrefix]+[Route] 組合，建立成一張全域路由表。路由表只認「最終組出來的網址字串」，完全不在乎這個組合來自哪一個類別。
時期SalesOrder/Get實際處理的類別
抽 Lite 前SalesOrder/GetSalesOrderController.Get()
抽 Lite 後（現況）SalesOrder/GetSalesOrderGetLiteController.Get()

只要「同一時間點，兩個 Controller 不會同時對同一個網址各自宣告 [Route]」（否則會路由衝突報錯），拆分時把舊方法整個刪掉、新方法沿用同樣的路由字串接手，對外部呼叫者而言網址完全沒變、行為完全無感知，這就是「無痛搬家」的原理。

總結一句話：不是「以前打 SalesOrder/Get 會到另一支完全獨立的 API」，而是「以前 SalesOrder/Get 打到的是巨型 SalesOrderController 裡眾多方法之一的 Get()」；2025-09-26 重構時把這一個方法連同對應商業邏輯，整個搬遷到新建的、專屬精簡的 SalesOrderGetLiteController，並在新類別上刻意沿用一模一樣的 [RoutePrefix("SalesOrder")] + [Route("Get")]，讓路由表指向新類別，達成「網址完全不變、呼叫端無需修改任何程式碼」的無痛搬遷效果。這也解釋了為什麼「Route 用的名稱（SalesOrder）」跟「限流引擎讀取的 ControllerName（SalesOrderGetLite）」會不一致——兩者資料來源本來就不同，Route 是刻意維持歷史相容性，ControllerName 則反映了目前實際的類別名稱。

12HK Prod Config 套用評估 實際 IIS Log 數據驗證

目的：在正式對 HK Prod 環境補上與 TW 相同的 4 把 ExceededTimesLimiter Config 之前，先用 Athena（AWS）查詢近幾個月的實際 IIS Log，評估「如果 HK Prod 也套用跟 TW 一樣的參數（true|200|1|0，即每秒最多 200 次），會不會真的擋到任何供應商」，避免上線後才發現誤傷正常流量。

12.1 查詢方法

資料來源：hk_prod_osm.osm_api_iislog（HK Prod 環境 OSM API 的 IIS Log，透過 Athena SQL 查詢），鎖定 SalePage/GetMain 這支 API 為例，統計「每一秒、每一個供應商 Token」的呼叫次數，由高到低排序，藉此找出歷史上真正出現過的尖峰流量：

SELECT
    date,
    time,
    regexp_extract(cs_uri_query, '(^|&)t=([^&]+)', 2) AS token,
    COUNT(*) AS request_count
FROM "hk_prod_osm"."osm_api_iislog"
WHERE cs_uri_stem = '/scm/V1/SalePage/GetMain'
  AND date > '2026/05/01'
  AND date < '2026/08/14'
GROUP BY regexp_extract(cs_uri_query, '(^|&)t=([^&]+)', 2), date, time
ORDER BY request_count DESC
LIMIT 10;

查詢邏輯重點：用 regexp_extract 從 cs_uri_query 這個 Log 欄位裡把驗證用的 t（Token，識別供應商）參數抓出來，依「日期＋秒級時間戳（IIS/W3C Log 的 time 欄位本身就是精確到秒，格式 HH:MM:SS）＋Token」分組計數，藉此還原「某個供應商在那一整秒內實際打了幾次」——這與限流器 CacheSeconds=1 窗口的統計粒度完全對齊（1:1 對應，非估算），可以直接拿來對照 MaxTimes=200 這個門檻，評估歷史上是否曾經逼近或超過。

  • 擋下後的行為：依第 4 章流程圖，超過門檻時 ExceededTimesLimiterException 會被拋出，最終呼叫端會收到 HTTP 429 回應（Too Many Requests），而非伺服器錯誤，是限流器設計上預期的正常拒絕行為。
