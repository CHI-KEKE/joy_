👻 Search.ServiceV2.Cache.Enabled 完整分析

這份文件整理一個開關設定從程式碼原理到正式環境實際狀態的完整追查過程，包含意外發現的市場設定落差。

nineyi.webstore.mobilewebmall nineyi.configuration
01

情境概述

消費者在前台網站瀏覽某個商品分類時，會看到一份商品清單，可以捲動、換頁、依照標籤或價格篩選。這份清單的資料來自一套獨立的搜尋服務，程式裡有一個開關叫做 Search.ServiceV2.Cache.Enabled，決定這份清單資料要不要先暫存一份副本，還是每次都重新去搜尋服務要一次。

這份文件會依序說明這個開關實際控制了什麼行為、背後搜尋服務為什麼採用 Elasticsearch、篩選條件裡的標籤代表什麼意思，最後追查到這個開關在不同市場、不同應用程式之間的真實設定值，並發現香港市場出現一個跟其他市場不一致的特例。

涉及專案

nineyi.webstore.mobilewebmall（程式碼與預設 config）、nineyi.configuration（正式環境各市場實際部署 config）。

核心發現

香港市場在 WebAPI 這個獨立應用程式裡，這個快取開關被關閉，跟其他市場的設定不一致。

延伸問題

消費者實際瀏覽分類頁時，資料到底是走哪個應用程式的設定，需要追到前端呼叫路徑才能確認。

02

快取機制原理

這個開關讀取的位置在共用類別庫的 SearchService 裡，建構子執行時會把設定值存到一個內部欄位。

// SearchService.cs 建構子內
this._enableCache = this._configService.GetAppSetting("Search.ServiceV2.Cache.Enabled").ToBoolean();

這個欄位只在一個方法裡真正被使用，也就是取得商店分類商品頁清單的方法。這個方法會把搜尋條件組成一把快取鍵值，交給快取服務去判斷要不要真的呼叫搜尋服務。

快取服務內部的判斷邏輯是一個非常單純的分支，決定了整個機制的行為：

收到查詢請求
→
快取開關是否為關閉
→
直接呼叫搜尋服務，不查快取

如果快取開關不是關閉，流程會先去暫存區找有沒有符合這把鍵值的資料，找不到才會去呼叫搜尋服務，並把結果暫存一分鐘，下一次同樣條件的查詢就能直接使用暫存內容，不用再呼叫一次搜尋服務。

💡

白話理解：開關打開，代表短時間內同樣的分類、同樣的篩選條件，只會真正去問一次搜尋服務，其餘請求都直接用暫存結果回應。開關關閉，代表每一次瀏覽都會直接去問搜尋服務，沒有任何暫存。

⚠️

取捨：暫存機制能大幅降低搜尋服務的查詢壓力，但代價是商品資料變動後，最多要等一分鐘才會反映在分類頁上；關閉暫存則資料即時，但流量高的時候會讓搜尋服務承受更大的壓力。

快取 Key 怎麼組成

前面提到「把搜尋條件組成一把快取鍵值」，實際上這把鍵值不是一個字串，而是由三段資訊組成一個結構，最後才拼接成真正存進 Redis 的完整 Key。

ServiceName（固定 "Search"）
→
TypeName（方法名稱＋版本編號）
→
Key（查詢條件依序組合）

以分類頁清單這個方法為例，程式會先把會影響查詢結果的條件，依照固定順序放進一個字串陣列，再用這個陣列組出 CacheKeyEntity：

// SearchService.cs：組合快取鍵值用的參數
var cacheKeyParams = new List<string>
{
    requestEntity.ShopId.ToString(),
    requestEntity.ShopCategoryId.ToString(),
    requestEntity.OrderEnum.ToString(),
    requestEntity.StartIndex.ToString(),
    requestEntity.MaxCount.ToString(),
    includeSalePageGroup.ToString(),
    includeInvisibleSalePage.ToString()
};
// 之後依條件是否有值，陸續加入 LocationId、ShippingType、ApplyType、
// Tags、ShowMoreTags、MinPrice、MaxPrice、PayType、品牌頁排序標籤 等參數

換句話說，只要商店、分類、排序方式、頁碼、頁數、標籤、價格區間、付款方式、運送方式其中任何一項不同，組出來的 Key 就不同，等於是不同的快取內容；只有這些條件完全相同的兩次查詢，才會共用同一份暫存資料。

接著這批參數會交給 GetCacheKey 方法，組成完整的 CacheKeyEntity：

// SearchService.cs：依方法名稱決定 TypeName 版本編號
CacheKeyEntity cacheKey = new CacheKeyEntity("Search", keys);

switch (type)
{
    case "GetShopCategorySalePageList":
        cacheKey.TypeName = string.Format("{0}-{1}", type, "2020121416");
        break;
    // GetShopPayTypeAndShippingType、GetSalePageByIds 等其他查詢，
    // 也各自對應一組「方法名稱-版本編號」
}

其中 CacheKeyEntity 內部會把陣列裡的每個參數用 - 串起來當作 Key，最終真正存進 Redis 的完整鍵值，是三段資訊用 : 串接的結果：

完整 Key 格式： ServiceName:TypeName:Key

以分類頁清單為例，實際組出來的樣子接近：Search:GetShopCategorySalePageList-2020121416:{ShopId}-{ShopCategoryId}-{OrderEnum}-{StartIndex}-{MaxCount}-{是否含商品群組}-{是否含隱藏商品}-...（其餘有值的條件）

💡

版本編號的用途：TypeName 後面那串數字（例如 2020121416）是修改當次查詢邏輯或回傳結構時人工遞增的版本號。一旦查詢邏輯改變導致舊快取內容不再適用，只要把版本號改掉，等同讓所有舊的 Key 全部失效，不需要額外清除快取，新舊版本的快取也不會互相污染。

⚠️

語系也會影響 Key：實際寫入 Redis 前，快取服務還會依站台是否啟用多語系，把目前的語系代碼再接到 Key 後面（例如 -zh-TW）。也就是說同樣的查詢條件，不同語系會各自擁有獨立的一份快取，不會互相共用。

03

為何選用 Elasticsearch

分類頁背後真正提供資料的搜尋服務，底層是 Elasticsearch，這個判斷來自幾個直接證據，而不是憑空猜測。

證據一 Config 檔案分類註解

正式環境 config 裡，這個開關被歸類在一段標註著「Elasticsearch」的區塊底下，跟搜尋服務網址、版本號放在一起。

證據二 服務網址命名

搜尋服務的主機名稱本身就包含 search-es 這個字樣，其中 es 就是 Elasticsearch 的縮寫。

證據三 程式碼裡的列舉值

搜尋結果物件的資料來源欄位，被明確標記成代表 Elasticsearch 的列舉值，程式註解也直接稱呼這個資料來源為 ES。

確認底層技術之後，接著要理解為什麼分類頁要特地用 Elasticsearch 而不是直接查詢主要交易資料庫，理由可以分成三個層面。

多條件過濾與排序

分類頁同時要處理分類、標籤、價格區間、付款方式、運送方式等條件，還要支援相關度、銷售排行、瀏覽人氣等多種排序方式。這類「多條件過濾加多種排序」的組合，關聯式資料庫需要靠大量索引與多表關聯才能勉強應付，搜尋引擎的反向索引架構天生就是為這種查詢設計。

標籤分面統計

分類頁篩選介面需要同時顯示「目前有哪些標籤可以選、每個標籤底下有幾件商品」，這種一次查詢同時拿到清單與統計數字的能力，是搜尋引擎的分面統計功能，關聯式資料庫沒有對應的原生機制。

流量分流

商品瀏覽是全站流量最大的功能之一，行銷用的商品動態廣告資料來源也是同一套搜尋服務。把高頻讀取的商品查詢獨立到搜尋服務，可以避免主要交易資料庫被大量讀取請求拖慢寫入效能，也讓查詢層可以獨立水平擴充。

👻

運作原理簡述

商品資料會先透過另一支同步程序，從交易資料庫轉換成文件格式寫進 Elasticsearch，建立反向索引，這個過程是離線進行的，因此商品異動到搜尋服務查得到中間會有延遲。查詢時，Elasticsearch 會先用反向索引快速篩出符合條件的商品集合，這一步不計算分數、只做集合交集，速度很快；如果排序方式是相關度，才會再用評分演算法排序，如果是銷售排行等其他排序方式，則直接依欄位數值排序。

04

Tag 篩選條件的意義

分類頁請求裡有一個叫做 Tags 的篩選欄位，代表消費者在畫面上勾選的商品標籤篩選條件，會被組進呼叫搜尋服務的網址參數，讓搜尋服務只回傳帶有指定標籤的商品，同時這個條件也會被加進暫存鍵值裡，不同標籤組合會對應到不同的暫存內容。

標籤群組用途是否為消費者可篩選項目
N1-S-ProductBadge顯示在商品圖片上的角標圖示，例如新品、限量等視覺標記，依角標開始時間排序顯示否，純顯示用途
N1-S-Brand品牌頁排序邏輯使用，搭配「館長推薦」排序方式時用來對應品牌間接影響排序，非直接勾選篩選
其他自訂標籤群組由各商店在後台自行建立的標籤分類，例如材質、風格、適用對象等是，消費者可直接勾選篩選
⚠️

常見誤解澄清：「新品」比較接近角標顯示用途，「館長推薦」比較接近一種排序方式，兩者都不是消費者直接勾選的標籤篩選項目。真正開放給消費者勾選篩選的標籤群組內容，是由各商店在後台自訂的，並非寫死在程式碼裡的固定清單。

05

多專案部署與 Config 分散

提供分類頁功能的程式碼分佈在三個獨立部署的應用程式：一個是純後端的 WebAPI，另外兩個是消費者實際瀏覽的前台網站，分別是舊版的 MobileWebMall 與新版的 MobileWebMallV2。三者各自有自己的設定檔，但共用同一份寫在共用類別庫裡的 SearchService 程式碼。

💡

重要釐清：設定檔有三份，不代表程式碼裡真的寫了三套獨立的判斷邏輯。實際讀取這個開關的程式碼只有一行，寫在共用類別庫裡，被三個應用程式各自載入、各自吃自己的設定值。

兩層 Config 來源

一開始只查了程式碼所在專案（nineyi.webstore.mobilewebmall）內附的設定檔，這份設定檔比較像是預設值或範本，並沒有針對每個市場分開設定。真正決定正式環境實際行為的，是另一個獨立維護的設定專案（nineyi.configuration），裡面針對每個市場都有各自的疊加設定檔，用來覆蓋預設值。

webstore 程式碼專案

內附的設定檔只有單一份 Prod 設定，沒有市場別差異，比較像是基準版本。

configuration 設定專案

針對每個市場（台灣、香港、馬來西亞、菲律賓、其他）都有獨立的疊加設定檔，才是實際部署到正式環境的真實內容。

追查教訓

只查程式碼所在的 repo 容易漏掉正式環境的真實設定，需要同時查證兩個來源才能下結論。

06

HK 市場設定異常發現

實際查詢 nineyi.configuration 內每個市場的正式環境設定檔後，發現一個跟預期不同的結果。

應用程式台灣香港馬來西亞菲律賓其他市場
WebAPI啟用關閉啟用啟用啟用
MobileWebMall啟用啟用啟用啟用啟用
MobileWebMallV2啟用啟用啟用啟用啟用
🔎

唯一特例：只有 WebAPI 這個應用程式在香港市場把快取關閉，其餘所有應用程式、所有市場都是啟用狀態。這代表香港市場的設定並非全面關閉，而是三個應用程式當中只有一個關閉，形成一個跨應用程式不一致的組合。

這個發現帶出下一個必須追查的問題：三個應用程式各自的設定不一致，消費者實際瀏覽分類頁時，體驗到的到底是哪一種行為，需要找出真正承載這個功能的呼叫路徑。

07

實際觸發路徑分析

要回答香港市場最終是啟用還是關閉，不能只看單一應用程式的設定值，必須追查消費者瀏覽器實際發出的請求，究竟打到哪一個應用程式。

1
前端網頁載入分類頁

不論消費者使用舊版或新版前台網站，畫面上顯示的分類頁外殼都是各自網站自己產生的。

2
瀏覽器發出資料查詢請求

消費者捲動、換頁、勾選篩選標籤時，瀏覽器端的程式會發出一個網路請求去要商品清單資料，這個請求的目標網址是由一個共用的網址工廠決定的，指向獨立部署的 WebAPI 應用程式，而不是前台網站自己的伺服器端程式。

3
WebAPI 處理請求並讀取自己的設定

WebAPI 收到請求後，用自己載入的 SearchService 實例處理，讀取的是 WebAPI 自己的設定值，也就是香港市場關閉快取的那一份。

✅

結論：消費者真正瀏覽、捲動、篩選商品清單這個高流量互動，不論走舊版或新版前台網站，最終都是由 WebAPI 承載，因此香港市場目前的真實行為是快取關閉，每次瀏覽都直接呼叫搜尋服務，並非快取啟用。

新版前台自己讀取設定的例外情況

新版前台網站的伺服器端程式裡，確實有一處直接使用自己載入的 SearchService，讀取的是新版前台自己的設定值，也就是啟用快取的那一份。但這一處只用在網頁初次載入時，產生搜尋引擎優化用的預覽圖片，只抓取前五筆商品資料，並不是消費者實際捲動、換頁、篩選時使用的清單資料來源，影響範圍非常有限。

⚠️

追查方法提醒：設定檔有三份不代表要分別下三個結論，必須找出實際承載主要功能的呼叫路徑，再判斷該路徑讀取的是哪一份設定，才能得到正確答案。
