# Config Drift 比對邏輯完整解析

## 01 這份文件在談什麼

公司內部多個服務（例如 `Shopping-Service`、`Cart-Service`）在 TW、HK、MY 三個市場各自維護一份設定檔，放在 GitLab repo 裡。這些設定檔理論上除了少數市場專屬欄位以外，其餘的 key 應該要三邊都存在，只是允許數值不同（例如 TW 用一組網域、HK 用另一組網域）。但實際維運中常常發生某個工程師只改了 TW 的設定檔，卻忘記同步到 HK 或 MY，導致某個功能在其他市場悄悄壞掉卻沒人發現。`Config Monitor Worker` 就是為了解決這個問題而建立的每日排程程式：每天自動去 GitLab 抓三個市場的設定檔，做兩種比對，再把結果整理成一則 Slack 通知送到頻道。

技術重點：.NET 10 Worker Service、GitLab API、Slack Block Kit 通知、每日排程巡檢。

白話版本：可以把這支程式想成一個每天固定時間巡邏的稽核員。它不管設定檔的值是什麼意思，只在乎兩件事：「今天跟昨天比，有沒有東西被偷偷加上去或拿掉」，以及「今天這一刻，三個市場彼此比較，有沒有誰漏設了某個項目」。

三個核心動作：

1. **跨環境缺漏比對**：同一天，把 `TW`／`HK`／`MY` 三份設定檔互相比較，找出哪個市場漏設了其他市場都有的項目。
2. **今日新增／刪除比對**：同一個市場，把「今天抓到的內容」跟「昨天存下來的內容」比較，找出今天新增或刪除了哪些設定項目。
3. **白名單排除**：部分項目本來就設計成只有某些市場才需要，這類已知差異會被排除，不列入每天的告警。

## 02 整體巡檢流程

巡檢以「一個要比對的服務」為單位重複執行，設定檔內容統稱 `CompareGroup`，例如 `Shopping-Service-API`、`Cart-Service-API` 各自是一個 `CompareGroup`，底下各自綁定一個 GitLab repo 與 TW／HK／MY 三個檔案路徑。

流程四階段：

1. 讀取設定檔：依序抓 TW / HK / MY 檔案，失敗則記錄錯誤原因。
2. 攤平內容：把巢狀 JSON 展開成一維字典，逐一市場處理。
3. 新增／刪除比對：與昨日快照比對差集，存回今日內容作為新基準。
4. 跨環境缺漏比對：至少兩個市場成功才進行，套用白名單後彙整結果。

決策點一：單一市場的檔案這次讀取成功嗎？
- 是：攤平內容，並拿去跟該市場昨天的快照比對新增／刪除，比對完後用今天的內容覆蓋快照，成為明天的比對基準。
- 否：記錄一筆讀取失敗（含錯誤訊息），該市場快照維持不動，不會被不完整的資料覆蓋。

決策點二：這個服務本次成功抓到的市場數量達到 2 個以上嗎？
- 是：才進行跨環境缺漏比對，找出各市場之間互相缺少的設定項目。
- 否：跳過本次跨環境缺漏比對，只留下讀取失敗的紀錄，避免用不足兩個市場的資料做出沒有意義的比較。

待觀察：「新增／刪除比對」與「跨環境缺漏比對」是各自獨立執行的兩段邏輯，讀取失敗只會讓跨環境比對被跳過，不會影響已經成功的市場照常進行新增／刪除比對。

## 03 攤平：把巢狀設定變成一維字典

兩種比對邏輯都建立在同一份「攤平後的 key/value 字典」之上，攤平是整個機制的地基，先理解這一步才能理解後面兩種比對為什麼可以簡化成集合運算。

1. **物件會展開成路徑**：JSON 物件的每個屬性會遞迴往下展開，用小數點串接路徑，例如巢狀屬性 `A` 底下的 `B` 會變成一個 key 叫 `A.B`。
2. **其餘型別一律當葉節點**：陣列、字串、數字、布林、`null` 都不再往下展開，直接把原始 JSON 文字存成該 key 的值，用於比對與顯示。
3. **陣列刻意不展開索引**：如果把陣列每個項目也展開成 `A.0`、`A.1` 這種索引 key，陣列項目順序不同就會被誤判成新增或刪除，所以陣列整體視為一個葉節點。

範例對照：

| 攤平前（原始 JSON 片段） | 攤平後（一維字典） |
|---|---|
| `{ "A": { "B": 1, "C": [1,2] } }` | `A.B = "1"`，`A.C = "[1,2]"` |

這一步的意義：把「巢狀結構比對」簡化成「單層 key/value 集合的集合運算」，後面兩種比對本質上都只是同一份攤平字典在不同維度上做聯集或差集。

## 04 跨環境缺漏比對

在同一天這個時間點上，把 `TW`／`HK`／`MY` 三份攤平字典放在一起比較，核心邏輯是「聯集加上逐一檢查成員是否存在」。

流程：取三個市場 key 的聯集 → 逐一檢查每個 key 在各市場是否存在 → 任一市場缺少就記一筆缺漏。

1. **取聯集**：把 TW、HK、MY 三個攤平字典的所有 key 合併去重，得到「理論上應該存在的所有 key」清單。
2. **逐一檢查存在性**：對聯集中每個 key，分別檢查 TW、HK、MY 三個字典裡有沒有這個 key，並記錄哪些市場有值、哪些市場沒有。
3. **只要有一個市場缺少就成立**：只要任一市場沒有這個 key，就判定為缺漏，輸出一筆結果，包含各市場實際的值以及缺少的市場清單。

例外情況：三個市場都有這個 key，但數值彼此不同，不算異常。只要三個市場都設定了這個 key，就算合理的市場差異（例如各自網域不同），不會出現在缺漏結果中。這套機制比對的是「有沒有設定」，不是「設定的值是否一致」。

已完成：比對結果最後會依 key 的英文字母排序輸出，並附上白名單過濾（見第 06 章），避免已知差異每天重複告警。

## 05 今日新增／刪除比對

針對同一個市場，把「今天攤平出來的字典」跟「昨天存下來的快照字典」相比，本質是兩個時間點快照之間的差集運算，跟第 04 章的跨市場聯集是完全不同維度的比對。

運算公式：
- 今天字典 減去 昨天快照 = 今日新增的 key
- 昨天快照 減去 今天字典 = 今日刪除的 key

決策點：這個市場有前一次快照可以比較嗎？
- 是：正常執行差集比對，找出今日新增與今日刪除的 key。
- 否：代表是第一次執行、尚無比對基準，一律回傳空清單，只建立今天的內容作為未來比對用的基準，不會把既有的所有設定都誤判成新增。

補充規則：

- 比對範圍限定在同一個市場，不會拿 TW 今天的內容去跟 HK 昨天的內容比。
- 只有本次成功讀取的市場才會比對並更新快照。
- 讀取失敗的市場，快照保留原樣，不用不完整的內容覆蓋既有基準。
- 比對完成後，無論有沒有發現新增或刪除，都會用今天的內容重新存一次快照，作為明天的比對基準。

## 06 白名單排除機制

部分設定項目本來就是設計成只有某些市場需要，例如某個東南亞地區專屬的運費區域設定，這種缺漏並非疏漏，而是刻意的市場差異，若每天都告警反而會讓工程師開始忽略通知。

1. **設定層級是每個服務各自獨立**：白名單掛在 `CompareGroup` 底下，也就是每個 repo／服務各自維護自己的排除清單，不會互相影響。
2. **比對方式是完全字串相等**：用大小寫敏感的完整字串比對排除清單裡的 key，不是模糊比對或前綴比對。
3. **在跨環境比對完成後才過濾**：先照第 04 章的邏輯找出全部缺漏，再把出現在白名單裡的 key 從結果中移除，並記錄本次排除了幾筆，方便追蹤白名單實際生效狀況。

待觀察：白名單只影響「跨環境缺漏比對」，完全不影響「今日新增／刪除比對」。如果白名單裡的某個 key 今天被刪除了，仍然會照常出現在今日刪除清單中，因為那是兩種不同的比對邏輯。

## 07 兩種比對邏輯的本質差異

雖然都建立在同一份攤平字典上，跨環境缺漏比對與今日新增／刪除比對其實是兩個完全正交、互不影響的比對維度。

| 比對項目 | 比對對象 | 核心運算 | 是否比對數值本身 |
|---|---|---|---|
| 跨環境缺漏比對 | 同一天，`TW`／`HK`／`MY` 之間互相比較 | key 聯集後逐一檢查存在性 | 否，只比對有沒有設定 |
| 今日新增／刪除比對 | 同一市場，今天與昨天兩個時間點比較 | key 集合的差集運算 | 否，只比對 key 是否存在，值只是附帶記錄 |

共用地基是攤平字典；橫向維度是跨市場聯集；縱向維度是今昔差集。

白話總結：這整套機制從頭到尾都只在乎「有沒有這個設定項目」，完全不管「設定的內容是什麼意思」。把巢狀 JSON 攤平成一維的 key 清單之後，橫向去比三個市場的 key 有沒有缺，縱向去比今天跟昨天的 key 有沒有變化，兩件事各自算各自的，最後才把兩種結果彙整起來，一起送進同一則 Slack 通知。

## 08 通知呈現：以 Repo 為主軸

比對邏輯算出來的結果最終會交給 Slack 通知模組整理成訊息，呈現方式的設計原則是「每個服務只出現一次，狀態逐項列清楚」，避免同一個服務的資訊分散在不同區塊、或某個服務因為沒有異動而完全消失看不見。

**某服務完全沒有異動時：**
- 顯示服務名稱加上「檢查完成」。
- 底下逐項列出：無 `config` 新增、無 `config` 移除、無 `config` 缺漏。

**某服務有部分異動時：**
- 有資料的項目（例如缺漏）逐筆列出明細，跨環境缺漏會用市場並排的方式呈現每個 key 在各市場的實際數值。
- 沒有資料的項目（例如當天沒有新增）仍然要顯示「無 `config` 新增」，不會因為缺漏區塊有內容就把新增／移除區塊整段省略。

已完成：只有讀取設定檔真的失敗時，才會額外顯示一個「取得狀態」區塊說明哪個市場失敗、失敗原因是什麼，避免每天都顯示一次「全部成功」造成洗版。
