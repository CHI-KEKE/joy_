DI 設定（QFPayModule）

使用 Refit + Polly WaitAndRetry 做 HTTP 重試，retry 次數與間隔由 config 控制。

// QFPayModule.Register()
services.AddPaymentMiddlewarePlugins<QFPayPlugin>();
services.AddScoped<IClientFactory, ClientFactory>();

services.AddRefitClient<IQFPayHttpClient>()
  .AddHttpMessageHandler<RawResponseMessageLoggingDelegatingHandler>()
  .AddTransientHttpErrorPolicy(b =>
      b.WaitAndRetryAsync(retryCount, _ => TimeSpan.FromMilliseconds(retryInterval)));

// Config Keys
"_N1CONFIG:Plugins:QFPay:HttpClient:RetryCount"
"_N1CONFIG:Plugins:QFPay:HttpClient:RetryInterval"
"_N1CONFIG:Plugins:QFPay:HttpClient:BaseUrl"

💳 付款流程（Pay）

📌 核心設計：Hosted Payment Page（付款頁面型）
QFPay 採用 PayPage 模式。PaymentMiddleware 不直接向 QFPay 發送付款 API，而是產生一個帶有簽名的 URL， 把 Consumer 重導向到 QFPay 的托管付款頁面。付款完成後由 QFPay 非同步 Notify 或由 ReCheck Job 主動查詢。

付款流程步驟

1
SMSCart 呼叫 POST /api/v1.0/Pay/QFPay/{TGCode}
帶入 X-Api-Key、X-Api-Code Header，Body 含金額、幣別、ExtendInfo（ReturnUrl、FailedUrl、NotifyUrl 等）
2
組裝 QFPayCreatePaymentRequestEntity
AppCode, SignType, PaySource="91App_checkout", TxAmt(×100), CurrencyCode, out_trade_no(TGCode), txdtm, return_url, failed_url, notify_url, goods_name, lang, expired_time…
3
GetPayloadToDictionary() → 依 JsonPropertyName 反射所有屬性，按 Key 字母排序
null / 空值欄位在後續 GetPayloadString 中會被過濾排除
4
GenerateSha256Signature(payloadString_未UrlEncode, apiKey)
簽名只用未 URL Encode 的字串進行；URL 中的 payload 則使用 UrlEncoded 版本
5
回傳 PaymentResponseEntity：Action = Redirect，WebPaymentUrl = payPageUrl + &sign=xxx
ReturnCode = WaitingToPay，TransactionId = 空字串（付款頁面型，尚未取得）

Pay 請求參數（QFPayCreatePaymentRequestEntity）

欄位（json_key）說明必填
appcodeQFPay 分配的 API 憑證（X-Api-Code）必填
sign_type固定 "sha256"必填
paysource固定 "91App_checkout"必填
txamt付款金額（×100，單位分）必填
txcurrcd幣別（如 HKD）必填
out_trade_noTGCode（最長128）必填
txdtm訂單時間（yyyy-MM-dd hh:mm:ss）⚠️ hh 格式 Bug必填
return_url付款成功重導向必填
failed_url付款失敗重導向必填
notify_url非同步 Webhook 通知 URL選填
mchntid代理商商戶 ID選填
goods_name商品名稱（不得含特殊字符）選填
txzone時區（預設 +0800）選填
expired_timeQRCode 到期（分鐘，5~120）選填
checkout_expired_time結帳到期（毫秒）選填
langUI 語言（zh-hk / zh-cn / en）選填

🔍 查詢流程（QueryPayment）

1
POST /trade/v1/query
傳入 out_trade_no（TGCode） 或 syssn（TransactionId）；支援分頁（Page, PageSize 最大100）
2
驗證 apiResponse.ResponseCode == "0000"
非 0000 → throw ApplicationException（無區分錯誤類型）
3
篩選成功付款紀錄
OrderType == "payment" && ResponseCode == "0000" && TradeOrderCode == OrderCode 取最早一筆（OrderBy TransactionId）
4
SuccessCount 計算
統計同一 TG 成功付款筆數，若 > 1 → ExtendInfo 中帶回 SuccessCount，Payment Console Alert 告警
5
Fallback 邏輯
若無成功付款紀錄 → 取任一筆符合 TradeOrderCode 的紀錄作為 orderData；ReturnCode = WaitingToPay

Query 請求參數（QFPayQueryRequestEntity）

欄位說明備注
syssnQFPay 交易編號與 out_trade_no 擇一
out_trade_noTGCode 或 TSCode
pay_type支付類型篩選（逗號分隔）選填
respcd回應碼篩選選填
start_time / end_time時間區間查詢跨月查詢必填；提供 syssn/out_trade_no 時忽略
page / page_size分頁（最大頁碼 8，最大 100 筆）選填

🔄 退款流程（Refund）

1
POST /trade/v1/refund
傳入 syssn（原交易 TransactionId）、out_trade_no（TSCode）、txamt（退款金額 ×100）、txdtm（退款時間）
2
Response Code Switch 轉換 ReturnCode
依 QFPay ResponseCode 轉換為 PaymentMiddleware ReturnCode（見下表）
3
FPS 特殊處理
若 apiResponse.ResponseDescription 包含中文字串 "該筆訂單被禁止退款，已經超出可退款時限" → 強制設為 Failed（FPS 只能退 29 天內的交易）

❌ 取消流程（Cancel）

1
POST /trade/v1/reversal（撤銷）
注意：是 reversal（撤銷），而非一般 cancel API。用於同日交易撤銷。
2
傳入參數：syssn, out_trade_no, txamt（×100）, txdtm（交易時間）, udid
TransactionDatetime 同樣有 hh 格式 Bug
3
Response Code == "0000" → Success；其他 → Failed
Cancel 的回應判斷比退款簡單，只有 Success / Failed 兩種

🔐 簽名機制（SHA256）

1
反射 Request Entity 所有屬性，以 JsonPropertyName 取得 json key
2
過濾 null / empty 欄位
3
依 Key 字母排序（A→Z） 組成 key=value&key=value&...
4
不做 URL Encode（簽名用 raw string）；URL 中的 payload 才做 URL Encode
5
SHA256(payloadStringWithoutEncode + apiKey) → hex lowercase
6
Query/Refund/Cancel：X-QF-SIGN: {signature} in Header
Pay：附加在 URL query string &sign={signature}
// GenerateSha256Signature
private static string GenerateSha256Signature(string data, string apiKey)
{
    using var sha256 = SHA256.Create();
    byte[] hash = sha256.ComputeHash(Encoding.UTF8.GetBytes($"{data}{apiKey}"));
    return Convert.ToHexString(hash).ToLower();
}

// QFPay API Header
{
  "Content-Type": "application/x-www-form-urlencoded",
  "X-QF-APPCODE": apiCode,
  "X-QF-SIGN": signature,
  "X-QF-SIGNTYPE": "SHA256"
}

⚠️ 缺點分析

CRITICAL 時間格式 Bug：hh（12小時制）應為 HH（24小時制）

Pay、Refund、Cancel 三個流程都有相同 Bug：

// ❌ 錯誤：hh 是 12小時制，下午時間會錯
OrderDatetime = extendInfo.OrderDateTime.ToString("yyyy-MM-dd hh:mm:ss");
EventDatetime = extendInfo.RequestDatetime.ToString("yyyy-MM-dd hh:mm:ss");
TransactionDatetime = extendInfo.TransactionDatetime.ToString("yyyy-MM-dd hh:mm:ss");

// ✅ 正確：HH 是 24小時制
OrderDatetime = extendInfo.OrderDateTime.ToString("yyyy-MM-dd HH:mm:ss");

HK 下午 13:00~23:59 的交易，傳給 QFPay 的時間會變成 01:00~11:59，導致 QFPay 可能驗證失敗或交易時間記錄錯誤。

全部改為 HH（大寫）24小時制格式。影響檔案：QFPayPlugin.cs 中 Pay、Refund、Cancel 三處。

HIGH Pay 流程無 Webhook 接收：依賴 NotifyUrl（非必填）或 ReCheck Job

QFPay 的 notify_url 在 ExtendInfo 為選填，若上游沒傳入，付款完成後 PaymentMiddleware 不會收到任何通知。 系統需仰賴定時 ReCheck Job 主動查詢付款狀態，造成付款完成到系統確認之間有時間延遲。

Pay 回傳的 TransactionId 永遠是空字串，後續的 Query 必須靠 TGCode 查詢，無法以 TransactionId 快速定位。

強制要求 NotifyUrl 必填（移到必填欄位），並在 QFPay 呼叫前做 validate。

HIGH QueryPayment 無法區分「未付款」與「付款失敗」

當查無成功付款紀錄時，系統一律回傳 ReturnCode = WaitingToPay。 但 QFPay 的 Data 陣列可能包含 Failed 狀態的記錄，目前代碼無法分辨訂單是「還在等待付款」還是「已經付款失敗」。 導致 ReCheck Job 可能對一筆已失敗的訂單持續重試查詢。

// 現在的判斷：所有非成功一律 WaitingToPay
var responseCode = orderData != null && orderData?.ResponseCode == "0000"
    ? ReturnCodes.Success
    : ReturnCodes.WaitingToPay; // ← 無法區分 Failed

增加 Failed 狀態判斷：若 orderData.ResponseCode 不為 null 且不是 Pending 狀態 Code，則回傳 ReturnCodes.Failed。

MEDIUM RefundQuery 未過濾 OrderType == "refund"

QueryPayment 正確過濾了 OrderType == "payment"，但 RefundQuery 共用同一個 /trade/v1/query API， 卻只用 TradeOrderCode == OrderCode 過濾，未加 OrderType == "refund"。

這導致退款查詢可能取到付款紀錄而非退款紀錄，造成 ReturnCode 判斷錯誤。

// ❌ RefundQuery 缺少 OrderType 過濾
var orderData = apiResponse.Data
    .FirstOrDefault(i => i.TradeOrderCode == extendInfo.OrderCode); // 缺 && i.OrderType == "refund"

加上 && i.OrderType == "refund" 過濾條件。

MEDIUM GetPayloadToDictionary 使用反射，效能較差且欄位順序依賴屬性宣告順序

每次簽名都使用反射（GetType().GetProperties()）取得屬性並排序。 雖然透過字母排序確保順序一致，但反射本身有效能損耗，且若未來新增繼承或 interface 屬性可能有意外行為。

另外，null 值屬性會先轉成空字串再過濾，代表邏輯分散在兩個方法中，不夠內聚。

考慮緩存反射結果或改用 Source Generator 方式；或將過濾邏輯統一移入 GetPayloadToDictionary。

MEDIUM IsUsingLiveTest 混入 Request ExtendInfo（環境設定應與請求資料分離）

每個 ExtendInfo Entity 都有 IsUsingLiveTest 欄位，由呼叫端傳入決定要打正式環境還是 Live Test 環境。 這是典型的環境設定（infrastructure concern）混入業務資料（request payload）的設計問題。

理想的設計應由商店層級的設定（如 ShopStaticSetting 或 ShopSecret）決定環境，不應由 caller 動態傳入。

將環境判斷移到 Plugin 初始化層，依 ShopId 或 API Key 的 env 前綴判斷，從 ExtendInfo 移除 IsUsingLiveTest。

MEDIUM FPS 退款限制靠中文字串比對：脆弱且易壞

當 QFPay 回傳 1265 且為 FPS 超出退款時限時，判斷邏輯依賴：

apiResponse.ResponseDescription.Contains("該筆訂單被禁止退款，已經超出可退款時限")

若 QFPay 修改回應訊息（更新措辭、語系、標點符號），這個判斷會直接失效，導致 FPS 超期退款被誤判為 RefundPending 而持續重試。

向 QFPay 確認是否有更穩定的 sub-code 或錯誤碼可識別此情境，改用 code-based 判斷取代字串比對。

LOW QueryPayments 未實作（NotImplementedException）

IQueryable 介面的 QueryPayments（複數查詢）方法直接 throw NotImplementedException， 若有任何上層邏輯誤呼叫此方法會造成 500 錯誤。

如確認不需要實作，改 return 空集合或加明確的 TODO 說明；或從 Interface 實作中移除。

LOW SuccessCount > 1 只記錄 Alert，無自動防呆機制

當同一 TGCode 有多筆成功付款記錄時（SuccessCount > 1），目前只靠 Payment Console Alert 通知商家協助退款， 系統不會自動阻擋或觸發退款流程。這在網路重試場景下可能造成多扣款。

增加自動觸發退款的保護機制，或在偵測到 SuccessCount > 1 時直接回傳 Failed 阻止後續流程。

LOW 無 Circuit Breaker，僅有 Retry

QFPayModule 只配置了 Polly WaitAndRetry Policy，沒有 Circuit Breaker。 當 QFPay 服務異常時，系統會持續重試所有請求，可能對 QFPay 造成不必要的壓力，也延長每筆請求的 timeout。

搭配 AddCircuitBreakerPolicy 使用，在連續失敗達閾值時暫停呼叫。

1

QFPay 整體串接架構清晰，採用 Hosted PayPage 模式、Refit 作為 HTTP Client、Polly 做 Retry，符合 PaymentMiddleware 的 Plugin 規範。
最需要立即修正的是 時間格式 Bug（hh→HH），這會影響所有 HK 下午時段的付款、退款、取消交易。
其次建議補強 RefundQuery 的 OrderType 過濾 與 QueryPayment 的 Failed 狀態區分， 避免查詢結果誤判導致 ReCheck Job 重複執行。
