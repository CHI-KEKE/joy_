⚠️ Cybersource QueryPayment 慢速回應異常紀錄

📅 發現日期：2026-07-01 🏷 金流：Cybersource（透過 PaymentMiddleware） 🌐 市場：HK 📌 狀態：待優化
🔴 問題描述
🚨
消費者完成 Cybersource 信用卡付款後被轉導回 mweb，mweb 向 PMW 查詢付款狀態時， 因 Cybersource API 回應極慢，導致 mweb 端的 HTTP 請求在 30 秒 timeout 前無法拿到結果， 整條 PayChannelReturn 鏈路斷掉，訂單無法即時完成。 只能等待 下一次 ReCheck Job（約 3 分鐘後） 重新補查，且同樣依賴 Cybersource 當下的回應速度。

現象

  • 消費者按下付款 → Cybersource 頁面付款成功 → 被導回 mweb
  • mweb 的 PayChannelReturn action 回應時間超過 30 秒
  • 使用者看到「訂單處理中」或被導向訂單列表，無法立即看到成功頁
  • 訂單狀態停在 WaitingToPay，需等 ReCheck Job 補完
  • 若 ReCheck 當下 Cybersource 同樣緩慢，需等更多輪才能完成
🔗 完整鏈路說明

路線一：正常付款回調（PayChannelReturn）

1
消費者在 Cybersource Hosted Page 完成付款
Cybersource 將 Form POST 導回 mweb 的中繼頁 /V2/PayChannel/CreditCardOnce/Cybersource/{tgCode}
2
mweb 解析 Form Data，取得 TGCode + UniqueKey
CybersourcePayChannelService.ProcessResponseFormAfterPayment()
取得 req_reference_number（TGCode）及 req_transaction_uuid（UniqueKey）
3
導向 PayChannelReturn Action
PayChannelController.PayChannelReturn()
呼叫 TradesOrderPaymentService.FinishPayment(isFromWorker: false)
4
呼叫 PMW 查詢付款狀態 ← 瓶頸點
PaymentMiddlewareService.QueryPayment()
→ PaymentMiddlewareHttpClient.Query()
→ POST PMW /api/v1.0/QueryPayment/CreditCardOnce_Cybersource
→ PMW 呼叫 Cybersource API 查詢交易狀態

⚠️ HttpClient.Timeout = 30 秒（ServiceModule.cs 設定）
5a
【異常路徑】Cybersource 回應慢 → 30 秒 Timeout 觸發
HttpClient 拋出 TaskCanceledException
→ catch (Exception ex) 捕捉後回傳 PaymentStatusDefEnum.Fail
→ FinishPayment() 拋出例外或回傳錯誤
→ PayChannelController 的 catch (Exception ex) 處理
→ 使用者被導向「訂單處理中」頁面
→ 訂單維持 WaitingToPay
5b
【正常路徑】PMW 在 30 秒內回傳結果
依 ReturnCode 分流：
Success → 訂單完成，導向付款成功頁
Failed → 訂單取消
Expired → 訂單逾時取消
WaitingToPay → 訂單留 WaitingToPay，等 ReCheck

路線二：ReCheck Job 補查（isFromWorker: true）

1
SQL Job 每 3 分鐘觸發一次
撈取 TradesOrderThirdPartyPayment.Status = WaitingToPay（3 天內）
為每個 PayType 建立 NMQ Task
2
NMQ Job 執行 ThirdPartyPaymentReCheckProcess
PaymentMiddlewareReCheckService.OrderReCheck(payment)
組裝 InternalFinishPaymentRequestEntity → POST mweb /Internal/FinishPayment
3
mweb 內部呼叫 FinishPayment（isFromWorker: true）← 同樣的瓶頸
走相同路徑：TradesOrderPaymentService.FinishPayment()
→ PaymentMiddlewareService.QueryPayment()
→ PMW → Cybersource

⚠️ 若 Cybersource 仍然緩慢，同樣會 Timeout
只能等下一輪 ReCheck（再等 3 分鐘）
4
Cybersource 回應速度恢復正常時
PMW 拿到 Success → ReCheck 路徑成功完成訂單
Thread.Sleep(250ms) 批次流控後繼續處理下一筆

⚠️
與 mweb 前台路徑的關鍵差異：
前台 PaymentMiddlewareService.RequestPayment() 有 catch (Exception ex) 會寫 logger.Error， WebAPI 的 QueryPayment() 路徑完全沒有對應的 exception 攔截與 log。 這使得 WebAPI 路徑的 timeout 是完全靜默的， 只能從 Log 在 GetRequestId 之後突然中斷來間接判斷。
📊 影響分析
影響面 描述 嚴重度
使用者體驗 付款成功後看不到成功頁，被導向訂單列表，誤以為付款失敗，可能重複嘗試 高
訂單完成延遲 最快需等 3 分鐘（一次 ReCheck），若 Cybersource 持續緩慢可能延遲更久 中
重複付款風險 若使用者因看不到成功頁而重新下單，可能導致重複扣款（由 DuplicateRequest 機制保護，但仍有視窗期） 中
mweb Thread 佔用 每個請求佔用 ASP.NET Thread 長達 30 秒，高峰期若大量並發可能造成 Thread Pool 壓力 中
ReCheck 堆積 Cybersource 緩慢期間，WaitingToPay 訂單堆積，ReCheck 批次量增加 中
資料一致性 Cybersource 端已扣款但 mweb 不知道，依賴 ReCheck 補齊；不存在資料不一致，只是延遲 低
🕐 時序：正常 vs 異常
✅ 正常路徑（Cybersource 回應快）
  1. 使用者完成付款 → 導回 mweb
  2. PayChannelReturn 接到 callback
  3. POST PMW /QueryPayment/CreditCardOnce_Cybersource
  4. PMW 查 Cybersource → 10 秒內回傳 Success
  5. 訂單完成，導向付款成功頁
  6. 使用者立即看到成功畫面 🎉
❌ 異常路徑（Cybersource 回應慢）
  1. 使用者完成付款 → 導回 mweb
  2. PayChannelReturn 接到 callback
  3. POST PMW /QueryPayment/CreditCardOnce_Cybersource
  4. PMW 等待 Cybersource → 超過 30 秒無回應
  5. TaskCanceledException → 回傳 Fail
  6. 使用者被導向「訂單處理中」
  7. 等 3 分鐘 → ReCheck Job 觸發
  8. 再次 POST PMW Query → 若 Cybersource 仍慢 → 再等下一輪
  9. Cybersource 恢復正常 → 訂單補完成
🔍 根本原因分析
架構設計：同步等待第三方回應
mweb 的 PayChannelReturn 是同步 HTTP 請求，必須在 Response 回傳前完成所有查詢與訂單處理。 這使得整條鏈路的等待時間受 Cybersource 回應速度直接影響。
HttpClient Timeout 固定 30 秒，無法針對 Cybersource 個別設定
PaymentMiddlewareHttpClient 的 HttpClient 為所有 PayChannel 共用一個 30 秒 Timeout， 無法為 Cybersource 設定更長的等待時間（或更短以快速 fallback）。
Cybersource 第三方 API 本身回應不穩定
Cybersource 的查詢 API 在特定時段（高峰 / 維護 / 網路抖動）回應時間超過 30 秒， PMW 無法在 mweb 的 timeout 窗口內拿到結果並回傳。
ReCheck 是唯一的救援路徑，且同樣依賴 Cybersource 速度
ReCheck Job 走的是相同的 PMW Query 路徑。 Cybersource 若持續緩慢，需要多輪 ReCheck 才能完成，每輪間隔至少 3 分鐘。
🛠 改善方向（參考）
📌
以下為可行的改善方向，尚未實作，供後續評估參考。
方向 說明 難度 效果
縮短 mweb → PMW Timeout，更快進入 ReCheck 流程 目前 30 秒才觸發 fallback。若改為 10 秒，能更快釋放 mweb Thread， 讓使用者更快看到「訂單處理中」畫面（雖然體驗不完美，但比 hang 30 秒更好） 低 部分改善體驗
縮短 ReCheck 間隔（特定 PayType） 若採用「每個 PayType 獨立 CronJob」架構，可讓 Cybersource 的 ReCheck 每 1 分鐘跑一次， 縮短訂單完成延遲 中 縮短延遲
PayChannelReturn 改為非同步：先回應使用者，後台補查 Cybersource callback 進來後，立即導向「訂單確認中」頁，非同步呼叫 PMW Query， 不等第三方回應就先釋放使用者端。前端輪詢訂單狀態直到完成。 高 根本改善體驗
監控 Cybersource Query 回應時間 在 PMW 或 mweb 層加入 Cybersource Query API 的 P99 回應時間監控， 當超過閾值時主動告警，快速確認是 Cybersource 側問題還是網路問題 低 提升可觀測性

📋

🎯
判斷依據：若 P99 耗時 ≥ 30 秒，且集中在特定時段，可判定為 Cybersource 第三方 API 在該時段回應異常緩慢，非 mweb / PMW 本身問題。

輔助判斷：在 Grafana 搜尋 "FinishPayment parameters" 後的 Log， 若接著出現的是 "Internal Finish Payment" 的下一筆請求（即同一筆訂單沒有後續 Log）， 且 沒有出現 "QueryPayment - RequestId" 這行， 則可確認是 QueryPayment HttpClient 呼叫掛住後 timeout，Log 在此靜默斷掉。

Step 2 — 確認 DB 目前資料更新狀況

直接查 TradesOrderThirdPartyPayment 確認異常時段內有多少筆訂單卡在 WaitingToPay，以及是否有更新中的狀態。

-- 查詢異常時段內的 Cybersource WaitingToPay 訂單
SELECT
    TradesOrderThirdPartyPayment_TradesOrderGroupId,
    TradesOrderThirdPartyPayment_TypeDef,
    TradesOrderThirdPartyPayment_StatusDef,
    TradesOrderThirdPartyPayment_DateTime,          -- 付款建立時間
    TradesOrderThirdPartyPayment_StatusUpdatedDateTime,  -- 最後狀態更新時間
    DATEDIFF(MINUTE,
        TradesOrderThirdPartyPayment_DateTime,
        GETDATE()) AS MinutesSinceCreated
FROM dbo.TradesOrderThirdPartyPayment WITH (NOLOCK)
WHERE TradesOrderThirdPartyPayment_TypeDef LIKE '%Cybersource%'
  AND TradesOrderThirdPartyPayment_StatusDef = 'WaitingToPay'
  AND TradesOrderThirdPartyPayment_DateTime >= '2026-07-01 00:00:00'  -- 換成異常日期
  AND TradesOrderThirdPartyPayment_ValidFlag = 1
ORDER BY TradesOrderThirdPartyPayment_DateTime DESC;

MinutesSinceCreated 多在 5 分鐘內被 ReCheck 處理完 有訂單停留 10+ 分鐘仍未更新

Step 4 — 判斷規則：Query 耗時過長 → WaitingToPay 的對應關係

根據鏈路設計，可以用以下規則快速判斷訂單的最終狀態：

PMW Query 耗時 mweb 端行為 訂單最終狀態 判斷
< 30 秒 正常取得 ReturnCode 依 ReturnCode 決定（Success / Fail / Timeout） 正常
≥ 30 秒（timeout） TaskCanceledException → Fail 回傳 WaitingToPay（等 ReCheck） 等 ReCheck
≥ 30 秒（每輪 ReCheck 都 timeout） 每輪 ReCheck 都拋例外 持續 WaitingToPay，每次 ReCheck 都失敗 持續異常
某輪 ReCheck < 30 秒 ReCheck 成功取得 Success 訂單補完成 ReCheck 補回
⚠️
重要結論：只要在 Grafana 看到某筆訂單的 PMW QueryPayment 耗時 ≥ 30 秒（或看到 TaskCanceledException Log）， 可以直接判定該訂單在 PayChannelReturn 時沒有成功更新， 訂單狀態一定是 WaitingToPay，需等 ReCheck 或手動觸發補查。

方案 改動範圍 解決的問題 優先級

🔴 Fix 1：InternalFinishPayment 加 try-catch（只動 Controller）

目前 WebAPI/Controllers/PayChannelController.InternalFinishPayment 完全沒有 try-catch， TaskCanceledException 一路往上噴到 ASP.NET MVC framework，造成 HTTP 500 + ELMAH 記錄，應用層無任何 Log。

改法（只改這一個 Controller Action）：

// WebStore\WebAPI\Controllers\PayChannelController.cs

[HttpPost]
[Route("PayChannel/InternalFinishPayment")]
public ActionResult InternalFinishPayment([FromBody] InternalFinishPaymentRequestEntity request)
{
    if (!this.IsFromCompany())
        return this.Json(ApiResultEntity<object>.Success(string.Empty));

    // 解析 PayType（既有邏輯不動）
    var payType = this._payTypeResolver.Resolve(request.PayProfileType);

    try
    {
        var result = this._tradesOrderPaymentService.FinishPayment(
            request.ShopId, request.MemberId,
            payType.PayChannel, payType.PayMethod,
            request.TradesOrderGroupCode, request.UniqueKey,
            string.Empty, isFromWorker: true);

        return this.Json(ApiResultEntity<object>.Success(result));
    }
    catch (TaskCanceledException ex)
    {
        // PMW → Cybersource 超過 30 秒無回應，訂單維持 WaitingToPay 等 ReCheck
        this._logger.Warn(ex,
            $"InternalFinishPayment Timeout - OrderCode:{request.TradesOrderGroupCode}, PayType:{request.PayProfileType}");

        return this.Json(ApiResultEntity<object>.Fail("TIMEOUT", "Payment query timeout"));
    }
    catch (Exception ex)
    {
        this._logger.Error(ex,
            $"InternalFinishPayment Error - OrderCode:{request.TradesOrderGroupCode}, PayType:{request.PayProfileType}");

        return this.Json(ApiResultEntity<object>.Fail("ERROR", ex.Message));
    }
}
改善前改善後
HTTP 500，ELMAH 爆 exception HTTP 200 + TIMEOUT error code，ELMAH 不再記錄
應用層完全無 Log，靜默斷掉 logger.Warn 明確記錄是哪張訂單、哪個 PayType timeout
NMQ 拿到 500 → errorList → Task 失敗 NMQ 拿到結構化 response，可區分 TIMEOUT 與真正的錯誤
前台路徑（PayChannelReturn）不受影響 前台路徑（PayChannelReturn）不受影響（不同 Controller）

🟠 Fix 2：Timeout 依路徑分離（ReCheck 路徑給 60 秒）

為什麼不能只在 Controller 改 Timeout？

⚠️
PaymentMiddlewareHttpClient 是 singleton，HttpClient.Timeout 是 instance 層級屬性， 在 singleton 上做 per-request 修改是 non-thread-safe。 若在 Controller 暫時改 Timeout 再改回，多執行緒環境下會有 race condition。

需要的改動範圍：

// 方法：用 CancellationTokenSource 做 per-request timeout
// 需貫穿以下呼叫鏈，每個方法都要新增 CancellationToken 參數：

InternalFinishPayment(request)
  → FinishPayment(..., CancellationToken token)            // TradesOrderPaymentService.cs
    → QueryPayment(..., CancellationToken token)           // PaymentMiddlewareService.cs
      → Query(..., CancellationToken token)               // PaymentMiddlewareHttpClient.cs
        → SendHttpRequestWithJsonBody(..., token)          // PaymentMiddlewareHttpClient.cs
          → httpClient.SendAsync(request, token)          // 實際生效點

// Controller 側傳入 60 秒的 token
using var cts = new CancellationTokenSource(TimeSpan.FromSeconds(60));
var result = this._tradesOrderPaymentService.FinishPayment(..., cts.Token);
方案 Frontend PayChannelReturn WebAPI InternalFinishPayment（ReCheck） 改動範圍
不改（現狀） 30 秒 30 秒 —
統一改 60 秒 60 秒（使用者等更久） 60 秒（✅ ReCheck 有更長窗口） 只改 ServiceModule.cs 1 行，但兩條路徑都受影響
Fix 2（CancellationToken 分離） 30 秒（不變） 60 秒（✅ ReCheck 有更長窗口） 需改 4~5 個檔案的方法簽章
💡
評估前置條件：實作 Fix 2 前，建議先從 Grafana 確認 Cybersource 慢速時的實際回應時間落在哪個區間。 若 P99 普遍超過 60 秒，調整 Timeout 意義不大；若多數在 30~55 秒之間，Fix 2 能有效減少 ReCheck 失敗次數。
