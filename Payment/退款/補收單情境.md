
## Elemis SG 退款金額異常

**訂單**：MG260424N00001（PayNow_Razer）

| RefundRequest | Amount | SourceDef |
|---------------|--------|-----------|
| MS260424N000001 | **57.00** | ReturnGoodsOrderSlave |
| MS260424N000002 | 0.00 | ReturnGoodsOrderSlave（補收單） |
| MS260424N000003 | 0.00 | ReturnGoodsOrderSlave（補收單） |
| MS260424N000004 | 0.00 | ReturnGoodsOrderSlave（補收單） |
| SalesOrderFee | **5.00** | SalesOrderFee |

**Razer 實際收到**：SGD 57 + SGD 5（兩筆分開）

**原因分析**：
1. `57 = 62（商品）- 5（補收單扣抵）`→ 商品退款計算時補收單已被扣除
2. 運費 SGD5 與商品退款被不同批 Grouping Job 撈到 → 成為獨立的 Task → Razer 收到兩筆分開的退款

**消費者預期**：SGD 62 + SGD 5 = SGD 67

---

## 根本原因分析

### 補收單沒有獨立的 RefundRequest，是淨額扣抵進 ReturnGoodsOrderSlave 退款

補收單（`RechargeReceipt`）本身**不會**產生一筆屬於自己的 `RefundRequest`。它是被直接淨額扣抵進「該筆 `ReturnGoodsOrderSlave` 應退款金額」裡：

`ReturnGoodsOrderFinishService.cs`（`ProcessPaymentAllocations`，line 802-845）：
```csharp
var totalRechargeAmount = rechargeReceipt?.RechargeReceipt_RechargeAmount ?? decimal.Zero;
var totalRefundAmount = returnGoodsOrderSlave.ReturnGoodsOrderSlave_TotalPayment.Value - totalRechargeAmount;
// 62 - 5 = 57
```

也就是「一個 `ReturnGoodsOrderSlave` → 一筆（或多筆，若多付款方式）`RefundRequest`（`SourceDef = ReturnGoodsOrderSlave`）」，而補收單金額是在計算這筆 `RefundRequest` 金額時被扣掉，不是另開一張。案例中 4 筆 `ReturnGoodsOrderSlave` 退款單，其中 3 筆金額為 0，代表這 3 個商品明細列各自對應的補收單金額剛好等於或大於其退款金額，扣抵後歸零並直接結案（`RefundRequest_IsClosed = true`），只有第 4 筆扣抵後還剩 57。

### 補收單被誤用：`SalesOrderFee` 類型補收單的設計語意是「跟消費者多收運費」，不是「退運費」

先前已確認 `RechargeTypeDefEnum.SalesOrderFee` 類型補收單的正確使用情境是：**原訂單滿額免運，退貨後剩餘商品金額不再達免運門檻，需向消費者「多收」運費差額**（正值、屬於扣抵/收費性質）。

但補收單機制在計算上是「一律從退貨退款中扣除」，不管商家建立補收單的初衷是什麼。因此若商家誤以為「建立一張補收單」是達成「退運費」效果的方法，實際上是**反向操作**——扣掉的是要退給消費者的商品退款，而不是額外退還運費。

### 退運費（SalesOrderFee 退款）在「退貨」情境下必須人工手動觸發，系統不會自動處理

追蹤 `ThirdPartyRefundRequestService.CreateRefundRequestByCancelFlow`（line 263-298）後發現，系統自動判斷退運費的邏輯**只存在於「取消訂單」流程**（只被各付款方式的 `*CancelOrderService.cs` 呼叫），跟「退貨」完全無關。

而退貨結案邏輯（`ReturnGoodsOrderFinishService.cs`）本身**完全沒有**任何自動建立 `SalesOrderFee` 退款的程式碼。運費退款要靠獨立 API：

```
POST /RefundRequest/ReturnSalesOrderFee   // RefundRequestController.cs line 37-42
→ RefundRequestService.ReturnSalesOrderFee(entity)   // line 178
```

必須**商家/客服在 SCM 賣家後台手動點擊「退運費」按鈕**才會觸發，退貨結案不會自動連動。

### 完整因果推導

1. 商家想幫消費者退運費 SGD 5，**誤以為**要透過建立一張補收單（金額 5）來達成。
2. 補收單機制的語意是「淨額扣抵」，不是「額外退款」，於是這張補收單反而讓商品退款從 62 被扣成 57（商家原意是多退，結果變少退）。
3. 商家**又**另外在 SCM 後台手動點擊了「退運費」，觸發 `ReturnSalesOrderFee` API，補退一筆獨立的 SGD 5（`RefundRequest_SourceDef = SalesOrderFee`）。
4. 兩個都是**人為手動操作**，不是系統自動疊加——是商家對「補收單」與「退運費」兩個機制的用途搞混，各自觸發了一次，才產生 `57 + 5 = 62`（比消費者預期的 67 少了 5）的結果，且因為分屬不同 SourceDef、又被不同批 Grouping Job 撈到，才會拆成兩筆分開送給 Razer。

### 建議

- **補收單建立畫面**應明確標示：此欄位效果為**從退貨退款中扣抵**，用於「多收運費/折扣」等情境，**不能**用來達成「退運費」的效果。
- 若要退運費，應直接使用「退貨」畫面中的「退運費」功能（`ReturnSalesOrderFee` API），而非透過補收單繞道處理。
