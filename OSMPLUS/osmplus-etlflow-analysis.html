1在整個流程中的位置（Big Picture）

OSMPlus 是一套「ETL 排程引擎」型態的後台系統：以 ShopEtlFlow（流程設定） 定義每個商店要跑的批次流程， 以 ShopEtlFlowStep（步驟設定） 定義流程中每一步要執行的 ETL Service（例如：下載檔案、轉檔、寫入 ERP、通知等）。 排程/訊息觸發後，引擎會依設定「產生一筆執行記錄（Task / TaskSlave）」，再依序呼叫每個步驟的 Service 執行，並把過程寫入 Log。

觸發來源（2 種模式） Windows Task Scheduler 定時呼叫 Batch.exe（run-once）　／　常駐程式監聽 RabbitMQ 訊息
① Windows Task Scheduler → Batch.RunFlowById.exe依排程時間，帶入 ShopEtlFlowId/Name 啟動，執行完即結束（run-once）
① Windows Task Scheduler → Batch.RunFirstFlowTask.exe撈第一筆到期 Ready Task 或指定 TaskId，執行完即結束
② 常駐程式 Batch.RunFlowByMessageQueue(V2/Concurrency).exe行程不結束，持續監聽 RabbitMQ Queue，收到訊息才觸發一次流程
[NineYi.OsmPlus.Console.BL.Service] 核心引擎 EtlFlowControlService
CreateFlowTask → GetToDoTaskSlave → DoFlowValidation → DoProcess（逐步執行）
[Console.BL.Service.EtlServices.*] 各 EtlService 實作類別（依 EtlFlowTaskSlave_EtlServiceClassName 反射建立，實作 IEtlFlowService）
[DA.Repositories.EtlFlows / EtlDB] EtlFlowTask ／ EtlFlowTaskSlave ／ EtlFlowTaskLog（狀態與執行紀錄落地）
通知 SlackService / EmergencyService（電話警示）／ PlusNotify（Redis 快取通知去重）
核心概念： ShopEtlFlow / ShopEtlFlowStep 是「設定檔（藍圖）」，永久保存、可重複使用； EtlFlowTask / EtlFlowTaskSlave 是「每次執行的實例（副本）」，一次觸發產生一筆 Task 與多筆 TaskSlave； EtlFlowTaskLog 則是「每一步驟每一次嘗試」的執行歷程留痕，三者是 1（設定）→N（實例）→N（歷程） 的關係。

2觸發條件與進入點

OSMPlus 沒有對外 Web API，所有流程都由背景批次程式觸發，實際佈署上分為兩種截然不同的觸發模式：

模式一・Windows Task Scheduler（最主要的觸發方式）： RunFlowById.exe 與 RunFirstFlowTask.exe 都是「執行完即結束」的 Console 執行檔，本身完全不具備排程能力（程式裡沒有任何 Timer/Cron 邏輯）。 實務上是在 ETL 執行機器上，透過 Windows 工作排程器（Task Scheduler）依商店/流程各自設定觸發時間（對應 ShopEtlFlow_BookingTime 這個「預期執行時間」欄位）， 時間到就呼叫一次 exe 並帶入對應參數；exe 執行完流程就結束程序，等下一次排程時間再被叫起來。這部分排程設定屬於**機器/維運層設定，不在此程式碼庫（Git Repo）中**，因此程式碼分析看不到，需要向維運/DevOps 或直接看 ETL Server 的工作排程器設定才能取得完整排程時間表。
模式二・常駐監聽（RabbitMQ）： RunFlowByMessageQueue(V2/Concurrency).exe 啟動後就是一個不會結束的行程（Thread.Sleep(Timeout.Infinite)），用於「事件觸發」而非「時間觸發」的流程。 這類常駐程式通常也是掛在 Task Scheduler 上（用「開機時」或「登入時」觸發一次、之後不重跑），或是註冊成 Windows Service 保持常駐，跟模式一的「定時執行、跑完就關」性質不同。
進入點（Project）觸發方式用途關鍵行為
NineYi.OsmPlus.Batch.RunFlowById Windows Task Scheduler 依排程時間帶入 --flowid 或 --flowname 呼叫；亦支援人工下 --redo <TaskId> 重跑 依「流程設定」啟動一次新的執行（最常見、最主要的排程進入點） 呼叫 CreateFlowTask(shopEtlFlowId, Running) → 走 DoProcess；失敗時依 RetryCount/RetryInterval 在同一行程內 Sleep 後重試，重試耗盡才讓行程結束（下次仍要等 Task Scheduler 排程時間到才會再被叫起）
NineYi.OsmPlus.Batch.RunFirstFlowTask Windows Task Scheduler 定時呼叫；無參數＝撈 EtlFlowTask_Status='Ready' 且到期第一筆；有參數＝指定 TaskId 設計上是處理「已存在但尚未執行」的 Ready Task GetFirstToDoTask() → DoProcess，不做重試迴圈
NineYi.OsmPlus.Batch.RunFlowByMessageQueue / V2 / Concurrency 常駐程式（非 Task Scheduler 定時觸發），監聽 RabbitMQ Queue，收到訊息即觸發指定 --flow-id 事件驅動型流程（例如上游系統丟訊息通知「有新資料」） 將 MQ 訊息內容包成 QueueMessageFlowChainEntity 當作第一步的 InputChainData 帶入 DoProcess；ack 後才視為處理完成。Concurrency 版本可多工併發處理多筆訊息
重要釐清：建立（Create）與執行（Execute）是在同一個 process 內完成，不是分開兩支程式接力。 看 RunFlowById\Program.cs 原始碼可以確認：CreateFlowTask(shopEtlFlowId, EtlFlowTaskStatusEnum.Running) 一開始就直接把 Task 狀態建立成 Running（不是 Ready）， 緊接著在同一個 while(true) 迴圈內立刻呼叫 DoProcess 把每個 TaskSlave 真正執行完畢，整個「建立→跑完所有步驟→收尾」都在這一次 exe 啟動的生命週期內發生，執行完 process 才結束。 也就是說：Task Scheduler 觸發 RunFlowById.exe，並不是「寫一筆紀錄進 DB 就結束」，而是「這次啟動就會把整個流程真正跑完」。 目前在 RunFlowById／RunFlowByMessageQueue／V2／Concurrency 這 4 個進入點的原始碼中，呼叫 CreateFlowTask 時傳入的狀態全部都是 Running， 找不到任何地方會建立 Ready 狀態的 Task；也就是 RunFirstFlowTask.exe 設計上要撈的「Ready 且已存在的 Task」，在目前程式碼庫中找不到對應的產生來源。 合理推測：這支 exe 可能是給「人工先用 SQL 塞一筆 Ready 狀態 Task，再排程這支程式去撿」的備援/特殊情境使用，或是舊架構遺留、目前 Production 排程實際上主要掛的是 RunFlowById.exe。 此點程式碼無法百分之百確認，建議直接向維運/DevOps 確認 ETL Server 上 Windows Task Scheduler 實際掛載的是哪一支 exe。

RunFlowById vs RunFlowByMessageQueue 差異對照

RunFlowById.exeRunFlowByMessageQueue(.exe)
觸發方式Windows Task Scheduler，定時觸發一次常駐程式，監聽 RabbitMQ Queue，訊息一來就觸發
Process 生命週期啟動 → 跑完一次流程 → process 結束（run-once）Thread.Sleep(Timeout.Infinite)，process 永不結束，持續等訊息
一次啟動能跑幾次流程1 次（跑完就關）無限次（只要有訊息進來就跑一次，跑完繼續等下一則）
flowId 從哪來啟動時 CLI 參數 --flowid/--flowname 決定，之後每次都是同一個 flowId啟動時 --flow-id 固定要跑哪個流程；真正變動的是 InputChainData——每次收到不同 MQ 訊息內容，就包成 QueueMessageFlowChainEntity 當作這次流程第一步的輸入資料
觸發的本質時間驅動（Time-based）：到點就跑，不管有沒有新資料事件驅動（Event-based）：有新資料/事件通知才跑，資料本身隨訊息帶進來
完成後的動作直接結束 processchannel.BasicAck() 確認訊息已處理，然後回到 while 迴圈等下一則訊息
失敗重試方式process 內 while(true) 重試，耗盡才丟出例外讓 process 結束（下次要等 Task Scheduler 排程時間再啟動）同樣有 process 內重試；但若最終失敗拋出例外，該訊息不會被 Ack，可能被 RabbitMQ 重新派送給其他 consumer，行為上更接近「訊息隊列的重試機制」而非「排程重試」
適合場景每天/每小時固定要跑的批次（例如「每日 CRM 同步」）上游系統資料一產生就要立刻處理的流程（例如「訂單一建立就要同步到 ERP」）

一句話總結：RunFlowById 是「時間到就跑一次然後關掉」；RunFlowByMessageQueue 是「常駐等訊息，來一則跑一次，永遠不關」。V2 差異只是改用 Consul 取得連線設定；Concurrency 版本則是同時開多個 Task 平行處理多筆訊息，其餘邏輯相同。

前置條件

  • ShopEtlFlow_IsEnabled = 1 且 ShopEtlFlow_ValidFlag = 1：流程設定必須啟用中
  • 對應 EtlServer_IsEnabled = 1 且 ValidFlag = 1：執行伺服器必須有效
  • ShopEtlFlowStep_ValidFlag = 1：至少要有一個有效步驟，否則 DoProcess 會直接判斷「Task 沒有 TaskSlave」而丟 ApplicationException 並將 Task 標記為 Error

3資料表結構與 ER 關係

整個引擎圍繞 5 張核心表：2 張「設定表」＋ 3 張「執行/歷程表」。以下為欄位摘要與關聯：

ShopEtlFlow（流程設定・藍圖）
  • ShopEtlFlow_Id (PK)
  • ShopEtlFlow_ShopId
  • ShopEtlFlow_Name / Description
  • ShopEtlFlow_IsEnabled
  • ShopEtlFlow_BookingTime（每日排程時間, HH:mm）
  • ShopEtlFlow_EtlServerId → EtlServer
  • ShopEtlFlow_RetryCount / RetryInterval
  • ShopEtlFlow_EtlCategoryId → EtlCategory
  • ShopEtlFlow_AlertGroups（Slack 警示對象）
ShopEtlFlowStep（流程步驟設定・藍圖）
  • ShopEtlFlowStep_Id (PK)
  • ShopEtlFlowStep_ShopEtlFlowId → ShopEtlFlow
  • ShopEtlFlowStep_EtlServiceId → EtlService（對應 ClassName）
  • ShopEtlFlowStep_InitialData（該步驟初始參數 JSON）
  • ShopEtlFlowStep_Sort（執行順序）
  • ShopEtlFlowStep_DefaultInputChainData
EtlFlowTask（流程「執行主檔」・實例）
  • EtlFlowTask_Id (PK)
  • EtlFlowTask_ShopId
  • EtlFlowTask_ShopEtlFlowId → ShopEtlFlow
  • EtlFlowTask_Status（Ready/Running/Finish/Pass/Error）
  • EtlFlowTask_BookingDateTime / StartDateTime / EndDateTime
  • EtlFlowTask_ExecutionCount（重試次數計數）
  • EtlFlowTask_EtlServerId → EtlServer
EtlFlowTaskSlave（流程步驟「執行子檔」・實例）
  • EtlFlowTaskSlave_Id (PK)
  • EtlFlowTaskSlave_ShopId
  • EtlFlowTaskSlave_EtlFlowTaskId → EtlFlowTask
  • EtlFlowTaskSlave_ShopEtlFlowStepId → ShopEtlFlowStep
  • EtlFlowTaskSlave_Status（Ready/Running/Finish/Pass/Error）
  • EtlFlowTaskSlave_Sort（複製自 Step，執行順序）
  • EtlFlowTaskSlave_InitialData（複製自 Step，可被 Redo/檔案覆寫）
  • EtlFlowTaskSlave_InputChainData（上一步輸出/外部輸入序列化 JSON）
EtlFlowTaskLog（執行歷程・每次嘗試的留痕）
  • EtlFlowTaskLog_Id (PK)
  • EtlFlowTaskLog_ShopId
  • EtlFlowTaskLog_EtlFlowTaskId → EtlFlowTask
  • EtlFlowTaskLog_EtlFlowTaskSlaveId → EtlFlowTaskSlave
  • EtlFlowTaskLog_Status（Pass/Finish/Error）
  • EtlFlowTaskLog_StartDateTime / EndDateTime
  • EtlFlowTaskLog_ExecutionSequence（對應 Task 的第幾次重試）
關聯總覽（Cardinality）
  • ShopEtlFlow　1 ——* EtlFlowTask
  • ShopEtlFlowStep　1 —* EtlFlowTaskSlave
  • EtlFlowTask　1 —* EtlFlowTaskSlave
  • EtlFlowTask　1 —* EtlFlowTaskLog（Task 層級 Log，TaskSlaveId 為 0/略）
  • EtlFlowTaskSlave　1 —* EtlFlowTaskLog（每次嘗試一筆）
每次呼叫 DoProcess 皆為「同一 Task」，即使重試也不會新增 Task／TaskSlave，只會新增 Log

三張表的關係白話說明

Table角色誰產生它1 次流程觸發會有幾筆用途
EtlFlowTask 流程「執行主檔」，代表「這次要跑這個 ShopEtlFlow」這件事本身 csp_BatchCreateEtlFlowTaskByShopEtlFlowId（由 EtlFlowControlService.CreateFlowTask 呼叫） 每次觸發 1 筆 追蹤整體流程狀態（Ready→Running→Finish/Pass/Error）、重試次數、起訖時間
EtlFlowTaskSlave 流程「步驟執行子檔」，是 ShopEtlFlowStep 在這次 Task 下的「執行副本」，一個步驟一筆 同一個預存程序，在建立 Task 的同一個 Transaction 內依 ShopEtlFlowStep 逐筆複製產生 每次觸發 N 筆（N＝流程步驟數） 紀錄每個步驟各自的狀態、InitialData（可被覆寫）、InputChainData（步驟間傳遞資料）
EtlFlowTaskLog 「執行歷程」留痕表，不是狀態機的一部分，只負責記錄事件 EtlFlowControlService.InsertTaskLog（在 DoProcess 中，Task 開始/結束、每個 TaskSlave 開始/結束都會各寫一筆） 每次觸發（含重試）至少 2 筆起：1 筆 Task 層級 + N 筆 TaskSlave 層級；若中途發生 Error 重試，重試次數越多 Log 越多 作為 Console 後台查詢「每次執行明細/除錯」的依據，狀態值只有 Pass/Finish/Error 三種（沒有 Ready/Running，因為 Log 只在「動作結束」時才寫入）

4核心流程（逐步）

以 Batch.RunFlowById 進入點為例（其餘進入點只是觸發方式不同，核心邏輯完全共用 EtlFlowControlService）：

#步驟對應程式說明
1建立 Task（+ 所有 TaskSlave） EtlFlowControlService.CreateFlowTask() 呼叫預存程序 csp_BatchCreateEtlFlowTaskByShopEtlFlowId，一次交易內依 ShopEtlFlow/ShopEtlFlowStep 產生 1 筆 EtlFlowTask（狀態 Running）與 N 筆 EtlFlowTaskSlave（狀態 Ready）
2（選用）RunTime 覆寫 InitialData RunTimeReplaceInitialData() 若呼叫端帶了 --initdatapath 檔案內容，依 ShopEtlFlowStepId 對應覆寫某些 TaskSlave 的 InitialData（常用於人工排錯/重跑帶不同參數）
3解析 Slack 通知設定 ShopProfileRepository.GetShopProfile 先查 SlackUrlByFlowId，找不到再查 SlackUrlByFlowCategory，組成 IAlertService
4輪詢 Task 狀態，執行 DoProcess GetTask() → DoProcess() 每次重試前都重新 GetTask 讀最新狀態；若已是 Finish 則直接結束
5Task 狀態改為 Running，建立 Task 層級 Log 物件 UpdateTaskStatusToRunning + taskLog taskLog 先在記憶體建立，等整體流程結束才 Insert
6撈出所有 TaskSlave（含步驟/服務資訊） GetToDoTaskSlave() = EtlFlowTaskRepository.GetTaskSlave() INNER JOIN ShopEtlFlowStep / ShopEtlFlow / EtlService / EtlCategory，依 Sort 排序
7Flow Validation DoFlowValidation() 用反射建立每個步驟的 Service 假實例，檢查前一步 OutputChainType 是否可指派給下一步 InputChainType（型別鏈必須銜接），不通過則整批判 Error
8逐一執行每個 TaskSlave foreach (flowTaskSlave in flowServiceTasks) 已 Finish → 補記 Pass Log 並跳過；
流程已被前面步驟中斷（isFlowStopped）→ 標記 Pass 並跳過；
否則：反射建立 Service（CreateFlowService）→ 狀態改 Running → 執行 flowService.DoProcess(taskSlave, inputChain, flowVariables, alertService) → 依回傳的 OutputChainEntity.IsStopFlowProcess 決定是否中斷後續步驟 → 狀態改 Finish 並寫 Log
9步驟間資料傳遞 inputChainEntity = outputChainEntity 上一步的輸出物件直接作為下一步的輸入物件（見第 8 節）
10收尾：整體 Task 狀態判定 UpdateTaskStatusToFinish / ToPass 若流程被中途 Stop（isFlowStopped）→ Task 狀態為 Pass；否則為 Finish，並寫入 Task 層級 Log
11完成通知 alertService.Info(...) 僅在非 Debug、未被步驟要求靜音（IsMuteSlackNotificationWhileFinish）、且 ShopEtlFlow_IsNotifyWhenFinish=1 時才發送 Slack 完成通知
錯誤重試（僅限 RunFlowById / RunFlowByMessageQueue 進入點）： 當 DoProcess 拋出例外，外層 while 迴圈依 ExecutionCount - 1 < RetryCount 判斷是否重試； 是則 Thread.Sleep(RetryInterval秒) 後重新 GetTask 再跑一次 DoProcess（同一 Task/TaskSlave，狀態會被覆寫，但每次嘗試都會新增一筆 EtlFlowTaskLog）； 超過重試次數則對外拋出例外、行程結束（交由外部排程系統決定是否再次啟動整個 Batch）。

5分支決策 / 狀態對照

EtlFlowTask 產生條件（csp_BatchCreateEtlFlowTaskByShopEtlFlowId）

條件結果
ShopEtlFlow_IsEnabled=0 或 ValidFlag=0不會被撈入 #tmpTaskBase → 不會產生 Task/TaskSlave（等於 no-op）
EtlServer_IsEnabled=0 或 ValidFlag=0同上，不會產生
ShopEtlFlowStep_ValidFlag=0（全部步驟皆停用）會建立 1 筆 EtlFlowTask，但 0 筆 EtlFlowTaskSlave → DoProcess 判斷「Task has no taskSlave」直接丟例外、Task 狀態轉 Error
正常情況1 筆 EtlFlowTask（狀態依呼叫端傳入，通常 Running）＋ N 筆 EtlFlowTaskSlave（狀態 Ready）

Flow Validation 結果

條件行為最終結果
TaskSlave 數量 = 0validFailMessage 直接設為錯誤訊息Task/Log 皆標記 Error，丟 ApplicationException
前一步 OutputChainType 與下一步 InputChainType 無繼承關係組出「無法串接」訊息同上，整批視為驗證失敗，不執行任何步驟
驗證通過不動作，直接進入逐步執行正常往下走

單一 TaskSlave 執行分支

條件行為
TaskSlave.Status == Finish（代表重試時此步驟先前已成功）寫入 Pass Log，continue 跳過，不重跑
isFlowStopped == true（前面某步驟輸出要求中斷）該 TaskSlave 直接標記為 Pass，並寫 Pass Log，不呼叫 Service
正常執行拋出 EtlFlowTaskDoNotSendSlackExceptionTaskSlave/Task 皆標記 Error、寫 Error Log，但不發送 Slack 告警，直接往外拋出
正常執行拋出其他 ExceptionTaskSlave/Task 皆標記 Error、寫 Error Log；非 Debug 模式下組裝團隊 @提及 並發送 Slack 告警（必要時撥打緊急電話），呼叫 PlusNotify 避免重複通知，最終往外拋出
Service 執行成功，OutputChainEntity.IsStopFlowProcess = true該步驟仍標記 Finish，但將 isFlowStopped 設為 true，後續步驟全部改走「Pass」分支

7例外處理一覽

例外類型觸發時機資料庫影響通知行為

8關鍵資料說明：InputChainData / OutputChainData

Chain Entity（繼承自 BaseEtlFlowChainEntity） 是貫穿整條流程、步驟與步驟之間唯一的資料傳遞媒介，其生命週期如下：

  1. 產生： 第一個 TaskSlave 若本身沒有 InputChainData（來自 ShopEtlFlowStep 設定的 DefaultInputChainData），則用呼叫端傳入的 inputChainData（例如 RabbitMQ 訊息內容包成 QueueMessageFlowChainEntity，或 --initdatapath 檔案內容）補上。
  2. 傳遞： 每個 Service 執行完 DoProcess() 回傳 OutputChainEntity，該物件會被序列化並存回下一筆 TaskSlave 的 InputChainData 欄位（DB 落地，供中斷後重跑時可還原現場），同時在記憶體中直接指派給下一輪迴圈的 inputChainEntity 繼續往下傳。
  3. 型別契約檢查： DoFlowValidation 在真正執行前，先用反射建立每個 Service 檢查 GetFlowOutputChainType() 是否可指派給下一個 Service 的 GetFlowInputChainType()，確保鏈可以串起來（例如 FileBaseFlowChainEntity 系列彼此相容）。
  4. 特殊旗標： Chain Entity 上帶有 IsStopFlowProcess（要求中斷後續步驟）與 IsMuteSlackNotificationWhileFinish（完成時不發送 Slack 通知）兩個旗標，由個別 Service 依商業邏輯決定是否設置，直接影響第 5、6 節的狀態流轉。
  5. 消費： FlowVariables（Dictionary，跨步驟共享的執行期變數，如 FILESROWCOUNT、ERRORFILES、EXECUTE_NOTE）與 Chain Entity 一起在告警/完成通知訊息中被組裝顯示。

9特殊案例 / 備註

  • Redo（人工重跑既有 Task）： --redo <TaskId> 或 RunFirstFlowTask 帶入 TaskId，皆直接 GetTask(taskId) 後呼叫 DoProcess，沿用同一筆 Task/TaskSlave（已 Finish 的步驟會被跳過只補 Pass Log，未完成/Error 的步驟才會真正重跑），不會建立新的 Task。
  • Debug Mode（--debug）： 僅在 Execmode=Dev 時允許 FlowDebugHelper.DoFlowModification 動態調整要執行的步驟；Debug 模式下發生錯誤不會觸發外層重試迴圈與 Slack 錯誤告警。
  • Emergency（--emergency / isEmergency）： 發生一般 Exception 時，除了 Slack 告警外，額外透過 EmergencyService 撥打設定於 Emergency.CellPhone 的電話號碼，用於極重要流程的即時示警。
  • PlusNotify（Redis 去重通知）： 每次 Task/TaskSlave 發生錯誤都會呼叫 PlusNotify，透過 Redis Cache 判斷同一 Shop/Flow 是否已通知過，避免重試風暴造成 Slack 洗版。
  • NOLOCK 查詢： 幾乎所有讀取 SQL 皆使用 WITH (NOLOCK)，追求排程查詢效能，但需留意讀到暫時性不一致資料的可能性（例如剛建立尚未 Commit 的 Task）。
  • ExecutionSeconds / ExecutionSequence： Task 與 TaskSlave 皆有唯讀計算欄位 ExecutionSeconds（Start/End 相減），Log 表則多一個 ExecutionSequence 對應「這是第幾次執行嘗試（等同外層重試次數）」，可用於在 Console 後台把同一次真正的執行流程與重試流程分開檢視。
  • RabbitMQ 進入點的 Ack 時機： RunFlowByMessageQueue 系列在 ExecuteFlowId（含其內部重試）全部完成後才 BasicAck，若行程中因重試耗盡而拋出例外，該訊息不會被 Ack，可能被 MQ 重新派送（需留意流程冪等性設計）。
