2症狀

批次上傳主檔（BatchUpload_Id = 327407）狀態卡在 InProcess 超過 30 分鐘未變化，觸發監控告警。

3根本原因

⛔ Root Cause
翻譯資源字串的語系版本參數數量不一致，導致 string.Format 在補記錯誤訊息時拋出未攔截的例外，使整個 NMQ Task 直接失敗（^500 FAILED），批次狀態來不及更新為終態，因而卡在 InProcess。

觸發點：翻譯資源不同語系佔位符數量不同

Core\NineYi.NMQV2.Translation\AutoGenerated\Scm.Service.BatchModifyPromotionSalePage.cs

語系內容所需參數數
en-USPromotion ID: {0}1
zh-TW活動序號：{0}1
zh-HK活動序號：{0}；異動狀態：{1}2
zh-CN活動序號：{0}；異動狀態：{1}2
ms-MYPromotion ID: {0} ; Update: {1}2

而呼叫端只傳入 1 個參數（SCM\Frontend\BLV2\BatchUpload\BatchModifyPromotionSalePageService.cs）：

// 只傳入 promotionId 一個參數
private string GetBatchUploadMessageTitle(int promotionId) =>
    string.Format(
        NineYi.NMQV2.Translation.Scm.Service.BatchModifyPromotionSalePage.BatchUploadMessageTitle,
        promotionId   // zh-HK/zh-CN/ms-MY 需要 2 個參數！
    );

商店序號 15 屬於 HK 市場，該 Task 執行緒語系解析為 zh-HK，組錯誤訊息標題時因缺少 {1} 對應參數而拋出：

FormatException: Index (zero based) must be greater than or equal to zero
and less than the size of the argument list.

此例外發生在 catch (ApplicationException ex) { ... } 區塊內部，屬於二次例外，未被任何外層 try-catch 攔截，整個 NMQ Task 直接失敗結束。

5誰把狀態改成 FinishWithError？

💡 不是人工操作
是系統既有的自動收尾邏輯判定的，位置在 BatchUploadRepositoryService.UpdateBatchUploadStatus()。 
case BatchUploadStatusEnum.Finish:
case BatchUploadStatusEnum.FinishWithError:

    int detailMessageCount = this.BatchUploadRepository.GetBatchUploadMessageCount(...);
    batchUploadEntity.BatchUpload_HasDetail = (detailMessageCount > 0);

    // 如有錯誤, 更改狀態成 (已完成 / 發現錯誤)
    if ((batchUploadEntity.BatchUpload_FailCount > 0 || detailMessageCount > 0) ...)

7解法

✅ 立即處置
  • 確認 BatchUploadMessage 內容，即是 PromotionId: 48778, ShopId: 15 這筆 Promotion API 呼叫失敗的原始錯誤（非 zh-HK bug 本身導致的資料錯誤，是記錄錯誤訊息時才二次炸開）
  • 若該筆 Promotion 更新確實需要補做，需重新提交批次或手動呼叫 API 補處理
✅ 根本修正（程式碼）

修正 GetBatchUploadMessageTitle，同時傳入 PromotionId 與 ModifyStatus 兩個參數：

private string GetBatchUploadMessageTitle(int promotionId, string modifyStatus) =>
    string.Format(
        NineYi.NMQV2.Translation.Scm.Service.BatchModifyPromotionSalePage.BatchUploadMessageTitle,
        promotionId,
        modifyStatus
    );
多傳的參數對只有 {0} 的語系（en-US/zh-TW）不會有影響（string.Format 允許提供比佔位符更多的參數），可安全修正所有語系。
  • commercenmq 專案內同名的 BatchModifyPromotionSalePageService（Nine1.Commerce.Console.BL.Services.BatchUpload 命名空間）需要同步修正，因為那份才是本案例實際觸發崩潰的執行環境
  • 檢查同一個 Service 內其他呼叫 GetBatchUploadMessageTitle 的地方（DoValidate() 內的驗證失敗訊息也共用同一組翻譯字串，可能有相同風險）
  • 全面搜尋 Translation 資源，找出其他「不同語系佔位符數量不一致」的字串，避免同類問題在其他批次類型再次發生
