# 案例：zh-HK 語系錯誤訊息缺參數，導致批次卡在 InProcess 逾時告警

## 症狀

告警訊息：

> [HK][Prod] 批次作業逾時警告，建立超過 30 分鐘未執行完畢，請 @oversea_brd 協助確認批次作業異常筆數: 1
> • 批次作業序號: 327407 類型: BatchModifyPromotionSalePage 狀態: InProcess 客戶序號: 12 商店序號: 15

批次上傳主檔 (`BatchUpload_Id = 327407`) 狀態卡在 `InProcess` 超過 30 分鐘未變化，觸發監控告警。

<br>

---

## 根本原因

**翻譯資源字串的語系版本參數數量不一致，導致 `string.Format` 在補記錯誤訊息時拋出未攔截的例外，使整個 NMQ Task 直接失敗（`^500 FAILED`），批次狀態來不及更新為終態，因而卡在 `InProcess`。**

### 觸發點

```
Core\NineYi.NMQV2.Translation\AutoGenerated\Scm.Service.BatchModifyPromotionSalePage.cs
```

`batch_upload_message_title` 這組翻譯字串，各語系佔位符數量不一致：

| 語系 | 內容 | 所需參數數 |
|------|------|------|
| en-US | `Promotion ID: {0}` | 1 |
| zh-TW | `活動序號：{0}` | 1 |
| **zh-HK** | **`活動序號：{0}；異動狀態：{1}`** | **2** |
| zh-CN | `活動序號：{0}；異動狀態：{1}` | 2 |
| ms-MY | `Promotion ID: {0} ; Update: {1}` | 2 |

而呼叫端程式碼（`SCM\Frontend\BLV2\BatchUpload\BatchModifyPromotionSalePageService.cs`）**只傳入 1 個參數**：

```csharp
private string GetBatchUploadMessageTitle(int promotionId) =>
    string.Format(
        NineYi.NMQV2.Translation.Scm.Service.BatchModifyPromotionSalePage.BatchUploadMessageTitle,
        promotionId   // 只傳 1 個參數，zh-HK/zh-CN/ms-MY 需要 2 個
    );
```

商店序號 15 屬於 **HK 市場**，該 Thread/Task 執行時語系被解析為 `zh-HK`（依 `TranslationHelper.GetLocale()` / `AssignLocale` 機制決定），因此在組錯誤訊息標題時，`string.Format` 因缺少 `{1}` 對應參數而拋出：

```
FormatException: Index (zero based) must be greater than or equal to zero and less than the size of the argument list.
```

此例外發生在 `catch (ApplicationException ex) { ... GetBatchUploadMessageTitle(...) ... }` 區塊內部，屬於**二次例外**，未被任何外層 try-catch 攔截，導致整個 NMQ Task 直接以 `FAILED` 結束。

## 誰把狀態改成 FinishWithError？

**不是人工操作，是系統既有的自動收尾邏輯判定的。**

位置：`SCM\Frontend\BLV2\BatchUpload\BatchUploadRepositoryService.cs` → `UpdateBatchUploadStatus()`

```csharp
case BatchUploadStatusEnum.Finish:
case BatchUploadStatusEnum.FinishWithError:
    ...
    // BatchModifyPromotionSalePage 屬於通用分支（else）
    // 依 BatchUploadData 狀態統計失敗/成功筆數
    batchUploadEntity.BatchUpload_FailCount = ...ValidateFailed + ProcessFailed 筆數...;
    int detailMessageCount = this.BatchUploadRepository.GetBatchUploadMessageCount(...);
    batchUploadEntity.BatchUpload_HasDetail = (detailMessageCount > 0);

    // 如有錯誤, 更改狀態成 (已完成 / 發現錯誤)
    if ((batchUploadEntity.BatchUpload_FailCount > 0 || detailMessageCount > 0) ...)
    {
        batchUploadEntity.BatchUpload_StatusDef = BatchUploadStatusEnum.FinishWithError.ToString();
    }
```

觸發呼叫端：`BatchUploadTaskProcess.ExecuteByProcessType()`

```csharp
var dataList = this.GetReadyToProcessDataList(nmqDataEntity);
if (dataList.Count > 0) { /* 還有資料要處理，繼續跑 */ }
else
{
    if (ProcessType == ByProcessCount)
    {
        // 所有資料都處理完了（沒有 ReadyToProcess 的了），準備收尾
        this.BatchUploadRepositoryService.UpdateBatchUploadStatus(batchUploadService, this.BatchUploadEntity, BatchUploadStatusEnum.Finish);
        // ↑ 傳入 Finish，但方法內部會檢查 FailCount/錯誤明細，發現有錯誤就自動改成 FinishWithError
    }
}
```

### 推論鏈

1. 11:39:28 崩潰時，`BatchUploadData_Id 35522` 因例外發生在 `DoProcess` 內部且未被攔截，整個 Task 崩潰，`UpdateBatchUploadData` 沒機會被呼叫 → 該筆資料狀態沒有被更新，但呼叫 Promotion API 失敗的錯誤訊息已經在崩潰前寫入 `BatchUploadMessage`
2. 11:40 ~ 12:08 之間，由 `BatchUploadCounterService` 派發的**另一個獨立 Task**（非崩潰的 `28a28bdc`）重新抓到剩餘待處理資料並處理完
3. 該 Task 處理完後 `GetReadyToProcessDataList` 回傳空清單 → 呼叫 `UpdateBatchUploadStatus(..., Finish)`
4. 方法內部偵測到 `FailCount > 0` 或 `detailMessageCount > 0`（因為步驟 1 已寫入的錯誤訊息明細）→ **自動把狀態由 `Finish` 改判為 `FinishWithError`**
5. 因此 12:08:16 那個「重試」的失敗 taskId (`28a28bdc`) 被 Router 重新派送過來時，查到狀態已是 `FinishWithError`，判定不可處理，直接結束

## 解法

### 立即處置

- 確認 `BatchUploadMessage` 內容，就是 `PromotionId: 48778, ShopId: 15` 這筆 Promotion API 呼叫失敗的原始錯誤（非 zh-HK bug 本身導致的資料錯誤，是另一層錯誤訊息記錄時才炸開）
- 若該筆 Promotion 更新確實需要補做，需重新提交批次或手動呼叫 API 補處理

### 根本修正（程式碼）

修正 `GetBatchUploadMessageTitle`，同時傳入 `PromotionId` 與 `ModifyStatus` 兩個參數：

```csharp
private string GetBatchUploadMessageTitle(int promotionId, string modifyStatus) =>
    string.Format(
        NineYi.NMQV2.Translation.Scm.Service.BatchModifyPromotionSalePage.BatchUploadMessageTitle,
        promotionId,
        modifyStatus
    );
```

> 多傳的參數對只有 `{0}` 的語系（en-US/zh-TW）不會有影響（`string.Format` 允許提供比佔位符更多的參數），可安全修正所有語系。

同時建議：

- commercenmq 專案內同名的 `BatchModifyPromotionSalePageService`（`Nine1.Commerce.Console.BL.Services.BatchUpload` 命名空間）需要同步修正，因為那份是本案例實際觸發崩潰的執行環境
- 檢查同一個 Service 內其他呼叫 `GetBatchUploadMessageTitle` 的地方（`DoValidate()` 內的驗證失敗訊息也共用同一組翻譯字串，可能有相同風險）
- 全面搜尋 Translation 資源，找出其他「不同語系佔位符數量不一致」的字串，避免同類問題在其他批次類型再次發生
