# BatchUpload 狀態機完整解說

## 核心觀念：兩層狀態

BatchUpload 有**兩層狀態**，很多人會混：

| 層級 | Table | 欄位 | 代表什麼 |
|------|-------|------|----------|
| **主狀態** | `BatchUpload` | `BatchUpload_StatusDef` | **整批**任務現在在哪個階段 |
| **子資料狀態** | `BatchUploadData` | `BatchUploadData_StatusDef` | **每一列** Excel 的個別結果 |

<br>

---

## 主狀態完整地圖

### `WaitingToLoadData` — 已建立，等 NMQ 接手

> 📍 位置：**剛離開 SMS，NMQ 還沒摸到它**

```csharp
// BatchUploadService.cs
StatusDef = BatchUploadStatusDefEnum.WaitingToLoadData.ToString()
// ← SMS 建立 BatchUpload 時就寫這個狀態
```

- NMQ 主 Task (JobId=49) 已放入佇列，但尚未被 Worker 取走執行
- 若這個狀態卡很久 → **NMQ Worker 沒在跑** 或 **NMQ 佇列塞車**

<br>

---

### `InLoadData` — NMQ 正在讀 Excel 檔

> 📍 位置：**BatchUploadProcess.DoJob 正在執行 LoadData()**

```csharp
// BatchUploadProcess.cs
UpdateBatchUploadStatus(..., BatchUploadStatusEnum.InLoadData);
this.BatchUploadService.LoadData();  // ← 讀 Excel，建立 Wrapper
```

- 進入 NMQ Worker，`InitContainerBuilder()` 完成，開始讀檔案
- 若卡在這 → **Excel 很大讀很慢、或 Filer/S3 連線異常**

<br>

---

### `InValidation` — NMQ 正在跑二次驗證

> 📍 位置：**BatchUploadProcess.DoJob 正在執行 DoValidate()**

```csharp
// BatchUploadProcess.cs
UpdateBatchUploadStatus(..., BatchUploadStatusEnum.InValidation);
this.BatchUploadService.DoValidate();  // ← FluentValidation 業務邏輯驗證
```

- Excel 讀完了，正在做業務邏輯驗證（如驗 PromotionId 是否存在）
- 若卡在這 → **驗證在打外部 API 或 DB，資料量太大**

<br>

---

### `ValidateFailed` — 二次驗證失敗，整批終止

> 📍 位置：**終態，不會再有任何 Task**

- 驗證完全失敗（全部都是 ValidateFailed），整批作廢
- 可查 `BatchUploadData` 看每筆失敗原因

<br>

---

### `WaitingToProcess` — 驗證完成，等子 Task 開始

> 📍 位置：**主 NMQ 跑完了，子 Task 已放入佇列但還沒被取走**

```csharp
// BatchUploadProcess.cs
bool hasAnyDataValidationFailed =
    dataList.Any(x => x.BatchUploadData_StatusDef == nameof(BatchUploadDataStatusEnum.ValidateFailed));

status = hasAnyDataValidationFailed == true
    ? BatchUploadStatusEnum.ScheduleAbortedWithErrors
    : BatchUploadStatusEnum.WaitingToProcess;

// 子 Task 已建立
taskHelper.CreateTask(batchUploadExecuteTaskType.ToString(), taskData, bookingTime);
```

- `BatchUploadData` 已全部 INSERT 完成，狀態為 `ReadyToProcess`
- 子 Task 已入 NMQ 佇列，但還沒被 Worker 執行
- 若卡在這 → **NMQ 子 Task 佇列塞車 / Worker 沒在跑**
- ⚠️ 若是**預約批次**，`WaitingToProcess` 是正常等待排程時間到才執行

<br>

---

### `InProcess` — 子 Task 正在逐批處理中

> 📍 位置：**BatchUploadTaskProcess.DoJob 正在跑 DoBatchProcess()**

```csharp
// BatchUploadTaskProcess.cs
if (status == BatchUploadStatusEnum.WaitingToProcess)
{
    UpdateBatchUploadStatus(..., BatchUploadStatusEnum.InProcess);
}
// 每輪跑 10 筆 → DoProcess → re-queue +10s → 下一輪
```

- 子 Task 已開始，**每輪跑 10 筆，跑完再 re-queue，重複直到沒有資料**
- 這個狀態可能**持續很長時間**（10 萬筆 ≈ 一萬輪 Task）
- ⚠️ **Quota 計算以這個狀態為準**（同廠商 `InProcess` 筆數 ≥ 10 → 新批次排隊等待）

<br>

---

### `ScheduleAbortedWithErrors` — 預約批次驗證有錯，已中止

> 📍 位置：**終態，只有預約批次會出現**

```csharp
// BatchUploadProcess.cs
if (status == BatchUploadStatusEnum.ScheduleAbortedWithErrors)
{
    return;  // ← 直接 return，不建立子 Task
}
```

- 預約批次在主 NMQ 階段發現驗證錯誤，**整個預約取消**，不會執行
- 非預約批次即使有部分驗證失敗也**不會**進這個狀態

<br>

---

### `ScheduleCancelled` — 使用者手動取消預約

> 📍 位置：**SMS 端直接設定的終態**

```csharp
// BatchUploadService.cs
batchUpload.BatchUpload_StatusDef = nameof(BatchUploadStatusDefEnum.ScheduleCancelled);
// 條件：狀態必須是 WaitingToProcess，且距排程時間 > 5 分鐘
```

<br>

---

### `Finish` — 全部完成

> 📍 終態，有**兩種路徑**都可以到達（⚠️ 不一定代表成功）

```csharp
// 路徑 A：主 NMQ 發現 dataList.Count == 0（全驗證失敗，沒有可執行資料）
// BatchUploadProcess.cs
UpdateBatchUploadStatus(..., BatchUploadStatusEnum.Finish);

// 路徑 B：子 Task 撈不到 ReadyToProcess 的資料了（全部跑完）
// BatchUploadTaskProcess.cs
UpdateBatchUploadStatus(..., BatchUploadStatusEnum.Finish);
```

> ⚠️ **路徑 A 的 `Finish` 是「因為全部都驗證失敗沒事可做的完成」，不代表成功！**  
> 要確認 `BatchUpload_TotalCount` 與 `BatchUpload_SuccessCount`。

<br>

---

### `FinishWithError` — 完成但有部分失敗

> 📍 終態，由 `UpdateBatchUploadStatus` 在判斷 FailCount > 0 時**內部覆蓋**原本傳入的 `Finish`

```csharp
// BatchUploadRepositoryService.cs
// 外部傳入 Finish，但內部自行判斷改掉
if ((batchUploadEntity.BatchUpload_FailCount > 0 || detailMessageCount > 0)
      && status != BatchUploadStatusEnum.FinishWithUnExpectedError
      && status != BatchUploadStatusEnum.ScheduleAbortedWithErrors)
{
    batchUploadEntity.BatchUpload_StatusDef = BatchUploadStatusEnum.FinishWithError.ToString();
}
```

> ⚠️ **「狀態偷換」**：呼叫端傳入 `Finish`，函式內部判斷有錯誤後自行改成 `FinishWithError`，看程式碼時很容易搞混設定點。

<br>

---

### `FinishWithUnExpectedError` — 主 NMQ 執行中噴未預期例外

> 📍 終態，只有主 NMQ 的 catch block 才能設這個

```csharp
// BatchUploadProcess.cs
catch (Exception ex)
{
    this.SendErrorNotificationMail(ex);  // ← 發 Email 通知
    UpdateBatchUploadStatus(..., BatchUploadStatusEnum.FinishWithUnExpectedError);
}
```

- 代表 `LoadData()` 或 `DoValidate()` 或 `CreateBatchUploadData()` 噴了未捕捉的例外
- **只有主 NMQ Process 才有這個 catch**
- 子 Task 若噴例外則由 NMQ 自行 retry，不會進這個狀態

<br>

## 狀態時間軸

```
SMS                主 NMQ (Job=49)               子 NMQ (各 TaskProcess)
─────────────────────────────────────────────────────────────────────────
WaitingToLoadData  ← CREATE
        ↓
                   InLoadData     ← LoadData()
                        ↓
                   InValidation   ← DoValidate()
                        ↓
              ┌─── ValidateFailed              (終態)
              │
              ├─── ScheduleAbortedWithErrors   (終態，僅預約批次)
              │
              └─── WaitingToProcess ──────────────────────────────────┐
                        ↓                                             │
                   Finish                                             │ 排程時間到
                   (dataList=0，終態)                                  ↓
                                             InProcess  ← 第一輪 10 筆
                                                 ↓
                                             InProcess  ← 第二輪 10 筆
                                             (re-queue +10s 繼續)
                                                 ↓
                                             Finish               (終態)
                                                 ↓（內部判斷有錯誤）
                                             FinishWithError      (終態)

主 NMQ catch block（任意時間點）：
                   FinishWithUnExpectedError                         (終態)

SMS CancelBatchUploadSchedule（只能在 WaitingToProcess 時）：
                   ScheduleCancelled                                 (終態)
```

<br>

## 一句話速查表

| 狀態 | 白話意思 | 卡住/停在這代表 |
|------|----------|----------------|
| `WaitingToLoadData` | 已建立，NMQ 還沒摸到 | NMQ Worker 掛了或佇列塞車 |
| `InLoadData` | 正在讀 Excel | 檔案太大 或 Storage 連線異常 |
| `InValidation` | 正在跑業務邏輯驗證 | 驗證打 API/DB 太慢 |
| `WaitingToProcess` | 驗證完，等子 Task 開跑 | ①NMQ 佇列塞車 ②預約等時間 ③Quota 鎖死 |
| `InProcess` | 子 Task 每 10 筆循環中 | ①正常進行中 ②Quota 鎖死 |
| `ValidateFailed` | 二次驗證整批失敗 | 終態，查 BatchUploadData |
| `ScheduleAbortedWithErrors` | 預約批次驗證有錯，取消 | 終態，修正後重新上傳 |
| `ScheduleCancelled` | 使用者手動取消 | 終態 |
| `Finish` | 跑完 或 沒東西可跑 | 終態，確認 SuccessCount |
| `FinishWithError` | 跑完但有部分失敗 | 終態，查 BatchUploadMessage |
| `FinishWithUnExpectedError` | 主 NMQ 噴例外 | 終態，查 NMQ Log + 通知 Email |

<br>

## 最容易混淆的三個點

### 1. `Finish` 不一定代表「成功跑完」

路徑 A：`dataList.Count == 0` 也會 `Finish`，可能是**全部都驗證失敗沒東西可跑**。  
必須確認 `BatchUpload_TotalCount` 與 `BatchUpload_SuccessCount` 才能判斷。

### 2. `WaitingToProcess` 可能是三件完全不同的事

| 情況 | 現象 |
|------|------|
| ① 正常等子 Task | 幾秒內就會變 `InProcess` |
| ② 預約批次等排程 | 可能等幾小時，是正常的 |
| ③ Quota 滿了被 re-queue | 無限等，需人工介入釋放 |

### 3. `FinishWithError` 是在函式內部被「偷換」的狀態

外部呼叫 `UpdateBatchUploadStatus(..., Finish)`，但 `BatchUploadRepositoryService` 內部判斷 `FailCount > 0` 後自行改為 `FinishWithError`。  
在 grep 設定點時容易找不到，**真正的設定點在 `BatchUploadRepositoryService.UpdateBatchUploadStatus`**。
