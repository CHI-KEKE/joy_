# 批次執行過久風險分析

## 架構概述

BatchUpload 分兩個 NMQ 階段：

```
主 NMQ (BatchUploadProcess)
  InitContainerBuilder → LoadData → DoValidate → CreateBatchUploadData → 發動子 Task

子 Task (BatchUploadTaskProcess)
  GetReadyToProcessDataList (N筆) → DoBatchProcess (foreach) → re-queue → 重複
```

---

## 瓶頸一：主 NMQ — 全程同步，無法切分

主 NMQ 的四個步驟全在同一個 Task 內同步執行：

| 步驟 | 潛在耗時原因 |
|------|------------|
| `InitContainerBuilder()` | 每次重建 150+ DI 服務，CPU/記憶體純開銷 |
| `LoadData()` | 整個 Excel 一次讀進記憶體，無分頁讀取 |
| `DoValidate()` | 每列可能查 DB 驗證，全部同步逐筆執行 |
| `CreateBatchUploadData()` | 多數 Supplier 逐筆 INSERT（非 BulkInsert） |

Excel 越大、列數越多 → 主 Task 執行時間線性增長 → 有超過 NMQ Timeout 的風險。

---

## 瓶頸二：子 Task — ProcessCount × re-queue 累積

每次子 Task 流程：
```
抓 ProcessCount 筆 (預設 10，AppSetting: BatchUpload.{Type}.TaskProcessCount)
  → foreach 逐筆 DoProcess()（純 sequential，無 Task.WhenAll / Parallel.ForEach）
  → 若還有資料 → re-queue（delay BatchUpload.BookingTime.DelaySeconds，預設 10 秒）
  → 重複直到沒有 ReadyToProcess 資料
```

### 最壞情況試算

| 條件 | 值 |
|------|---|
| 總資料筆數 | 1000 筆 |
| ProcessCount | 10 筆/次 |
| 每筆 DoProcess 耗時 | 1 秒（含外部 API / DB） |
| re-queue delay | 10 秒 |

```
1000 ÷ 10 = 100 次子 Task
每次執行 = 10 筆 × 1 秒 = 10 秒
每次 re-queue 等待 = 10 秒
總時間 = 100 × (10 + 10) = 2000 秒 ≈ 33 分鐘
```

若每筆 DoProcess 涉及多個外部 API（3~5 秒/筆）：
```
100 × (30~50 + 10) = 4000~6000 秒 ≈ 1~1.7 小時
```

## 瓶頸三：IsBatchTaskExecuted 與 NMQ 重試的競爭

```csharp
// ExpireSeconds 預設 50 秒
int taskRedoExpireSeconds = AppSetting("BatchUpload.{TypeDef}.TaskExecuted.ExpireSeconds", "50");
```

**競爭時序：**
```
T+0s：Task A 開始執行
T+35s：NMQ 判定超時，觸發 Task B
T+35s：Task B 檢查 IsBatchTaskExecuted → 在 50 秒內 → 跳過（OK）
T+55s：Task A 完成（花了 55 秒，超過 ExpireSeconds）
T+55s：NMQ 再次觸發 Task C
T+55s：Task C 檢查 IsBatchTaskExecuted → 50 秒已過 → 重複執行同一批資料！
```

結果：**同一批資料被執行兩次**，產生重複操作風險。

---

## 所有瓶頸彙整

| 瓶頸 | 所在位置 | 根本原因 |
|------|---------|---------|
| DI Container 重建 | 主 NMQ，`InitContainerBuilder` | 150+ 服務每次重建，無快取 |
| Excel 全量讀取 | 主 NMQ，`LoadData` | 整個檔案一次讀進記憶體 |
| DoValidate 同步逐列 | 主 NMQ，`DoValidate` | 無並行，每列可能查 DB |
| DoProcess 組內串行 | 子 Task，`DoBatchProcess` | 純 foreach，無任何並行機制 |
| re-queue 累積等待 | 子 Task，每批 +10 秒 | NMQ delay 設計本身的代價 |
| TaskExecuted 競爭 | 子 Task，`IsBatchTaskExecuted` | ExpireSeconds 可能比實際執行短 |

---

## 最容易出事的場景

1. **大量資料 + DoProcess 涉及外部 API**（最常見）
   - 每筆等外部回應，ProcessCount 再小也救不了總時間
   - 典型：出貨確認類批次，每筆呼叫多個下游系統

2. **Excel 行數接近上限時的 DoValidate**
   - 幾千列同步驗證，主 Task 可能跑超過 NMQ Timeout
   - 典型：黑名單匯入、大量商品更新

3. **高峰期多個批次同時執行**
   - Quota 限制 10 個 InProcess，但每個都很慢
   - 新批次一直 re-queue 等待（每次 120 秒），使用者體驗極差

---

## 備註

- `ProcessCount` 對應 AppSetting key：`BatchUpload.{TypeDef}.TaskProcessCount`，預設 `"10"`
- re-queue delay 對應 AppSetting key：`BatchUpload.BookingTime.DelaySeconds`，預設 `"10"`
- `IsBatchTaskExecuted` ExpireSeconds 對應 AppSetting key：`BatchUpload.{TypeDef}.TaskExecuted.ExpireSeconds`，預設 `"50"`
