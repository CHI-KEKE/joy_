# BatchUpload 權限管控設計分析

> 說明 `Definition Table`、`C# Enum`、`GetBatchUploadPermissionList()` 三者的關係，以及下拉選單的組成邏輯與權限設計的意圖與問題。

---

## 一、三者在下拉選單中的角色

```
C# Enum                     PermissionList                   Definition Table
────────────────────        ─────────────────────────        ──────────────────────────
BatchUploadTypeDefEnum       Dictionary<FunctionURL,           Definition_Code
  .BatchCreateBlackList        List<string>>                    = "BatchCreateBlackList"
  .ToString()               {                                 Definition_Desc
    ↓                         "/BatchUpload/BlackList"          = "批次匯入黑名單"
  "BatchCreateBlackList"        → ["BatchCreateBlackList"]    Definition_Sort
                            }                                   = 排序值
```

### 下拉選單組成流程（`GetBatchUploadTypeList()`）

```
① 取得使用者角色可存取的 FunctionURL 清單
   rolePermissionList = authService.GetRolesPermission(supplierId, rolesId, ...)
   → e.g. ["/StorePickup/FamilyShipConfirm", "/BatchUpload/BatchCreateBlackList", ...]

② PermissionList 過濾（GetBatchUploadPermissionList 是寫死的 Dictionary）
   比對使用者的 URL 清單，命中哪些 FunctionURL？
   → 收集對應的批次類型字串到 permissionList
   → e.g. ["FamilyBatchShipConfirm", "BatchPrintFamilyStoreLabel", "BatchCreateBlackList"]

③ 去 Definition Table 查顯示文字與排序
   用 permissionList 的字串比對 Definition_Code
   → 取得 Definition_Desc（中文名稱）、Definition_Sort（排序）

④ 回傳下拉選單資料
   KeyValuePairEntity { Key = "BatchCreateBlackList", Value = "批次匯入黑名單" }
```

## 二、三者各自的角色與缺一不可

| 元件 | 角色 | 缺了會怎樣 |
|------|------|-----------|
| **C# Enum** | 識別碼，`.ToString()` 產生字串作為 Key | 編譯失敗，或對應不到 |
| **PermissionList** | **門衛**：決定哪個角色能看到哪些批次類型 | 下拉選單完全看不到這個類型（任何角色都看不到） |
| **Definition Table** | **文案**：決定顯示的中文名稱與排序 | 出現在清單但顯示 null 文字，或 Definition 不存在則過濾掉 |

```
C# Enum 加了       ✅
    ↓ PermissionList 沒加 → 下拉選單空白（任何人都看不到）

PermissionList 加了  ✅
    ↓ Definition 沒 INSERT → 顯示 null 文字、排序異常

三個都加了  ✅ → 下拉選單正確顯示
```

## 三、權限管控的設計用意

### 核心思路

> **不另建「批次專屬的權限系統」，而是借用現有的「功能頁面」權限維度。**

SMS 本身已有一套 `Role → FunctionURL` 的權限系統：

```
角色 A  被允許進入 /StorePickup/FamilyShipConfirm（家樂富超取出貨確認頁面）
角色 B  不被允許
```

`GetBatchUploadPermissionList()` 的邏輯是：

> **「能操作這個功能頁面的人，就應該能使用對應的批次操作。」**

```csharp
// BatchUploadService.GetBatchUploadPermissionList()
{ "/StorePickup/FamilyShipConfirm", new List<string>
    {
        BatchUploadTypeDefEnum.FamilyBatchShipConfirm.ToString(),
        BatchUploadTypeDefEnum.BatchPrintFamilyStoreLabel.ToString()
        // ↑ 有這頁面的權限，自動獲得這兩個批次類型
    }
},
```

### 設計意圖的合理性

批次出貨確認，本質上是「在出貨確認頁面上重複做同樣的事」的自動化版本。因此：

- 管理員設定角色時，只要開放「家樂富超取出貨」功能
- 批次操作自動跟著開放
- **不需要另外設定「批次版的出貨確認」**

| 維度 | 說明 |
|------|------|
| **不是** 批次類型本身 | 沒有「能不能使用 FamilyBatchShipConfirm」這種獨立權限 |
| **而是** 業務功能頁面 | 「能不能進 /StorePickup/FamilyShipConfirm 這個頁面」 |

批次功能的存取粒度跟業務功能的存取粒度對齊，是這個設計的核心意圖。

## 四、現有設計的問題

### 問題一：映射關係寫死在程式碼裡

```csharp
// private method，不可設定，改了就要部署
private Dictionary<string, List<string>> GetBatchUploadPermissionList()
{
    return new Dictionary<string, List<string>>
    {
        { "/BatchUpload/BatchUploadSalePage", new List<string>
            { BatchUploadTypeDefEnum.SalePageCreate.ToString() }
        },
        // ... 數十筆
    }
}
```

- 新增批次類型必須改 code + 部署
- 無法從後台 DB 動態設定
- 非工程師無法維護

### 問題二：同一批次類型出現在多個 URL 下（歷史遺留）

```csharp
// 舊版 URL（仍保留）
{ "/SalesOrderSlaveStoreShippingMallListManager",
    [ FamilyBatchAllocateCode ] }

// 新版 URL
{ "/StorePickup/FamilyAllocateCode",
    [ FamilyBatchAllocateCode ] }
```

新舊頁面並存的技術債，同一批次類型被登記了兩次。有其中一個 URL 的權限就能看到批次，邏輯上重複。

### 問題三：匯出型批次的語意偏差

「操作型批次」（配號、出貨確認）的設計意圖是合理的：

```
有出貨確認頁面的權限 → 能批次出貨確認  ✅ 語意一致
```

但「匯出型批次」的語意已經偏掉：

```
有報表頁面的檢視權限 → 能觸發批次匯出  ⚠️ 語意偏差
「能看報表」≠「能觸發批次匯出作業」
```

這導致有些角色可以觸發大量資料匯出，但原本的業務意圖只是讓他「看報表」。

### 問題四：無法從 DB 查出角色的批次權限

映射只存在程式碼裡，DBA 或 PM 無法直接查：

```sql
-- 這個查詢做不到，因為映射不在 DB 裡
SELECT * FROM BatchTypePermission WHERE RoleId = @RoleId
```

只能閱讀程式碼才能知道「角色 X 能使用哪些批次類型」。

---

## 五、一句話總結

> 批次功能的使用權 = 對應業務頁面的使用權，不另建權限維度。  
> 這個設計在**操作型批次**（配號、出貨確認）上語意一致、維護合理；  
> 但在**匯出型批次**上已出現語意偏差，且整份映射寫死在 code 裡無法動態設定，是主要的技術債所在。
