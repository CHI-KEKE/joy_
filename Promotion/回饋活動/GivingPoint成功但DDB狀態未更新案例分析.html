根因判定

屬 promotionreward-investigator 已知模式一：LoyaltyPointService.ProcessRewardPointAsync 的邏輯為「先呼叫外部 GivingPoint API → 成功後才更新 DDB 狀態」，兩步之間沒有交易保護（no atomic transaction）。 當 Worker Process 在此空窗期因 NMQ 平台判定 Task 狀態異常而崩潰／重啟，外部 API 的給點副作用已真實發生， 但本地 DDB 狀態未能寫回，導致主單永遠停在 WaitToReward。

每小時執行一次的 BookingRewardLoyaltyPointsDispatcherV2Job 持續掃描到這筆 「假性待給點」記錄，不斷重新派工 → 不斷被 loyalty-api 的 api_0004 冪等保護擋下， 形成重複告警／重複執行的噪音循環，直到人工修正 DDB 記錄或訂單被取消為止。

影響評估

面向結論
財務風險 / 重複給點無風險 — 每次重派都被 loyalty-api 的訂單編號冪等保護（api_0004）擋下，會員實際只拿到一次點數。
系統噪音持續發生 — 每小時一次重派嘗試，直到 DDB 記錄被人工修正或訂單狀態改變。
資料正確性DDB 與實際情況不一致 — 會員已拿到點數，但主單狀態顯示尚未給點，可能影響後續報表/稽核判讀。

建議

  1. 短期：人工修正該筆主單 DDB 記錄（MY_Prod_Loyalty_PromotionReward，Key：10745_CrmSalesOrder:8974419 或對應 TradesOrderGroupCode），將 RewardStatus 更正為 Reward 並補上正確的 GivingPoints / TransactionCode = LT2607090400086，阻止後續重複重派。
  2. 中期：在 GivingPoint API 呼叫成功後、DDB 更新前，補上補償機制（例如先寫入中繼狀態，或憑 API 回傳的 TransactionCode 做 idempotent 補寫，而非整段流程從頭重跑）。
  3. 中期：檢討呼叫端遇到 api_0004 時是否應直接判定為終態，不需重試 3 次浪費資源。
  4. 長期：排查此類 NMQ Worker Fatal 崩潰的根本原因（Task 狀態健康檢查邏輯、逾時設定），評估是否可預防或至少確保崩潰前必要的 DDB 寫入已完成。
