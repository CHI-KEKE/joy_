# 凌晨 01:01（及其他整點尖峰）Job 大量觸發調查

> 調查日期：2026-08-25
> 調查範圍：TW Prod / HK Prod，`prod-promotion-service` namespace
> 觸發問題：是否正流程給點給券（不論線上/線下）都會固定在凌晨 01:01 booking 做 reward？

---

## 一、問題緣起

觀察到 Promotion Worker 疑似在凌晨 01:01（台北時間）固定有大量給點/給券 Job 被觸發，懷疑跟 `+N 天` 回饋活動的 `BookingTime` 計算方式有關。本文件記錄從「程式碼分析」到「Grafana Loki 實際資料驗證」的完整調查過程與結論。

---

## 二、程式碼面分析

### 2.1 相關角色與流程

```
[OrderCreated 事件 / 會員分級計算完成]
        │
        ▼
PromotionRewardBatchDispatcherV2Job  ──(建立 Task, S3Key: .../PromotionRewardBatchDispatcherV2/...)──┐
        │                                                                                              │
[每小時 CronJob 掃描 WaitToReward 補漏，schedule: "1 * * * *"（UTC 整點+1分）]                            │
        │                                                                                              │
BookingRewardLoyaltyPointsDispatcherV2Job ──(建立 Task, S3Key: .../BookingRewardLoyaltyPointsDispatcherV2Job/...)──┤
        │                                                                                              │
        │                                                                                              ▼
        │                                                                          PromotionRewardLoyaltyPointsV2Job / PromotionRewardCouponJob（真正給點/給券 Worker）
        ▼
RecycleLoyaltyPointsV2 / 退點退券流程（邏輯類似）
```

- **`BookingRewardLoyaltyPointsDispatcherV2Job`**：K8s CronJob，`Schedule: 1 * * * *`（每小時執行一次），每次撈取 `BookingTimeUTC` 落在 `ExecuteTime-1h ~ ExecuteTime`（取整點）區間、且 `RewardStatus == WaitToReward` 的 DDB 主單，依 `ShopId + MemberId + PromotionEngineId` 分組後重新建立給點/給券 Task。

  查詢邏輯（`BookingRewardLoyaltyPointsDispatcherV2Job.cs`）：
  ```csharp
  var startTime = entity.ExecuteTime.AddHours(-1).ToHour();
  var endTime = entity.ExecuteTime.ToHour();
  var records = await _promotionRewardService.GetPromotionRewardRecordByBookingTimeAsync(startTime, endTime);
  records = records.FindAll(item => item.RewardStatus == nameof(RewardStatusEnum.WaitToReward));
  ```

### 2.2 BookingTime 的計算與時分秒歸零

**線上訂單**（`EComOrderPromotionRewardCalculateService.GetRewardConditionSetting`）：
```csharp
//// 當回饋天數大於 0 時，將時分秒歸零確保日期計算的一致性
bookingTime = days > 0 ? orderTime.Date.AddDays(days) : orderTime.AddDays(days);
```

**線下訂單**（`OthersCrmSalesOrderPromotionRewardCalculateService.GetRewardConditionSetting`）：
```csharp
//// 當回饋天數大於 0 時，將時分秒歸零確保日期計算的一致性
if (rewardDays > 0)
{
    rewardDateTime = orderTime.Date.AddDays(rewardDays);
}
```

**未出貨訂單延後計算 / 訂單逆流程順延**（`LoyaltyPointService.cs` / `CouponService.cs`）：
```csharp
//// 若未完全出貨 以下時間加N天為下次執行時間
//// 若已完全出貨 以出貨時間加N天為最終給點時間
var bookingTime = isShippingCompleted ?
    slaves.Max(item => item.OrderSlaveStatusUpdatedDateTime).AddDays(record.RewardDays) :
    record.BookingTime.AddDays(record.RewardDays);

//// 將 bookingTime 的時分秒設定為 00:00:00
bookingTime = bookingTime.Date;
```

### 2.3 不受影響的情境

| 情境 | BookingTime 計算方式 | 是否會歸零 / 聚集 |
|---|---|---|
| `RewardDays = 0`（即時給點） | `bookingTime = orderTime` | 否，保留原始時間 |
| `RewardTimingType = ByDateTime`（指定日期回饋） | `bookingTime = RewardDateTime` | 否，依營運人員設定值 |
| 優惠券補發機制（`CalculateNextRetryBookingTime`） | 固定排在每日 10:00 / 22:00 | 是固定時間點，但與本次調查的 01:01 無關 |

### 2.4 初步結論（程式碼推論）

`+N 天回饋`（`RewardDays > 0`）以及繼承自它的「逆流程順延一天」情境，因為 `.Date` 歸零邏輯，會把大量不同訂單的 `BookingTime` 收斂到「當地日期 00:00:00」。換算成 UTC 後，剛好落在某個固定的 UTC 整點窗口，而每小時執行一次的 `BookingRewardLoyaltyPointsDispatcherV2Job` 掃描到該窗口時，就會把這批記錄一次性撈出並派工，形成尖峰。

## 四、總結論

1. **凌晨 01:01 固定會有大量給點/給券 Job 被觸發，此為事實，且 TW / HK 皆每天穩定重現。**
2. **根因是「+N 天回饋」活動計算 BookingTime 時，將時分秒歸零到當地日期 00:00:00」，多個不同活動的訂單因此被收斂到同一個 UTC 整點窗口，被每小時執行一次的 `BookingRewardLoyaltyPointsDispatcherV2Job`（schedule `1 * * * *`）一次性掃描並派工。**
3. **尖峰組成幾乎全為線上（ECom）訂單，並非線下訂單造成。**
4. **01:01 尖峰與 TW 另外兩個更大尖峰（10:01、22:01）是完全不同的兩批活動（PromotionEngineId）造成**，代表這是多個活動的 `RewardDays` 設定疊加後的自然結果，屬於現行設計下的結構性現象，而非單一異常活動或程式錯誤。
5. **意外發現**：活動 574730 有一張優惠券（ECouponId 1006915）庫存不足，導致相關記錄長期卡在 `WaitToReward` 並被重複重試，屬於獨立的待處理問題。

## 七、給點/給券鏈路釐清（修復方案討論前的前置確認）

在討論修法之前，先完整釐清整條鏈路的真實運作方式，確認以下理解無誤：

### 7.1 正流程鏈路（逐段確認）

```
OrderCreated
   │
   ▼
PromotionRewardBatchDispatcherV2Job 建立 PromotionRewardLoyaltyPointsV2Job(PriorityLow) Task（立即執行，非等待）
   │
   ▼
PromotionRewardLoyaltyPointsV2Job.DoJobAsync 執行試算
   │  → 計算 BookingTime（+N天回饋 → orderTime.Date.AddDays(N)，時分秒歸零成 00:00:00）
   │  → 寫入 DDB：RewardStatus = WaitToReward, BookingTime = 目標日 00:00:00
   │
   ▼
關鍵判斷（PromotionRewardLoyaltyPointsV2Job.cs 第 444 行附近）：
   if (DateTime.Now <= record.BookingTime)
   {
       "未到給點時間，不執行"
       return;  //// Task 直接結束，DDB 記錄留在 WaitToReward，不會自我重排程、不拋錯、不重試
   }
```

**確認結論：**
- 訂單建立當下 **確實會立即觸發一次** `PromotionRewardLoyaltyPointsV2Job`，但因為此時通常還沒到 `BookingTime`（例如目標是當天或未來某天 00:00），這次執行會在判斷式命中後直接 `return`，不做任何給點/給券動作。
- 這個 Task 執行完就結束了，**它本身不會自己排一個「未來 00:00 再叫醒我」的鬧鐘**。
- 記錄之後完全依賴 `BookingRewardLoyaltyPointsDispatcherV2Job`（每小時 01 分執行的 CronJob）被動掃描 `BookingDateUTC-BookingTimeUTC-index` GSI，抓出「`BookingTimeUTC` 落在前一小時整點區間、且狀態仍是 `WaitToReward`」的記錄，重新建立新 Task 觸發 `PromotionRewardLoyaltyPointsV2Job` 再跑一次——此時 `DateTime.Now > record.BookingTime` 已成立，才會真正執行給點/給券並把狀態轉為 `Reward`。

→ **「OrderCreated 時寫入 DDB、目標 0:00 生效、01:01 才被 Dispatcher 撈到執行」的理解完全正確**，這也是尖峰現象的完整成因鏈路。

### 7.2 稽核（Auditor）體系釐清 —— 不只一種，各司其職

一開始誤把 `PromotionRewardBookingTimeAuditor` 當成唯一或代表性的稽核，經完整盤點後，`AuditPromotionRewardLoyaltyPointsV2JobDIAttribute` 底下實際註冊了 6 個 Auditor：

| Auditor | 職責 | 是否依賴 BookingTime 的「值」 |
|---|---|---|
| `PromotionRewardLoyaltyPointsRecordAuditor` | 應中未中的活動、中了不應中的活動、給點總額是否正確、佔額狀態合理性 | **否**，`AuditRewardStatus` 對 `WaitToReward` 狀態明確設計為「無動作、略過」，不檢查是否逾期未轉狀態 |
| `PromotionRewardCouponRecordAuditor` | 給券版本對應邏輯 + 主單/子單狀態一致性 | **否**，唯一的時間比較（`current4AM`）是在排除「活動尚未開始」，比對的是活動 `StartDateTime`，與個別訂單 `BookingTime` 無關 |
| `PromotionRewardBookingTimeAuditor` | **驗證 DDB 現有 BookingTime 這個值本身有沒有算對**（重新按出貨狀態/RewardDays/RewardDateTime 算一次「預期值」，比對是否一致） | **是**，直接影響 |
| `PromotionRewardPerformanceAuditor` | 活動業績相關 | 否 |
| `PromotionRewardMemberAuditor` | 會員資格相關 | 否 |
| `PromotionRewardQuotaAuditor` | 佔額/名額相關 | 否 |
| `PromotionRewardBirthdayMonthAuditor` | 壽星月活動相關 | 否 |

**確認結論：**「稽核是否依據 BookingTime 判斷『該轉 Reward 卻還沒轉』」這個理解需要修正——目前 6 個 Auditor 裡**沒有任何一個**在做這件事（`WaitToReward` 狀態在給點/給券 Auditor 裡都被明確設計成略過不查）。真正跟 BookingTime 這個「時間值本身對不對」相關的，只有 `PromotionRewardBookingTimeAuditor` 一個，其他 5 個 Auditor 檢查的是「該中的活動有沒有中」「點數/券數對不對」「狀態轉換合理性」等內容，跟具體幾點鐘給獎完全無關。

### 7.3 `PromotionRewardBookingTimeAuditor` 的精度落差（未來若改 BookingTime 計算方式的風險點）

進一步拆解 `PromotionRewardBookingTimeAuditor` 內部各驗證方法對時間的比對精度：

| 方法 | 比對精度 | 是否受「小時級偏移」影響 |
|---|---|---|
| `VerifyBookingTimeForShippedOrder`（已出貨訂單） | 只比對**日期**（`BookingDate == expectedDate`），不含時分秒 | **不受影響**，同一天內加偏移仍是同一天 |
| `VerifyBookingTimeForUnshippedOrder`（未出貨訂單） | 把預期值寫死歸零成當天 `00:00:00`，只允許 **`Math.Abs(difference.TotalHours) < 1`**（±1 小時容忍度） | **會受影響 ⚠️**，一旦 BookingTime 加了超過 1 小時的偏移，`difference` 會遠超過 1 小時，**每一筆被加偏移的記錄都會被誤判為「BookingTime 驗證失敗」** |
| `VerifyBookingTimeForRewardDateTime`（指定日期回饋） | 依營運設定的 `RewardDateTime` 比對 | 不受影響（不受 `+N天` 偏移邏輯管轄） |
| `VerifyBookingTimeForInsufficientECoupon`（券不足重試） | 依 10:00/22:00 兩個固定時間點比對 | 不受影響（本來就是另一套固定時間邏輯） |

**結論：若未來實作 BookingTime 小時級偏移（方案 A），只有 `VerifyBookingTimeForUnshippedOrder` 這一支需要同步修改**——必須把「預期值寫死歸零成 00:00」的邏輯，改成呼叫跟正流程完全相同的偏移計算函式，重新算出跟正流程一致的 `expectedBookingtime`，而不是繼續假設「一定要在當天 00:00 左右」。其餘 Auditor（含 `PromotionRewardLoyaltyPointsRecordAuditor`、`PromotionRewardCouponRecordAuditor`）皆已確認不受影響，無需修改。

## 八、修復方案設計討論

### 8.1 為何「秒級/分鐘級抖動」無效

`BookingRewardLoyaltyPointsDispatcherV2Job` 撈取邏輯是**整小時桶**掃描：
```csharp
var startTime = entity.ExecuteTime.AddHours(-1).ToHour();  // 取整點
var endTime = entity.ExecuteTime.ToHour();                  // 取整點
```
只要 BookingTime 仍落在同一個小時窗口內（例如 00:00:05、00:00:30、00:59:59 都算「00:00~01:00 這桶」），秒級或分鐘級的微小抖動完全不會改變它被同一次 Dispatcher 執行一次性撈出的事實。**必須是「小時級」的偏移，才能把同一天的記錄分散到不同小時桶，被不同次的 Dispatcher 執行分批消化。**

### 8.2 方案 A：BookingTime 加確定性小時級偏移（jitter）

**設計要點：**
- 使用**穩定雜湊**（`MD5`/`SHA256`），而非 `Random` 或 C# 內建的 `string.GetHashCode()`：
  - `Random` 每次執行結果不同，同一筆訂單重算會得到不同偏移，稽核比對會失敗
  - `.GetHashCode()` 在 .NET 是「每次啟動 process 都會重新隨機化的雜湊」（string 雜湊加了隨機種子防 DoS），同一字串在不同 pod/不同次重啟算出來的值可能不一樣，不能用來做需要跨時間、跨 pod 一致的偏移計算
- Seed Key 建議使用 `PromotionEngineId + TradesOrderGroupCode`（同一筆訂單在同一活動下的組合鍵，永遠不變、跨重算保持 idempotent）
- 偏移範圍限制在 `0 ~ 1439 分鐘`（= 24hr × 60min，`1440` 這個常數即代表一天的總分鐘數），確保加在 `.Date` 歸零後的基準時間上，結果永遠落在**同一個日曆天內**，不會延誤到 N+1 天

**參考公式：**
```csharp
string seedKey = $"{promotionEngineId}_{tradesOrderGroupCode}";
using var md5 = MD5.Create();
byte[] hash = md5.ComputeHash(Encoding.UTF8.GetBytes(seedKey));
int offsetMinutes = (int)(BitConverter.ToUInt32(hash, 0) % 1440);
DateTime bookingTime = orderTime.Date.AddDays(days).AddMinutes(offsetMinutes);
```

**必要配套修改：** `PromotionRewardBookingTimeAuditor.VerifyBookingTimeForUnshippedOrder` 必須改用跟正流程完全相同的偏移公式重算 `expectedBookingtime`（詳見 7.3）。

### 8.3 方案 B：Dispatcher 端分批節流派工

不改變 BookingTime 語意，僅在 `BookingRewardLoyaltyPointsDispatcherV2Job` 掃描到大量 `WaitToReward` 記錄時，分批、間隔建立 NMQ Task，避免瞬間灌爆下游（給點/給券 API、DynamoDB 寫入）。風險最低、改動面最小，但不解決「同一時刻大量記錄堆積」的根因，只是把爆量平滑到後續幾分鐘內處理。

4. **待驗證**：本次試算樣本僅 16 筆，與實際尖峰量級（TW 01:01 尖峰約 4,400~6,800 筆/天）差距懸殊。建議後續針對量級更大的活動（如 10:01/22:01 尖峰主導活動 574730，量級上萬）重複同樣試算，驗證大樣本下 24 小時桶分布的實際標準差，以確認方案 A 在真實量級下的打散效果是否足夠，或是否需要改用「輪詢＋雜湊」混合法等更強保證的設計。

### 8.5 方案 A 的替代種子評估：能否改用 `OrderSlaveEntity.OrderGroupId` 做 mod（而非雜湊）？

**動機**：`OrderGroupId` 是資料庫遞增的 `long` 主鍵（對應 `TradesOrderGroup_Id` / `SalesOrderGroupId`），若拿嚴格遞增的數字做 `mod 24`，理論上會比 MD5 雜湊法更接近「精確輪詢」（遞增序列 mod N 天生均勻分布在 0~N-1，沒有雜湊帶來的統計噪音，8.4 節提到的小樣本聚集問題可望避免）。

**實際檢查發現：`OrderGroupId` 在關鍵資料路徑上未被填值，不可用。**

檢查了組出 `OrderSlaveEntity` 的兩個 Repository：

| Repository | 用途 | `OrderGroupId` 是否填值 |
|---|---|---|
| `TradesOrderRepository.cs`（WebStore DB，`OrderPlaced` 事件用） | `OrderGroupId = orderGroup.TradesOrderGroup_Id` | ✅ 有填值 |
| `SalesOrderRepository.cs`（ERP DB，`GetSalesOrderSlavesAsync`，**`EComOrderPromotionRewardCalculateService` 實際呼叫的路徑**） | 完全沒有 `OrderGroupId = ...` 這一行 | ❌ **未填值，C# 預設為 0** |

**結論：`OrderGroupId` 在系統實際呼叫最頻繁的路徑（`GetSalesOrderSlavesAsync`）上永遠是 `0`。** 若直接拿 `OrderGroupId % 24` 當偏移小時，這條路徑上所有訂單都會算出同一個偏移值（`0 % 24 = 0`），**完全沒有打散效果，甚至比現行 `.Date` 歸零問題更嚴重**（因為連現行方案偶然造成的跨天自然差異都沒有了）。這不是「統計效果好不好」的問題，而是「資料本身在此路徑就拿不到」的資料完整性問題，因此**不建議採用 `OrderGroupId` 作為 mod 種子**。

**若堅持採用「遞增數字 mod」而非雜湊法**，需要先確認：
- 是否存在一個在**所有**訂單來源（線上 ECom 的 `TradesOrderRepository` 路徑 + `SalesOrderRepository` 路徑 + 線下 CRM 訂單）都保證有值、且穩定遞增的欄位
- 目前看到比較有機會的候選是 `OrderSlaveId`（對應 `TradesOrderSlave_Id`，兩條路徑皆有填值），但仍要注意：同一筆訂單若有多個子單（`OrderSlaveId` 不同），同一筆給點記錄若依不同子單的 `OrderSlaveId` 算出的偏移可能不一致，需固定挑選規則（如「取第一個子單」）確保 idempotent，此點尚待進一步查證與驗證

**相較之下，8.2 節提出的 `MD5(PromotionEngineId + TradesOrderGroupCode) mod 1440` 之所以選這兩個欄位當種子，正是因為它們是 DDB 主鍵的一部分（`PromotionEngineId_TradesOrderGroupCode`），保證在稽核、正流程、任何重算路徑下都 100% 有值且不變，不會有「某條路徑未填值」的資料完整性風險**——這是選定 seed key 時的重要考量，優先度高於「用遞增數字理論上分布更均勻」這個統計上的優點。

### 8.6 根因完整盤點：`.Date` 歸零共有 4 個出處（線上/線下、初次計算/延後重算皆需同步修改）

原先只聚焦在「正流程初次計算」，實際盤點後發現整個系統共有 **4 個獨立的 `.Date` 歸零出處**，且都必須同步套用方案 A，否則會有漏改的路徑繼續產生尖峰：

| # | 出處 | 情境 | 檔案/方法 |
|---|---|---|---|
| 1 | 線上訂單初次計算 | ECom 訂單成立時計算 BookingTime | `EComOrderPromotionRewardCalculateService.GetRewardConditionSetting` |
| 2 | 線下訂單初次計算 | CRM/Others 訂單成立時計算 BookingTime（**先前誤判「線下 RewardDays 通常設0不受影響」，已更正，見下方 8.6.1**） | `OthersCrmSalesOrderPromotionRewardCalculateService.GetRewardConditionSetting`（約667~712行） |
| 3 | 已出貨延後給點重算 | 訂單出貨後才重新計算 BookingTime | `LoyaltyPointService.cs`（約970~985行） |
| 4 | 已出貨延後給券重算 | 同上，給券版本 | `CouponService.cs`（約1540~1560行附近） |

#### 8.6.1 更正：線下訂單一樣會有 +N 天 BookingTime 聚集問題

先前討論中誤以為「線下訂單（`Others`）通常 `RewardDays=0`，不受影響」，這只是**特定活動設定值恰好為0的偶然結果**，並非機制本身不支援 +N 天。實際查看 `OthersCrmSalesOrderPromotionRewardCalculateService.GetRewardConditionSetting`（約684~702行）：

```csharp
var rewardDays = crmOrderCondition.RewardDays;
...
else
{
    //// 當回饋天數大於 0 時，將時分秒歸零確保日期計算的一致性
    if (rewardDays > 0)
    {
        rewardDateTime = orderTime.Date.AddDays(rewardDays);   // ← 跟線上訂單完全相同的歸零邏輯
```

#### 8.6.2 出貨延後給點/給券（出處 #3、#4）同樣需要修改

`LoyaltyPointService.cs`、`CouponService.cs` 中「已出貨後才延後計算 BookingTime」的邏輯，同樣採用 `.Date` 歸零 + `AddDays` 的算法，跟正流程初次計算完全同構，**必須同步套用方案 A**，否則這兩條路徑仍會繼續產生尖峰。

**好消息**：對應的稽核 `VerifyBookingTimeForShippedOrder`（已出貨稽核）只比對「日期」不比對「時分秒」，**套用方案 A 後不受影響、不需修改**。

### 8.7 10:01 / 22:01 尖峰的真正根因：與 +N天回饋無關，是「優惠券庫存不足」的獨立重試機制

深入追查 TW 10:01/22:01 兩個尖峰時，發現它們**不是** +N天回饋 `.Date` 歸零造成的（那只會產生單一整點尖峰，例如 01:01），而是完全獨立的另一套機制：

**`CouponService.CalculateNextRetryBookingTime`（約1332~1358行）**：當優惠券庫存不足、無法立即發券時的專屬重試排程邏輯，**寫死只有兩個固定時間點**：

```csharp
// 邏輯示意：若目前時間 < 10:00，下次重試訂在當天10:00；
// 若目前時間 >= 10:00 且 < 22:00，下次重試訂在當天22:00；
// 若目前時間 >= 22:00，下次重試訂在隔天10:00
```

也就是說，任何時間點發生「券不足」都只會被排到 **10:00 或 22:00** 這兩個僅有的重試槽位，時間一到，Dispatcher 掃描到的所有這類記錄自然會全部集中在同一時刻觸發，形成 10:01/22:01 尖峰。**這與 +N天回饋的 `.Date` 歸零問題是兩套完全不同、各自獨立的根因，必須分開設計修復方案。**

對應稽核 **`VerifyBookingTimeForInsufficientECoupon`**（約164~206行）也是用這兩個固定時間點做精確比對，若修改 `CalculateNextRetryBookingTime` 要同步修改此稽核的預期值邏輯。

**打散建議**：在 `10:00`/`22:00` 基準上疊加一個較小範圍的偏移（例如 0~120 分鐘內，2 小時封頂），避免偏移過大跨越到下一個重試窗口（`22:00`）造成語意錯亂（本來預期「10點重試」卻被打散到超過22點才重試，等同延遲了一整個重試週期）。是否要對此機制也做 3 包/N 包拆分，或維持獨立設計，屬於待決策事項（見 8.9）。

### 8.8 NMQ Worker 平行消費模型：解釋「為何 Job 量暴增會直接反映在記憶體/HPA，而非被排隊攤平」

有一個常見疑問：「BookingDispatcher 一次建立大量 Task，應該只是排隊慢慢處理，不會造成記憶體飆升或 OOM 吧？」——實際查證後，答案是**不成立**，原因如下：

1. **NMQ Worker 不是單執行緒序列消費**：Worker 內部用 process pool 方式，同時開多條執行緒各自去撈 Task 執行；加上 K8s 這層本身是 **2～4 個 Pod**（`autoscaling.enabled: true, minReplicas: 2, maxReplicas: 4`，見 `charts/promotion-console-nmqv3worker-group4/values-tw-prod.yaml`）同時在跑，所以任務會被平行、非序列地消化。
2. **Dispatcher 是「先撈全部、一次性建立」，不是邊建立邊限流**：`BookingRewardLoyaltyPointsDispatcherV2Job.ProcessAllMemberGroupsAsync` 用 `foreach` 迴圈把所有符合條件的訂單一次性組成 `CreateTaskRequest` 全部送出建立 Task，沒有分批延遲送出的機制。Dispatcher 觸發瞬間，Queue 裡一口氣多出大量待執行任務，會被多執行緒/多 Pod 立即盡量平行吃掉。
3. **記憶體暴增＝平行任務數暴增的直接結果**：每個給點/給券 Task 執行中都要載入訂單、活動規則、DB context 等物件，同時間活著的 Task 數量越多，記憶體佔用就越高。這解釋了記憶體曲線「瞬間衝高、15~20分鐘內回落」的型態——正是 Queue 堆積的大量 Task 被平行執行完畢、逐漸清空的過程。
4. **HPA 自動擴容進一步證實「平行度暴增」而非「排隊」**：若真的是排隊慢慢處理，CPU/記憶體應維持平穩，不會觸發 HPA。實際觀測到尖峰時 Pod 數從 2 台被動態拉升到 4 台，代表系統偵測到當下平行工作負載已超過現有資源，才會擴容。

**結論**：方案 A（BookingTime 分桶打散）之所以有效，不是讓 Dispatcher 排隊慢慢送出去，而是**從源頭減少同一時刻需要平行處理的任務數量**，讓每個時間桶對應的任務數變少、平行負載峰值降低。

### 8.9 最終方案定案：拆成 3 包（0:00 / 1:00 / 2:00），使用可配置桶數的雜湊分桶設計

**決策結果**：不採用 8.2 節「1440 分鐘全天雜湊」或後續討論的「720 分鐘半天雜湊」，改為更單純的**「拆成 3 個固定整點桶：0:00、1:00、2:00」**設計，理由：
- 比分鐘級雜湊更簡單、更容易驗證與稽核
- 對「單一整點暴增 3~4 倍」的現況而言，打散成 3 份已足夠有感降低尖峰負載
- 保留未來彈性：桶數設計為可配置參數，之後要改成 4 包或更多包時，只需調整設定值，不需改動核心演算法

#### 8.9.1 共用 Helper 設計（`BookingTimeJitterHelper`）

```csharp
public static class BookingTimeJitterHelper
{
    /// <summary>
    /// 依 seedKey 將 BookingTime 分散到 [0, bucketCount) 個整點桶，避免大量訂單集中在同一時間點觸發。
    /// </summary>
    /// <param name="dateOnlyBase">已歸零的日期基準（如 orderTime.Date.AddDays(rewardDays)）</param>
    /// <param name="seedKey">訂單唯一識別鍵，建議用 PromotionEngineId_TradesOrderGroupCode</param>
    /// <param name="bucketCount">要拆成幾個時間桶，預設3（0:00/1:00/2:00）；未來要拆4包只需改這個值</param>
    /// <param name="startHour">起始小時，預設0</param>
    public static DateTime ApplyHourBucket(
        DateTime dateOnlyBase,
        string seedKey,
        int bucketCount = 3,
        int startHour = 0)
    {
        if (bucketCount <= 0)
        {
            throw new ArgumentOutOfRangeException(nameof(bucketCount), "桶數必須大於0");
        }

        var bucketIndex = GetBucketIndex(seedKey, bucketCount);
        return dateOnlyBase.Date.AddHours(startHour + bucketIndex);
    }

    /// <summary>
    /// 純計算 bucket index，方便 Auditor 端重算比對用，不必重複實作雜湊邏輯。
    /// </summary>
    public static int GetBucketIndex(string seedKey, int bucketCount)
    {
        using var md5 = MD5.Create();
        var hash = md5.ComputeHash(Encoding.UTF8.GetBytes(seedKey));
        return (int)(BitConverter.ToUInt32(hash, 0) % (uint)bucketCount);
    }
}
```

- `bucketCount` 建議搭配 `settings.json` 做外部設定（例如 `_N1CONFIG:PromotionReward:BookingTimeJitterBucketCount`），未來調整桶數不必改程式碼、重新編譯
- 正流程（4個 `.Date` 歸零出處）與 Auditor（`VerifyBookingTimeForUnshippedOrder`、`VerifyBookingTimeForInsufficientECoupon` 等）**共用同一個 `GetBucketIndex`**，只要兩邊都讀同一份 config，Auditor 重算出來的 expected 值永遠跟正流程一致，不會有「改了桶數卻漏改另一邊」的風險

#### 8.9.1.1 補充說明：`BitConverter.ToUInt32(hash, 0)` 在做什麼，Hash 本質是什麼

**MD5 雜湊的本質：是一串「位元組（bytes）」，不是數字。**

`MD5.ComputeHash()` 回傳的 `hash` 是一個 **`byte[]`（byte陣列）**，固定長度 **16 bytes（128 bits）**，本質上是一串看似隨機的二進位資料，不是數字。人類常看到的「32碼十六進位字串」（如 `d41d8cd98f00b204e9800998ecf8427e`）只是這16個byte各自轉成2位16進位字元、串接起來的**人類可讀呈現方式**，程式內部處理的仍是原始的 `byte[]`。

`BitConverter.ToUInt32(hash, 0)` 的意思是：**只取這16個byte裡的「前4個byte」（從index 0開始），把它們重新詮釋（reinterpret）成一個 `uint32`（無號32位元整數，範圍 0 ~ 4,294,967,295）。**

```csharp
BitConverter.ToUInt32(hash, 0)
//                     ^^^^  ^
//                     陣列   從第0個位置(index)開始取4個byte
```

實際驗證（`592364_YSS00121987` 的MD5前4個byte為 `81-13-05-5C`）：
```
前4個byte: 81-13-05-5C -> uint32 = 1543836545
```
這正好對應 8.9.4 節試算表裡該筆訂單的雜湊值 `1543836545`。

**為什麼只取前4個byte，不是全部16個byte？**
- 16 bytes = 128 bits 太大，C# 沒有原生型別能直接裝下（需用 `BigInteger`），且做 `mod` 運算沒必要這麼複雜
- `uint32`（32 bits，最大約43億）已經遠遠超過分桶所需的隨機性/均勻度，不需要動用完整128位元
- 選哪4個byte不重要（前4個、後4個、中間4個皆可），因為MD5每個byte都已經是雪崩效應後的結果，本身就具備隨機分佈特性，選「前4個（index 0）」只是最簡單常見的寫法慣例

**關於 Endianness（位元組順序）的補充**：`BitConverter.ToUInt32` 的轉換結果會受 CPU 架構的大小端序影響（可用 `BitConverter.IsLittleEndian` 檢查），但這對本方案用途沒有影響——只要同一套程式碼、同一種容器架構（.NET Docker容器在 x86/ARM 上皆為 Little-Endian）執行，永遠用同一種方式轉換，同一個 `seedKey` 永遠得到同一個 `uint32`，滿足 deterministic 特性的要求。

#### 8.9.1.2 ⚠️ 重要實作陷阱：務必先在 `uint` 型別下做 `%` 運算，再轉型成 `int`，否則會因溢位產生負數桶號

**實測重現的 bug**：若寫成先把 `uint32` 轉型成 `int`、再做 `%` 運算，會因整數溢位（overflow）得到負數結果：

```csharp
// ❌ 錯誤寫法：先轉 int 才做 %，可能得到負數桶號
var hashInt = (int)BitConverter.ToUInt32(hash, 0);
var modResult = hashInt % 3;   // 實測結果：可能得到 -2、-1 等負值！
```

**原因**：`BitConverter.ToUInt32` 回傳的是 **`uint`（無號，範圍 0 ~ 4,294,967,295）**，強制轉型成 **`int`（有號，範圍 -2,147,483,648 ~ 2,147,483,647）** 時，若原始值超過 `int.MaxValue`（約21.4億），轉型後會變成負數（兩者底層都是32個bit，只是最高位元從「數值位元」被重新解讀成「符號位元」）。且 **C# 的 `%` 運算子其實是 remainder（餘數）運算，不是數學上「永遠非負」的 mod 運算**，對負數取模，結果符號會跟著被除數（也就是原本溢位變負的那個數）走，因此可能產生負的桶號，導致 `AddHours(startHour + bucketIndex)` 算出離譜的結果（甚至跑到前一天）。

**實測驗證**（字串 `28343_TG20193021`）：
```
MD5前4byte轉出的 uint32 = 4,273,969,079   （超過 int.MaxValue = 2,147,483,647）
強制轉型 (int) 後        = -20,998,217     （溢位變負數）
C# 對負數取模: -20,998,217 % 3 = -2         （負的桶號！）
```

**正確寫法：務必在 `uint` 型別下先做完 `%` 運算，此時結果必然落在 `0 ~ bucketCount-1` 之間（非負），最後才轉型成 `int`：**

```csharp
// ✅ 正確寫法：先在 uint 下做 % (uint)bucketCount，結果已收斂到非負範圍，最後才轉 int
var bucketIndex = (int)(BitConverter.ToUInt32(hash, 0) % (uint)bucketCount);
```

8.9.1 節 `BookingTimeJitterHelper.GetBucketIndex` 的實作已採用此正確寫法，**這是實作時非常容易踩到的陷阱，Code Review 與單元測試時應特別針對「大量不同 seedKey，驗證 bucketIndex 永遠落在 `[0, bucketCount)` 範圍內、不會出現負數」寫測試案例覆蓋。**

#### 8.9.3 為什麼「訂單成立時間相近」不影響分桶均勻度

分桶依據是 **`seedKey`（訂單唯一識別碼）**，不是訂單時間本身。MD5 雜湊具有「雪崩效應」：輸入只要有一個字元不同，輸出雜湊值就會劇烈跳動、呈現隨機性，且雜湊值本身跟時間毫無關聯。

實際驗證（訂單號只差最後一碼）：

| TG碼 | 雜湊值(uint32) | mod3(桶) |
|---|---|---|
| `592364_YSS00121987` | 1,543,836,545 | 2 |
| `592364_YSS00121988` | 719,359,466 | 2（與上者恰巧同桶，屬機率巧合） |
| `592364_YSS00121989` | 77,901,321 | 0 |

即使 100 筆訂單都在同一秒鐘內成立，只要各自訂單號不同，雜湊出來的 bucket index 在統計上就會均勻散佈在 0/1/2 三桶，跟成立時間完全解耦。**反之，若改用「訂單時間本身做 mod」（例如秒數 mod 3）才會有問題**——時間相近甚至相同的訂單，算出的 mod 值會全部一樣，完全無法打散，這正是選用「雜湊訂單唯一鍵」而非「時間做mod」的關鍵原因。

（雜湊分桶保證的是「統計上均勻」而非「絕對均勻」：樣本數小時可能出現分佈不均的情況，屬正常統計波動；訂單數夠多時大數法則會讓桶數趨近 1/3、1/3、1/3。）
