# 付款前取消 — 績效稽核誤判

## 問題描述

線上佔額活動（RewardReachPriceWithCoupon / RewardReachPriceWithPoint2）的訂單，若使用者在付款前就取消（或付款失敗），Slack 會跳出以下稽核警報：

```
給券紀錄稽核監控到異常
市場環境: MY-Prod
TG Code: MG260420R00006
稽核到下列異常:
活動10459 查無活動成效紀錄
```

這是一個**結構性的必然誤報**，並非真實異常。

---

## 根本原因

### 佔額活動的狀態生命週期

線上佔額活動訂單有兩條路徑：

```
路徑 A（付款成功）：Occupy → WaitToReward → Reward
路徑 B（付款前取消）：Occupy → Cancel
```

Performance 紀錄（`NineYiDW.PromotionEnginePerformance`）**只在付款後**才會被建立：

- `PromotionRewardCouponJob.ProcessRewardStateAsync`
  - **Point 1**：record == null，非佔額活動（或線下佔額），計算符合後立即建立 Performance NMQ
  - **Point 2**：record.RewardStatus == Occupy，線上佔額活動付款後 Occupy → WaitToReward，才建立 Performance NMQ

因此路徑 B（付款前取消）**從未建立 Performance 紀錄**，這是正常設計行為。

### `Cancel` 的三個來源

| 來源 | 觸發事件 | 設定位置 |
|-----|---------|---------|
| ① 使用者取消訂單 | 訂單取消 | `CouponService.cs` L1590 |
| ② 付款失敗（OrderFailed） | 金流失敗 | `PromotionRewardOccupyDispatcherJob` L388 / L413 |
| ③ 付款後重算不符合 | `ProcessRewardStateAsync` | `CouponService.cs` L869 |

來源 ①② 皆為**付款前取消**，不會建立 Performance。  
來源 ③ 為**付款後取消**，Performance 應已存在，值得稽核。

### 稽核白名單設計缺陷（修正前）

`PromotionRewardPerformanceAuditor._whitelistStatuses` 原本包含 `Cancel`：

```csharp
private HashSet<string> _whitelistStatuses = new HashSet<string>(StringComparer.OrdinalIgnoreCase)
{
    nameof(RewardStatusEnum.WaitToReward),
    nameof(RewardStatusEnum.Reward),
    nameof(RewardStatusEnum.Cancel)   // ← 未區分付款前後取消
};
```

白名單未區分來源 ①②（付款前）與來源 ③（付款後），導致所有 Cancel 紀錄都被稽核，路徑 B 的訂單必然查無 Performance → 每次都誤跳。

## 稽核觸發機制

### 完整觸發鏈

```
外部排程（每小時 :01）
    ↓ 建立 NMQ
AuditPromotionRewardLoyaltyPointsDispatchV2Job
    ↓ GetWaitToAuditSalesOrderGroupAsync(executeTime)
    ↓ startTime = executeTime.ToHour().AddHours(-2)
    ↓ endTime   = startTime.AddHours(1)
    ↓ 查詢範圍：[executeTime 整點 - 2h, executeTime 整點 - 1h] 的訂單
    ↓ 依訂單的活動類型分流：
    有給點活動 → AuditPromotionRewardLoyaltyPointsV2Job（每筆訂單一個 NMQ）
    有給券活動 → AuditPromotionRewardCouponJob          （每筆訂單一個 NMQ）
    （同一筆訂單可能同時建立兩種）
        ↓
    AuditPromotionRewardCouponJob / AuditPromotionRewardLoyaltyPointsV2Job
        ↓ 執行多個 IPromotionRewardRecordAuditor，其中包含：
        ↓ PromotionRewardPerformanceAuditor
```

### 時間窗口說明

| executeTime | 查詢 startTime | 查詢 endTime | 受稽核訂單年齡 |
|---|---|---|---|
| 14:00:00 | 12:00 | 13:00 | 1~2 小時 |
| 14:30:00 | 12:00 | 13:00 | 1.5~2.5 小時 |
| 14:59:59 | 12:00 | 13:00 | 2~3 小時 |

**訂單成立後約 1~3 小時內會被稽核到。**

### 佔額與稽核的時序關係

```
T+0:00  訂單成立
         └─ EDA OrderPlaced → PromotionRewardOccupyDispatcherJob
              └─ 建立 DDB 紀錄，RewardStatus = Occupy

T+X     使用者付款 → RewardStatus = WaitToReward，建立 Performance NMQ
   或   使用者取消 / 付款失敗 → RewardStatus = Cancel（無 Performance）

T+1~3h  稽核執行（依訂單成立時間切窗口）
         └─ 舊邏輯：Cancel 在白名單 → 稽核 → 查無 Performance → ❌ 誤跳
         └─ 新邏輯：Cancel 且付款前取消 → 不稽核 → ✅ 正確跳過
```

## 修正方案

### 修改目標

`PromotionRewardPerformanceAuditor.cs`  
路徑：`src/Nine1.Promotion.Console.BL/Services/PromotionReward/Auditors/`

### 修正邏輯

利用 `RewardHistoryList` 歷程判斷 Cancel 是否為付款後取消：

```
付款前取消 → history: [ Cancel ]                        → 不稽核 Performance ✅
付款後取消 → history: [ WaitToReward, Cancel ]           → 稽核 Performance  ✅
給獎後取消 → history: [ WaitToReward, Reward, Cancel ]   → 稽核 Performance  ✅
```

**關鍵依據**：`RewardHistoryList` 在 DDB 是**同步寫入**（每次狀態更新即 append），可安全作為「是否曾付款」的判斷依據，不受 Performance NMQ 非同步執行影響。

### 主要變更

```csharp
// 1. 移除 Cancel，改為 readonly
private readonly HashSet<string> _whitelistStatuses = new HashSet<string>(StringComparer.OrdinalIgnoreCase)
{
    nameof(RewardStatusEnum.WaitToReward),
    nameof(RewardStatusEnum.Reward),
};

// 2. 新增已付款狀態集合
private readonly HashSet<string> _postPaymentStatuses = new HashSet<string>(StringComparer.OrdinalIgnoreCase)
{
    nameof(RewardStatusEnum.WaitToReward),
    nameof(RewardStatusEnum.Reward),
};

// 3. Where 子句加入 Cancel 的細分條件
.Where(item => this._whitelistStatuses.Contains(item.RewardStatus) ||
               (nameof(RewardStatusEnum.Cancel).Equals(item.RewardStatus, StringComparison.OrdinalIgnoreCase) &&
                this.IsPostPaymentCancel(item.RewardHistoryList)));

// 4. 新增輔助方法
private bool IsPostPaymentCancel(IEnumerable<PromotionRewardHistoryBaseEntity> historyList)
{
    return historyList.Any(h => this._postPaymentStatuses.Contains(h.RewardStatus));
}
```

## 影響範圍

`PromotionRewardPerformanceAuditor` 被以下 4 個 Job 注入，**一次修改，全部受益**：

| Job | 訂單類型 | 獎勵類型 |
|-----|---------|---------|
| `AuditPromotionRewardCouponJob` | 線上 | 給券 |
| `AuditPromotionRewardLoyaltyPointsV2Job` | 線上 | 給點 |
| `AuditCrmOthersOrderPromotionRewardCouponJob` | 線下 | 給券 |
| `AuditCrmOthersOrderPromotionRewardLoyaltyPointsV2Job` | 線下 | 給點 |

> **線下訂單補充**：線下訂單無佔額流程，Cancel 不會有 Occupy → Cancel 路徑，  
> `IsPostPaymentCancel` 對線下 Cancel 回傳 false，行為正確，無副作用。

## 修正後的稽核行為對照

| 情境 | 修正前 | 修正後 |
|-----|:---:|:---:|
| 付款前取消（Occupy → Cancel） | ❌ 誤跳 | ✅ 不稽核 |
| 付款失敗（OrderFailed → Cancel） | ❌ 誤跳 | ✅ 不稽核 |
| 付款後取消（WaitToReward → Cancel） | ✅ 正確稽核 | ✅ 正確稽核 |
| 正常完成（WaitToReward / Reward） | ✅ 正確稽核 | ✅ 正確稽核 |

## Race Condition 風險評估

**情境**：付款後取消，但 Performance NMQ 尚未執行完畢，稽核就已觸發。

| 評估項目 | 結論 |
|---------|------|
| 正常情況 | Performance NMQ 通常幾分鐘內完成，稽核在 1~3 小時後才執行，**不會發生** |
| NMQ 積壓嚴重 | 稽核觸發時 Performance 尚未寫入 → 短暫誤跳，下一輪稽核恢復正常，可接受 |
| Performance NMQ 執行失敗 | Performance 永遠不寫入 → 稽核正確 alert，**這才是真實異常** |

`RewardHistoryList`（同步寫入）與 Performance（非同步 NMQ）是獨立機制，  
`IsPostPaymentCancel` 的判斷不受 NMQ 執行進度影響。
