# 定期購機制分析（mweb 前台）

> 專案路徑：`C:\91APP\nineyi.webstore.mobilewebmall`
> 分析日期：2026-05-14

---

## 一、定期購是什麼概念？

定期購（RegularOrder）是一種「訂閱制購物」機制：

- 消費者首次購買時授權信用卡，同意按固定週期自動扣款出貨
- 商店不需要每次等消費者回來下單，系統自動建立後續訂單
- 類似訂閱制服務（Netflix、雜誌），但對象是實體商品

---

## 二、前置條件（商店後台要設定的事）

商店在後台必須做兩件事：

1. **商品 ShippingType 設為 RegularOrder（= 7）**
   - 把商品標記為定期購類型
2. **建立 `RegularOrderSettingEntity`（定期購設定）**
   - 可選的配送週期清單（如每 7 / 14 / 30 天）
   - 最大配送次數 `MaxDeliverCount`（0=無限、1=只買一次）
   - 供應商（`Nine1` 或 `GameBall`）

---

## 三、消費者購買流程（首購）

```
商品頁看到定期購標示
    ↓
加入購物車
    ↓
購物車選配送週期（如每 30 天）& 配送次數
    ↓
結帳頁勾選「同意定期購條款」(regularOrderForm.tsx)
    ↓
送出結帳
    ↓
系統建立 TG/TM/TS（訂單）+ RegularOrder（訂閱合約）
```

**特殊情況：**  
若 `MaxDeliverCount = 1`（只買一次），雖走定期購商品頁，但 TS 的 `ShippingTypeDef` 會被強制改回 `1`（一般商品），且不建立 RegularOrder 合約記錄。

## 五、TG / TM / TS 與一般商品的差異

**TG（TradesOrderGroup）**：無差異

**TM（TradesOrder）**：無差異

**TS（TradesOrderSlave）差異：**

| 欄位 | 一般商品 | 定期購商品 |
|------|----------|------------|
| `TradesOrderSlave_ShippingTypeDef` | `1`（Normal） | **`7`（RegularOrder）** |
| `TradesOrderSlave_ShippingDate` | 依商品設定 | **硬設為 `DateTime.Now + 2天`** |
| `TradesOrderSlave_StatusDef` | Finish | Finish（同） |
| `TradesOrderSlave_IsClosed` | true | true（同） |

**首購後額外動作：**  
`CreateRegularOrderProcessor` 另外插入一筆 `RegularOrder` 設定記錄（非 TS，是獨立 table），記錄信用卡 token、下次出貨日、配送週期、狀態。

## 六、RegularOrder Table：為什麼需要獨立 Table？

### 核心概念：TG/TM/TS 代表「這一筆交易」，RegularOrder 代表「這份訂閱合約」

```
RegularOrder #1001（每 30 天送一次，共 6 次）
  ├── 第 1 次出貨 → TG / TM / TS（1 月）
  ├── 第 2 次出貨 → TG / TM / TS（2 月）
  ├── 第 3 次出貨 → TG / TM / TS（3 月）
  └── ... 直到第 6 次或消費者取消
```

一個 RegularOrder → 多筆 TG/TM/TS（1 對多關係）

### 獨立 Table 的三個核心用途

| 用途 | 說明 |
|------|------|
| **存跨訂單的合約資訊** | 信用卡 token（每次自動扣款用）、下次出貨日（排程用）、配送週期 |
| **狀態管理** | `Ordering`（訂閱中）/ `Cancel`（已取消）；排程系統掃此 table 觸發出貨 |
| **消費者管理頁顯示** | 前台「定期購管理頁」顯示訂閱狀態、下次出貨日、商品資訊 |

TG/TM/TS 完成後就 `IsClosed=true` 了，不適合做持續追蹤。

## 七、信用卡 Token 機制

### 為什麼有 Token？

PCI DSS 法規明確規定：**商家不能直接儲存完整卡號（16位）、CVV、到期日**。

**Tokenization（代碼化）流程：**
```
消費者輸入卡號 16 碼
    ↓ 直接傳給金流服務商（TapPay / Stripe 等）
    ↓ 卡號永遠不經過 91APP 的伺服器
金流服務商回傳一組 token（亂碼字串）
    ↓
91APP 只存這個 token（存在 RegularOrder.CheckoutInfo）

下次自動扣款：
    91APP 拿 token → 傳給金流服務商 → 金流服務商查對應卡號 → 扣款
```

**一般購物 vs 定期購：**

| 購物類型 | 卡號處理 |
|---------|---------|
| 一般購物 | 消費者每次自己輸入，當場扣款，不儲存任何東西 |
| 定期購 | 需儲存 token，因為後續要在「消費者不在場」時自動扣款 |

**各市場 Token 格式差異：**

| 市場 | 金流服務商 | CheckoutInfo 內容 |
|------|-----------|-------------------|
| TW | TapPay / Nine1Payment | 卡號 token |
| MY | Razer | credit card token + email + phone + name |
| HK | Stripe | customer_id + payment_method_id |

## 八、供應商（Provider）：Nine1 vs GameBall

**Provider = 負責定義「定期購規則與週期」的服務來源**

是誰幫商店管理「定幾天配一次、配幾次、什麼條件終止」這套規則。

### Nine1（91APP 自有）

| 項目 | 說明 |
|------|------|
| 週期設定來源 | 直接存在 mweb DB（`RegularOrderSettingEntity`） |
| 獲取方式 | 直接從 DB 讀，**不打外部 API** |
| 次數限制 | 簡單：`MaxDeliverCount=0`（無限）或 `=1`（僅一次） |

### GameBall（第三方玩子遊戲化訂閱平台）

| 項目 | 說明 |
|------|------|
| 週期設定來源 | 呼叫 GameBall 外部 API（`/api/GetRegularSetting`），帶 `x-api-key` 驗證 |
| 返回資料 | `DeliverPeriodList`、`MaxDeliverCount`、`SalePageOption`、`LimitationType` |
| 次數限制 | 進階三種：`Unlimited`（無限）/ `CustomerSelectable`（消費者自選）/ `FixedCount`（固定次數）|

**自動續訂時：**  
`GetRegularOrderProcessor` 對 GameBall 走不同分支（直接從 ShoppingCartNode mapping 而非 DB），因為 GameBall 自己管合約資料。

## 九、「只買一次」選項的用途

`RegularOrderOptionEnum.BuyOnce = 2`（定期購僅購買一次）

**為什麼有這個看起來矛盾的選項？**

### 場景一：商品頁同時賣「定期購」和「一次性」

商店在同一個商品頁提供兩種選擇：
```
[選項 A] 定期購（每 30 天送一次，自動扣款）
[選項 B] 一般購買（只買這一次）
```
消費者選 BuyOnce 走相同的 checkout 流程，但結帳時不建立 RegularOrder 設定，TS 的 `ShippingTypeDef` 回到 `1`（一般商品）。

### 場景二：MaxDeliverCount = 1（試用訂閱）

消費者簽訂合約，系統自動執行一次就結束，後續不再續訂。

**本質上：** 定期購 UI 流程（綁卡 / 選週期）有商業價值，即使一次性也借用這套流程，方便未來升級轉成真正定期購。

## 十、自動續訂觸發方式

### 觸發入口（mweb WebAPI）

```csharp
// 新版
POST WebAPI/TradesOrderV2/SubscriptionOrderAutoGen

// 舊版
GET  tradesOrderLite/RegularOrderAutoGen?shopId=x&memberId=x&regularOrderId=x
```

這兩支 API 是**被外部系統主動呼叫**的，呼叫者才是真正的排程觸發器（可能是 Commerce Worker 或獨立 CronJob，需查該專案確認）。

### 防重複機制

`TraceId` + `RegularOrderTracing` table：
1. 插入 `RegularOrderTracing`（pending）
2. 執行 `GetPayProcessContextForRegularOrder`
3. 更新 `RegularOrderTracing`（success / fail）

### 自動續訂呼叫鏈

```
外部系統（Commerce Worker / CronJob）
    ↓ POST SubscriptionOrderAutoGen（含 RegularOrderId）
mweb WebAPI TradesOrderV2Controller
    → InsertRegularOrderTracing（pending）
    → TradesOrderService.GetPayProcessContextForRegularOrder()
        → ShoppingCartV2Service.GetShoppingCartContextForRegularOrder()
            → GetRegularOrderProcessor（從 RegularOrder DB 組仿購物車結構）
        → PayProcessService.GetProcessContextForRegularOrderPay()
    → PayProcessService.CreateTradesOrder()
        → Processor Pipeline（建 TG/TM/TS）
        → CreateRegularOrderProcessor（IsInternalSource=true → 直接 return，不重複建合約）
    → UpdateRegularOrderTracing（success / fail）
```

## 十一、Shopping / Cart 在定期購方面的處理

### Shopping 專案
幾乎沒有定期購特殊處理，純 pass-through。

### Cart 專案（有三個特別處理）

| 處理 | 說明 |
|------|------|
| `RegularOrderService` | 商品加入購物車時，呼叫 `RegularPurchaseWebApi` 取得商品頁定期購選項（週期清單 / 次數限制） |
| `ArrangeUnallowedRegularOrderSalePageListProcessor` | APP 結帳若商店開啟 `MaskUnallowedRegularOrderSalePageSwitch`，自動排除定期購商品（法規要求綁卡驗證，APP 尚未走通）|
| Checkout Pipeline | 無定期購特殊 processor，全部由 mweb 的 PayProcess Pipeline 處理 |

### 責任分層

```
Cart    ← 管「能不能買」（驗證 App 限制、取得週期選項、存使用者選擇）
mweb    ← 管「怎麼建單」（建 TS、建 RegularOrder 合約記錄、存信用卡 token）
外部服務 ← 管「什麼時候再買」（觸發 SubscriptionOrderAutoGen API）
```

## 十二、訂閱合約的終止條件（不只有主動取消）

RegularOrder 只有兩個 `StatusDef`：`Ordering` / `Cancel`

終止分兩大類：

### 1. 主動取消

| 觸發者 | 動作 |
|--------|------|
| 消費者 | 在前台「定期購管理頁」點擊取消 |
| 商店後台 | 管理員手動取消 |

### 2. 系統自動取消（自動建單任何環節失敗）

| 失敗原因（StatusCauseDef） | 說明 |
|--------------------------|------|
| `CreditCardFail` | 信用卡刷卡失敗（餘額不足、卡片過期等）|
| `CreditCardBlackList` | 信用卡被列入黑名單 |
| `MemberInBlackList` | 消費者帳號被列入黑名單 |
| `SalePageIsClose` | 商品頁被關閉 |
| `SalePageIsDelete` | 商品頁被刪除 |
| `SkuIsClose` | 商品選項（規格）被關閉 |
| `StockNotEnough` | 庫存不足 |
| `OverSellingEndDateTime` | 超過銷售截止時間 |
| `UnstartSelling` | 商品尚未開賣 |
| `PayOrDeliveryTypeNotAvailable` | 付款 / 配送方式不可用 |
| `LocationPickupNotAvailable` | 門市已關閉，無法門市自取 |
| `Other` | 其他未預期錯誤 |

以上邏輯在 `TradesOrderService.GetAutoGenStatusCause()` 中，把各種 Exception 類型對應到 CauseDef Enum。

### 3. 次數到達（靜默結束）

當 `MaxDeliverCount` 有設定時，**由外部呼叫端（Commerce Worker）負責判斷次數達到上限後不再觸發**。  
mweb 本身不會在每次建單後自動把合約 Cancel，是外部排程不再呼叫 API。

### 狀態機

```
首次購買結帳
    ↓
RegularOrder.StatusDef = Ordering（訂閱中）
    ↓
每個週期外部觸發 SubscriptionOrderAutoGen
    ├── 成功 → 繼續 Ordering，更新 NextExpectShippingDate
    ├── 失敗 → StatusDef = Cancel，記錄 StatusCauseDef（原因）
    └── 次數到了（外部判斷）→ 不再觸發，合約靜默結束

消費者主動取消 → StatusDef = Cancel
```
