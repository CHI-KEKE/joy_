⚠️ liveapi Session 驗證失敗分析紀錄（SessionNotExistException）

📅 分析日期：2026-07-09 🏷 站台：Live Buy WebAPI（liveapi，nine1.live.buy） 🌐 環境：prod-91app-live 📌 狀態：已釐清根因
🔴 問題描述
🚨
使用者呼叫 GET /api/live/comments/room 時，前端最終收到 401 Unauthorized，Log 中出現： Session validation failed for session "351b706cadbd4865bd51431c07e3dd71" ip="60.250.142.219"。 在初步查詢 Loki 時，同一時間點卻看到 /api/live/comments/room 這條路徑被標記為 404，造成「到底是 401 還是 404」的混淆，需要進一步追查。

現象

  • Session ID：351b706cadbd4865bd51431c07e3dd71，userId=108204，isImpersonated=True
  • 來源 IP：60.250.142.219
  • Loki 查詢 _props_RequestPath = /api/live/comments/room 時，_props_StatusCode 顯示為 404，耗時僅 21ms
  • 但程式碼中 SSO Middleware 對驗證失敗的處理是回 401，並沒有任何邏輯會讓這條路由回 404
🔗 完整鏈路說明

C:\91APP\AI_Devs\liveby\nine1.live.buy\src\Web\Nine1.Livebuy.Web.Api\Sso\Middleware\SsoAuthenticationMiddleware.cs

這 4 行 log（Start/Sending/Received/End processing HTTP request）是 .NET HttpClientFactory 內建的 outbound 呼叫日誌， 對象是 session-mgmt 的 /session/renew，跟耗時 21ms 完全吻合，並非 /api/live/comments/room 本身的路由結果。
4
TryRenewSessionAsync: SessionNotExistException for session "351b706..." userId="108204"
Session Client SDK 將 404 回應轉譯為 SessionNotExistException，代表 Session Mgmt 服務端已經找不到這個 session/token
5

SsoAuthenticationMiddleware.cs:206 設定 context.Response.StatusCode = 401，最終回給前端的是 401
🧩 為何 Loki 查詢時會誤判成 /api/live/comments/room 回 404
💡
outbound 呼叫 /session/renew 的這 4 行 log，是在同一個 incoming request （/api/live/comments/room）的 logging scope 內產生的。 Middleware/Enricher 會把外層 incoming request 的 RequestPath 帶入這個 scope 下所有的 log， 因此 Loki 的結構化欄位 _props_RequestPath 會被 enrich 成 /api/live/comments/room， _props_StatusCode 也順帶帶成了這筆 outbound 呼叫本身的 404， 造成「表面上看起來像是這條路由回 404」的錯覺。
層級 實際回應 說明
liveapi → 前端（incoming request） 401 Unauthorized SsoAuthenticationMiddleware 判定 session 無效後設定的真實回應碼
liveapi → Session Mgmt Service（outbound /session/renew） 404 Not Found Session Mgmt 服務端找不到該 session/token，是 log 中 404 的真正來源
✅ 根因結論
🎯
真正的根因是：Session Management 服務端已經找不到這個 session/token（SessionNotExistException）， 導致 Token 過期後的自動續期（Renew）失敗，SsoAuthenticationMiddleware 判定該次會話無效，最終回應 401 給客戶端。 Loki 上看到的 404 只是同一個 request scope 內、outbound 呼叫 /session/renew 的日誌被 enrich 混淆所致， 並非 /api/live/comments/room 這條路由本身發生 404。

可能造成 SessionNotExistException 的情境

  • Session 已在 Session Mgmt 服務端過 TTL 被清除，但本地 Redis 的 authData/userData 尚未同步失效
  • 該 session 在其他流程被主動登出 / 下線（例如單一裝置登入踢除、後台強制登出）
  • Impersonation（isImpersonated=True）情境下的 session 生命週期與一般使用者不同，可能提早被回收

後續可追查方向

  • 向 Session Management 服務team 確認該 userId=108204 的 session 何時、為何被清除
  • 確認 Impersonation session 的 TTL 設定是否與一般 session 不同，是否造成提早失效
  • 評估是否需要在 Renew 失敗、判定為 SessionNotExistException 時，於回應中補充更明確的錯誤碼，避免前端/監控誤判為單純路由 404
