1. 整體架構：涉及哪些多語系資料表

商品頁相關的多語系資料儲存在 DynamoDB（而非 SQL Server），依用途分為三張表（MultilingualTableNameEnum）：

資料表 Enum對應內容Entity
SalePage商品頁標題 / SEO 標題 / SEO 關鍵字 / SEO 描述SalePageMultilingualItemEntity
SaleProductDesc商品詳細說明（銷售重點 / 商品特色 / 詳細內容 Content）SaleProductDescMLItemEntity
SaleProductSKU商品選項（SKU）名稱組合SaleProductSkuMultilingualEditItemEntity

每張表以 (module, id) 為 key，id 為對應的 SalePageId 或 SkuId，內容再依 LangId（如 en-US、zh-CN）分組儲存。

2. 多語系存取核心方法（DynamoDB）

檔案：CrossLayer/Utilities/Multilinguals/MultilingualService.cs

public void CreateOrModifyMultilingualItemToDynamo<T>(MultilingualTableNameEnum module, long id, List<T> langItems)
    where T : MultilingualBaseEntity
{
    var contents = langItems.ToDictionary(item => item.LangId);
    this._mlAdmin.CreateOrUpdate(module.ToString(), id.ToString(), contents);
}
關鍵行為：此方法沒有任何「空值判斷」。只要某語系的物件存在於傳入的 langItems list，就會被組進 dictionary，直接呼叫 CreateOrUpdate，對 DynamoDB 執行「該語系整包覆蓋」。
換句話說：呼叫端（Service）自己要負責過濾掉不該寫入 / 全空的語系資料，這個共用方法本身不會幫你判斷。

4. CheckSaleProductSkuMultilingualItems 全填/全不填檢查

檔案：SalePageService.cs，第 5699 行

private void CheckSaleProductSkuMultilingualItems(
    Dictionary<string, List<string>> skuCheckDic,
    Action allValuedAction,
    DelegateFunctionWithParameter<string> allEmptyAction)
{
    foreach (var dic in skuCheckDic)
    {
        if (dic.Value.All(p => string.IsNullOrEmpty(p) == false))
        {
            allValuedAction();              // 全部有值 → 不做事，照常寫入
        }
        else if (dic.Value.All(p => string.IsNullOrEmpty(p)))
        {
            allEmptyAction(dic.Key);         // 全部沒值 → 呼叫端移除該語系，不寫入 Dynamo
        }
        else
        {
            throw new ApplicationException(Translations.Backend.Exception.Message.InvalidData);
            // 半填半不填 → 視為不合法輸入，直接擋下整個請求
        }
    }
}

設計目的：避免 SKU 多語系名稱出現「英文填了、簡中沒填」這種半調子狀態，導致前台切換語系顯示錯亂；同時也避免使用者「不想填某語系」時，被空字串誤蓋掉既有資料。

5. 核心問題：SalePageMLItems 沒有「全空跳過」保護

現況：
  • UpdateSalePageInfoWithSku 與 UpdateSalePageSeo 在寫入 SalePage 多語系（Title / SEOTitle / SEOKeywords / SEODescription）前，都沒有比照 SKU 的 CheckSaleProductSkuMultilingualItems 做「全空則移除、不寫入」的檢查。
  • 只要前端把 SalePageMLItems 內某語系（如 en-US、zh-CN）所有欄位都傳空字串 ""，該語系物件依然會被整包送進 CreateOrModifyMultilingualItemToDynamo，進而 CreateOrUpdate 覆蓋 DynamoDB 既有內容。
  • 結果：原本已存在的多語系 Title / SEO 資料會被覆蓋成空字串，等同被清除，且此行為不會拋出任何錯誤或警示，使用者可能無感中遺失多語系內容。

實際案例（UpdateSalePageInfoWithSku Request 節錄）

"SalePageMLItems": [
  { "Title": "", "SEOTitle": "", "SEOKeywords": "", "SEODescription": "", "LangId": "en-US" },
  { "Title": "", "SEOTitle": "", "SEOKeywords": "", "SEODescription": "", "LangId": "zh-CN" }
]

此請求送出後，第 1995 行 CreateOrModifyMultilingualItemToDynamo(SalePage, salePageId, entity.SalePageMLItems) 會直接把 en-US、zh-CN 兩個語系原本的內容全部覆蓋為空字串。

6. 建議修正方向

  1. 比照 SKU 的檢查機制：在寫入 SalePage / SaleProductDesc 多語系前，針對每個語系判斷「Title / SEOTitle / SEOKeywords / SEODescription 是否全部為空」，全空則從清單中移除（不寫入），維持 Dynamo 既有資料；只有「至少有一欄有值」才寫入該語系。
  2. 共用邏輯抽出：可以把 CheckSaleProductSkuMultilingualItems 的全填/全不填判斷邏輯，抽成通用的 CheckMultilingualItemsAllOrNothing<T> 之類的共用方法，讓 SalePageMLItems、SaleProductDescMLItems、SKU 名稱都能重複使用，避免各流程各自實作、邏輯不一致。
  3. 單元測試補強：針對「全空語系不應覆蓋既有資料」新增測試案例，確保未來修改不會再次踩雷。
  4. 短期防呆：若暫不調整既有商業邏輯，至少可在 API 層（Controller / Model Validation）針對全空的語系物件先行過濾，避免傳到 Service 層才處理。
