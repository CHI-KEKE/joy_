# Q1

## 問題

`BatchCreateAsync` 中的 ConditionId 查找邏輯：

```csharp
PromotionEngineSpecialPrice_ConditionId = promotion.ExtraPurchaseRuleList.FirstOrDefault(e =>
    promotionType == PromotionEngineTypeDefEnum.CartReachPieceExtraPurchase
        ? e.ReachPiece == x.ReachPiece
        : e.ReachPrice == x.ReachPrice)?.ConditionId ?? 0
```

這段表示只要 Reach 門檻匹配就取對應的 ConditionId。  
**但 Reach 門檻與 ConditionId 是一對一關係嗎？會不會一個 Reach 門檻對應多個 ConditionId？**

---

## 結論

**是一對一關係，不會出現一個 Reach 門檻對應多個 ConditionId 的情況。**

---

## 分析

### 資料結構

`ExtraPurchaseRuleList` 每個元素代表活動的一個**階**：

```
ExtraPurchaseRuleList = [
  { ConditionId: 1, ReachPiece: 2,  ReachPrice: 0 },  // 第 1 階
  { ConditionId: 2, ReachPiece: 5,  ReachPrice: 0 },  // 第 2 階
  { ConditionId: 3, ReachPiece: 10, ReachPrice: 0 },  // 第 3 階
]
```

- `ConditionId`：階的代理鍵，由 `CartReachPieceExtraPurchaseRuleService` 建立時以 `nextConditionId++` 自動分配，天然唯一
- `ReachPiece` / `ReachPrice`：階的自然鍵，由 Validator 的嚴格升序（`<=`）確保每階不重複

### 雙向唯一性保證

| 方向 | 保證來源 | 結果 |
|------|---------|------|
| ReachPiece → ConditionId | Validator 嚴格升序（`<=`）：ReachPiece 唯一 | 一對一 |
| ConditionId → ReachPiece | `nextConditionId++`：ConditionId 唯一 | 一對一 |

### Validator 核心邏輯

```csharp
// 滿件加價購：ExtraPurchaseRuleListPieceBeSortedAscending
if (extraPurchaseRuleList[i].ReachPiece <= extraPurchaseRuleList[i - 1].ReachPiece)
    return false;  // <= 包含等於，等值（重複）也會被擋掉

// 滿額加價購：ExtraPurchaseRuleListBeSortedAscending
if (extraPurchaseRuleList[i].ReachPrice <= extraPurchaseRuleList[i - 1].ReachPrice)
    return false;
```

使用 `<=` 而非 `<`，隱式保證了門檻值的唯一性。

---

## `FirstOrDefault` 的安全性

由於 `ReachPiece`（或 `ReachPrice`）在同一活動內唯一，`FirstOrDefault` 等同於 `SingleOrDefault`：

- **找到** → 唯一那一階的 ConditionId，結果正確
- **找不到** → 回傳 `null`，`?? 0` fallback 為 0（代表資料異常）

不可能出現「找到多筆但只取第一筆」而遺漏資料的情況。

---

## 設計語意

> `ReachPiece`（門檻件數）是一個階的**自然鍵**  
> `ConditionId` 是它的**代理鍵**  
> 兩者在同一活動內必然一對一對應
