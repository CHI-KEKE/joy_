# 退貨單查詢 — 加購品辨別邏輯優化

> Story: [#604576](https://dev.azure.com/91APP/91APP/_workitems/edit/604576)
> Branch: `feature/VSTS604576-退貨單查詢-加購品辨別邏輯優化`
> 異動專案: NineYi.Sms (SMS 後台)

---

## 1. 背景與目標

退貨單查詢列表（`QueryReturnGoodsOrder`）需顯示加購品的類型（滿額加價購 / 滿件加價購）。
優化前程式碼對 **所有** 子單做全量查詢 `SalesOrderCustomInfo`，即使批次中完全沒有 CartExtraPurchase 商品仍然會送出 DB 查詢，造成不必要的效能損耗。

**目標：** 僅當批次中有 CartExtraPurchase 子單時才查詢，並將查詢邏輯與回填邏輯分別抽成獨立私有方法，提升可讀性與可維護性。

## 3. 現況分析（優化前）

### 問題點

```csharp
// 優化前：對所有子單 TsCode 全量查詢，不管有沒有 CartExtraPurchase
var allTsCodes = mappedEntityList
    .Where(i => string.IsNullOrEmpty(i.TradesOrderSlaveCode) == false)
    .Select(i => i.TradesOrderSlaveCode)
    .Distinct().ToList();

cartExtraCustomInfoDic = this._salesOrderCustomInfoService
    .GetCartExtraPurchaseCustomInfosBySourceCodes(shopId, allTsCodes);
```

- 無論批次是否含 CartExtraPurchase 商品，都會送一次 DB 查詢
- 邏輯直接內嵌在主流程中，難以閱讀與測試

### 4.2 關鍵邏輯說明

#### `QueryCartExtraPurchaseCustomInfoMap`

**職責：** 篩選含 CartExtraPurchase 的子單 TsCode → 查詢 CustomInfo → 回傳 Map

| 條件 | 行為 |
|---|---|
| 無 CartExtraPurchase 子單 | Early return 空 Dictionary，不送 DB 查詢 |
| 查詢成功 | 回傳 `Dictionary<TsCode, PromotionEngineTypeDef>` |
| 查詢失敗（Exception） | Catch 後 log Error，回傳空 Dictionary，主流程不中斷 |

#### `ApplyCartExtraPurchaseTypeDef`

**職責：** 對單一 entity 標記 RuleType 並回填 `CartExtraPurchaseTypeDef`

| 條件 | 行為 |
|---|---|
| 一律執行 | 加入 `CartExtraPurchase` 到 `TradesOrderSlaveRuleTypes` |
| `cartExtraCustomInfoDic` 為 null 或 TsCode 為空 | Guard clause，不回填 TypeDef |
| Map 中找得到 TypeDef | 設定 `entity.CartExtraPurchaseTypeDef` 並 log |
| Map 中找不到（或為空字串） | TypeDef 維持 null（前端顯示 fallback） |

### 4.3 防護設計

| 防護點 | 做法 |
|---|---|
| 批次無 CartExtraPurchase | guard clause early return，完全跳過 DB 查詢 |
| DB 查詢失敗 | try-catch，Error log 含完整 Exception，回傳空 Map |
| `cartExtraCustomInfoDic` 為 null | guard clause，避免 NullReferenceException |
| TsCode 為空字串 | `string.IsNullOrEmpty` 防護，篩選時已排除 |
| TypeDef 不符合任何已知值 | 維持 null，不寫入錯誤的文案 |

## 7. 技術 Takeaway

### 設計決策

1. **效能 guard clause 優先**：判斷批次是否有 CartExtraPurchase 子單，避免對所有批次都發出無謂的 DB 查詢。大流量環境下，大多數退貨單不含加購品，此優化效果顯著。

2. **查詢失敗不阻斷主流程**：`QueryCartExtraPurchaseCustomInfoMap` 的 try-catch 設計讓 CustomInfo 查詢失敗時，`CartExtraPurchaseTypeDef` fallback 為 `null`，退貨單列表仍正常顯示，不影響客服作業。

3. **方法職責單一**：將篩選 TsCode + 查詢 + 回填分成兩個私有方法，各自可獨立測試，未來若邏輯變更只需修改對應方法。

### 注意事項

- `SalesOrderSlaveItemTypeMode` 中 CartExtraPurchase 的 mode code 為 `"C"`，由 `[OrderItemModes("C")]` attribute 定義，判斷邏輯依賴 `OrderItemModeHelper.ContainMode`。
- `CartExtraPurchaseTypeDef` 的值來自 `SalesOrderCustomInfo.JsonData` 中的 `PromotionEngineTypeDef` 欄位，由 `ISalesOrderCustomInfoService.GetCartExtraPurchaseCustomInfosBySourceCodes` 解析。
- 此欄位為前端識別滿額/滿件加購品所需，**前端尚未使用**（本次需求僅確保後端正確回傳）。

### 後續建議

- 前端可使用 `CartExtraPurchaseTypeDef` 在退貨單列表顯示「滿額加價購品」/「滿件加價購品」區別文案，與消費者訂單查詢列表行為一致。
- 若 `ExportReturnGoodsOrderData`（匯出功能）也需區分，可參考本次同樣的模式擴充。
