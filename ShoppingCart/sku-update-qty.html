二、Calculate Processor Flow（重算購物車的內部管線）

由 ProcessorFlowManager 依 ProcessorDefinitionCenter.CalculateProcessorLayers 定義的順序執行，每個 Layer 內的 Processor 若為同一層則平行執行，執行完畢後統一記錄一行 FlowType : Calculate, ProcessorLog : [...] 匯總所有子步驟的耗時與結果。

Layer 1CalculateProcessor
呼叫 Cart Domain：POST /api/carts/calculate，取得重算後的購物車主體資料（金額、商品清單、符合的促銷資訊 PromotionInfoList 等）。
Layer 2ArrangePromotionRuleInfoProcessor
整理活動資訊，記錄「取得活動給券資訊開始」；呼叫 Promotion Frontend API：POST /api/promotion-rules/list-by-ids 取得給券活動規則，再記錄「符合的給券活動數量：N」。
Layer 3GetSalepagePromotionDisplayTextProcessor
再次呼叫 POST /api/promotion-rules/list-by-ids（用途為商品卡折扣活動提示文案），將商品與活動 mapping 結果記錄為「商品與活動 mapping Result : [...]」，決定顯示順序：已符合活動 → 未符合活動 → APP 獨享提示 → 無法參與活動 → 各種不適用文案。
Layer 4（平行執行）9 個顯示文案 Processor
  • GetSalepageDiscountDisplayTextProcessor — 商品卡折扣顯示文案
  • UpdateLoyaltyPointDisplayStatusProcessor — 更新點數顯示於前台的文案／狀態
  • GetInsufficientPointsSalepageDisplayTextProcessor — P1 點數不足點加金商品卡提示文案
  • GetPurchaseExtraDisplayTextProcessor — 商品卡加價購顯示文案
  • GetDesignatePaymentPromotionDisplayTextProcessor<CartEntity> — 指定金流活動顯示文案
  • GetLoyaltyPointExcludedDisplayTextProcessor — 點數折抵排除商品顯示文案
  • GetUnmatchSalepageBundleDisplayTextProcessor — 不符合組合商品規則之重新選購文案
  • GetInStoreOnlySalepageDisplayTextProcessor — 門市限定商品提示文案
  • UnreachCartExtraPurchaseDisplayTextProcessor — 購物車滿額滿件加價購活動提示文案
Layer 5ArrangeHighlightTagProcessor
整理購物車商品的 HighlightTag（如優惠標籤）資訊，作為前端顯示用。
結尾CheckSelectedCheckoutPayTypeGroup
重算完成後，檢查目前已選擇的付款方式分組是否仍然有效。

六、觀察與建議

截圖中第一段請求 Request completed for POST .../api/carts/sku-update-qty ... after 16144.2544ms，相較於後續 calculate（156ms）與 promotion-rules/list-by-ids（<10ms）明顯異常緩慢。由於整體 Log 內容與程式碼邏輯完全吻合（登入判斷 → 呼叫 Cart Domain 更新 → 重算 → 促銷/顯示文案整理 → 贈品自動預選皆有執行），此耗時應非邏輯錯誤造成，而是該次請求中 呼叫 Cart Domain /api/carts/sku-update-qty 本身（Layer 3.2）或其上游（DB / Redis / 限次器服務）出現延遲，建議後續針對該次 RequestId 0HNN1A9TG4G17:00000008 往 cart-domain 服務端的 Log 追查實際延遲發生點。
